# LiDAR Hackathon

Инструменты для работы с данными лидара: визуализация облаков точек из ROS 2 bag-файлов и LAZ-файлов, проверка габарита железнодорожного пути.

## Структура проекта

```
├── for_hackathon/               # ROS 2 bag-файлы (Hesai LiDAR, PointCloud2)
│   ├── doubleT_obstacle/        # Двойная стрелка + препятствие (~20 сек, 201 кадр)
│   ├── doubleT_platform/        # Двойная стрелка + платформа (~34 сек, 345 кадров)
│   ├── roundT_doubleT/          # Круглая + двойная стрелка (~25 сек, 252 кадра)
│   ├── roundT_pressureGate_roundT/                   # Круглая + ворота + круглая (~27 сек, 268 кадров)
│   ├── roundT_squareT_pressureGate_squareT/          # Круглая + прямоуг. + ворота + прямоуг. (~55 сек, 545 кадров)
│   └── squareT_platform_squareT_switch/              # Прямоуг. + платформа + прямоуг. + стрелка (~88 сек, 877 кадров)
├── visualize_bag.py             # Анимированная визуализация bag-файлов (без ROS)
├── snapshot.py                  # Интерактивный 3D-просмотр одного кадра
├── trim_bag.py                  # Прореживание bag-файла (каждый N-й кадр)
├── view_cloud.py                # Просмотр LAZ/LAS облаков точек
├── gabarit.py                   # Проверка габарита ж/д пути по аннотированным рельсам
├── Dockerfile                   # ROS 2 Humble (для ros2 bag play)
└── docker-compose.yml           # Запуск player + listener в Docker
```

### Обозначения в названиях bag-файлов

| Сокращение | Что это |
|---|---|
| `roundT` | Круглая стрелка (round turnout) |
| `doubleT` | Двойная стрелка (double turnout) |
| `squareT` | Прямоугольная стрелка (square turnout) |
| `platform` | Платформа (перрон) |
| `obstacle` | Препятствие на пути |
| `pressureGate` | Напорные ворота / шлагбаум |
| `switch` | Стрелочный перевод |

## Визуализация bag-файлов (без ROS, без Docker)

Скрипт читает `.db3` (SQLite) напрямую, парсит CDR-сериализованные PointCloud2 и показывает покадровую анимацию в Open3D.
Кадры читаются и парсятся **по одному, по мере показа** (память не растёт с длиной bag), поэтому запуск мгновенный.

```bash
# По умолчанию — doubleT_platform
python3 visualize_bag.py

# Любой другой bag — просто указать путь к папке
python3 visualize_bag.py for_hackathon/doubleT_obstacle
python3 visualize_bag.py for_hackathon/roundT_doubleT
python3 visualize_bag.py for_hackathon/roundT_pressureGate_roundT
python3 visualize_bag.py for_hackathon/roundT_squareT_pressureGate_squareT
python3 visualize_bag.py for_hackathon/squareT_platform_squareT_switch
```

Флаги:

| Флаг | Смысл |
|---|---|
| `--real-time` | темп по таймстемпам bag (записи сняты на ~10 Гц) вместо фиксированного `--fps` |
| `--fps N` | скорость воспроизведения, по умолчанию 10 |
| `--max-points N` | прореживание для отображения, по умолчанию **0 = все точки** (нужно только на слабом GPU) |
| `--start N` | с какого кадра начать |
| `--point-size F` | размер точки, по умолчанию 2.0 |
| `--no-loop` | остановиться на последнем кадре |

Про скорость: главный расход — не `update_geometry` (<1 мс), а приведение типа при подаче точек в Open3D.
`Vector3dVector` ожидает float64, и на массиве float32 pybind конвертирует **поэлементно**: 112 мс на 185k
точек и 208 мс на 346k, против ~1 мс после `astype(np.float64)` (замерено). В скрипте приведение сделано,
поэтому все точки рисуются на 10 Гц без прореживания. `--max-points N` остался запасным вариантом
(равномерно оставить каждую N/len-ю точку) — форма облака при этом сохраняется.

При закрытии окна скрипт печатает, сколько кадров показал и за какое реальное время.

Управление в окне Open3D: мышь — вращение, scroll — зум, Q — выход.

## Прореживание bag-файла

# Каждый 5-й кадр (по умолчанию)

## Веб-вьюер (`web_viewer.py`)

Просмотрщик облака точек в браузере — на смену Open3D-инспектору: three.js и
OrbitControls лежат локально в `web/`, сервер поднят на стандартной библиотеке
Python, новых зависимостей нет, интернет не нужен. Кадр считается в Python
(`bag_reader.py` + `zones.py`), браузер только рисует.

```bash
python3 web_viewer.py for_hackathon/doubleT_obstacle

# дальше 60 м не грузить, точки крупнее
python3 web_viewer.py for_hackathon/doubleT_obstacle --max-dist 60 --point-size 4
```

Кадры читаются из `.db3` (SQLite) и парсятся на лету; сервер держит соединение на
поток, браузер предзагружает два кадра вперёд.

**Управление**: ЛКМ — орбита, ПКМ или средняя кнопка — сдвиг, колесо — зум.
`Space` — пауза, `←`/`→` — кадр, `Tab` — свернуть панель. В панели: пресеты камеры,
транспорт со слайдером и скоростью, раскраска, модель рельсов (ось, колея,
контактный рельс), размер точки, дальность, сетка/оси/рельсы и легенда зон.
Страница перезагружается сама, когда сервер видит правку файлов в `web/`.

**Флаги**: `--host`, `--port` (8765), `--mode` (по умолчанию `zones`), `--max-dist`
(200 — сколько сервер отдаёт клиенту; видимый диапазон внутри этого задаёт ползунок
`Дальность, м` в панели, 5…200), `--analysis-dist` (40 — дальность для геометрии:
коридор, ось, профиль рельсов, засорённость), `--behind` (5), `--max-points`
(400000), `--point-size` (3), `--axis-x`, `--gauge-mm`, `--obstacle-points` (20),
`--obstacle-height` (0.5), `--rail-clearance` (0.30), `--track-cache` (каталог
готовой геометрии пути, по умолчанию `.cache/track`; `none` — выключить), `--open`.

### Геометрия пути заранее (`precompute_track.py`)

Геометрия пути кадра (`/track`, а через неё и метка рельса в
`/frame?mode=zones` и `/labels`) считается вызовом `track_geometry.build_track` —
0.2–0.6 с на кадр, а воспроизведение просит 10 кадров в секунду (бюджет 0.1 с).
Раньше сборка шла прямо в запросе: сервер успевал 2–2.5 кадра/с, очередь
предзагрузки клиента не рассасывалась. Сборку можно сделать заранее:

```bash
python3 precompute_track.py for_hackathon --jobs 3
```

Скрипт идёт по кадрам 0, 1, 2, … каждой записи и кладёт в хранилище
`.cache/track/<запись>/<кадр>.json.gz` ровно те байты, которые отдал бы `/track`
при сборке на месте (сериализованный JSON, сжатый gzip). Сервер читает готовый
кадр первым делом, до всякой сборки: распакованное содержимое отдаётся как есть,
поэтому данные не меняются — только способ их достать (проверено побайтово на 12
кадрах шести записей). Кадра в хранилище нет — поведение прежнее, сборка на месте,
и один раз за сессию в лог идёт предупреждение; `GET /bags` показывает по каждой
живой записи счётчики `store_hits` / `cache_hits` / `builds`.

Замеры на `for_hackathon` (все 2488 кадров, 6 записей; «до» — сервер без
хранилища, «после» — с ним):

| | до | после |
|---|---|---|
| `/track`, нового кадра | медиана 0.387 с (0.305…0.549) | медиана 0.012 с (0.002…0.025) |
| `/frame?mode=zones`, нового кадра | медиана 0.471 с (0.380…0.766) | медиана 0.087 с (0.035…0.178) |
| сборок на месте за 50 идущих подряд кадров | каждый кадр (по 0.3–0.5 с в `/track`) | 0 (счётчик `builds` в `/bags`) |

Полный проход `precompute_track.py` (2488 кадров, `--jobs 3`) — 472 с, ошибок 0,
хранилище 511 МБ. Остаток времени `/frame?mode=zones` — это уже не геометрия, а
разбор кадра из `.db3` и метки зон: у самого плотного кадра (`doubleT_obstacle`,
346 тыс. точек) разбор 0.10–0.11 с плюс ~0.05 с на метки, поэтому там выходит
0.14–0.18 с; у остальных пяти записей медиана 0.070–0.084 с.

Что важно знать: **порядок кадров**. У `build_track` есть тёплая (инкрементальная)
сборка и связь решений соседних кадров (`warm` и `LINK_*` в `track_geometry.py`),
поэтому кадр, посчитанный после пропущенного, выходит не таким, как в непрерывном
проходе: замер — последний кадр `roundT_doubleT` в порядке воспроизведения 574 КБ
против 1043 КБ в изолированном холодном проходе. Поэтому `precompute_track.py`
идёт по кадрам строго по порядку, и хранилище фиксирует тот вариант геометрии,
который показывало воспроизведение. Новая запись или новый снимок → запустите
`precompute_track.py` по ней снова (уже посчитанные кадры пропускаются, `--force`
пересчитывает всё); старые файлы снимков хранилище не различает, поэтому при
подмене `.db3` под тем же именем нужен `--force`.

### Семантические зоны (`--mode zones`, по умолчанию)

Пять классов плоскими цветами вместо градиента, плюс красные разрывы рельсов.
Границы берутся из данных и все правятся слайдерами.

| класс | правило | цвет |
|---|---|---|
| **рельсы** | модель по оси пути (см. ниже) | оранжевый |
| **низ** | `z − z_пол(y) < 0.30 м` | серо-голубой |
| **потолок** | `z ≥ 2.0 м` | маджента |
| **стены** | `|x − x_стены| < 0.5 м` выше ложа | бирюзовый |
| **средний** | всё остальное | зелёный |

**Пол — наклонная плоскость, а не уровень.** Замерено: `z_пол(y) = −1.878 + 0.0218·y`,
СКО 9.5 см, уклон 2.2 % (либо уклон пути, либо лидар наклонён на ~1°). Поэтому «низ»
считается высотой **над плоскостью**; постоянный порог по Z красил бы дальние точки
неправильно.

**Стены находятся автоматически** — две сильнейшие вершины X-гистограммы точек выше
ложа: у `doubleT_obstacle` это `x = −2.65` и `x = +6.55` (тоннель ≈9.2 м).

**Рельсы — модель, а не детекция.** В этих данных рельсы не разделяются: средняя
интенсивность 10–13 и доля точек с `intensity > 25` равны 3–9 % в **каждой** Z-полосе,
а единственная яркая группа (верхние 0.5 %) — одиночный световозвращатель на
`x ≈ 5.9, y ≈ 0, z ≈ −0.5`. Отдельных гребней рельсов в геометрии тоже нет. Поэтому
рельсы строятся по оси пути: два ходовых на `x = ось ± колея/2` (1520 мм → ±0.76 м)
на высоте `z_пол(y) + 0.16 м` и контактный сбоку от оси (`Contact offset`, по
умолчанию 1.45 м **слева** по ходу, рабочая поверхность 160 мм над УГР, то есть
`contact_height = 0.32` м над полом — нормативы сведены в
`docs/superpowers/specs/2026-09-15-path-and-safety-tunnel-design.md`). Модель работает
только на разметку облака (зона `rail`) и на расчёт засорённости коридора; линиями в 3D она
больше не рисуется — ленты шли сквозь стены, их убрали из вьюера. Параметры правятся
слайдерами в панели, пол пересчитывается на лету.

**Ось выбирается по физическому ограничению — поезд не может проехать сквозь
вертикальное препятствие.** Из кандидатов внутри тоннеля (между стенами, с учётом
запаса) берётся та, у которой коридор свободен на наибольшей длине. Первая версия
брала середину между стенами — это неверно: она ставила левый рельс в столб. Замер
на `doubleT_obstacle` (41 бин по 1 м, запас 0.30 м):

| ось | свободно |
|---|---|
| **3.36 м — выбрана автоматически** | **40/41 = 98 %** |
| 2.71 м (что было правым рельсом) | 76 % |
| 1.95 м (середина между стенами) | 76 % |
| 1.19 м (что было левым рельсом) | **6/41 = 15 %** |

Ось **не подтверждена разметкой** (рельсы в этих данных не детектируются), но она
удовлетворяет ограничению проходимости. Абсолютная ось по-прежнему правится слайдером
`Axis x, m` или флагом `--axis-x`.

**Рельсы рвутся на препятствиях.** Поезд не может проехать сквозь вертикальное
препятствие, поэтому коридор (`колея/2 + запас`) проверяется на засорённость вдоль Y:
внутрь идут точки выше ложа и ниже габарита 3.7 м. Бин считается занятым, если в нём
не меньше `--obstacle-points` точек **и** они занимают по высоте не меньше
`--obstacle-height` (0.5 м, перцентили 5…95). Условие по высоте обязательно: одного
счёта точек мало — на `doubleT_obstacle` он красил **13–27 м из 46 м** красным, а это
были кромка балласта, кабельный лоток и стенка рельса вдоль края коридора высотой
0.0–0.19 м. С условием по высоте остаётся 1–5 м, при этом настоящий объект на
`y ≈ −38 м` (высота 1.0 м) по-прежнему ловится. Заблокированные участки красятся
**красным**, и рельс визуально упирается в препятствие вместо того, чтобы пройти
сквозь него; диапазоны печатаются в консоль строкой `RAILS blocked`. Засорённость
считается по всему bag'у один раз при старте, поэтому препятствие должно быть
неподвижным.

**Управление в режиме зон** (панель вьюера): `Ось X, м`, `Колея, мм`, `контактный
рельс` со смещением и стороной, `Размер точки`, `Дальность`, чекбоксы `сетка`,
`рельсы`, `оси`, `плотная заливка`.

Флаги: `--mode {height,intensity,range,ring,zones}` (по умолчанию `zones`), `--axis-x`,
`--gauge-mm`, `--obstacle-points` (20), `--obstacle-height` (0.5), `--rail-clearance` (0.30).

Цвета уходят в браузер как есть — палитра зон передаётся числами 0…255, а three.js
рисует их без тонмаппинга (`toneMapped: false`), поэтому на экране они совпадают с
таблицей. В Open3D-инспекторе было иначе: Filament пересчитывал цвета через sRGB, и
оттенки на экране отличались от заданных.

**Легенда цветов** (те же плашки в панели вьюера):

| цвет | что помечено |
|---|---|
| оранжевый | **рельс** — модельные линии на `ось ± колея/2` плюс контактный рельс |
| серо-голубой | **низ** — пол/балласт, в пределах 0.30 м над плоскостью пола |
| маджента | **потолок** — `z ≥ 2.0 м` (перекрытие) |
| бирюзовый | **стены** — найдены автоматически (`x = −2.65` и `+6.55`) |
| зелёный | **средний уровень** — всё, что выше ложа и ниже потолка |
| красный | **разрыв** — коридор занят препятствием, проезда нет |

### Замеры и известные ограничения

Замерено на `doubleT_obstacle` (346 808 точек/кадр): сервер `web_viewer.py` +
headless Chromium.

| метрика | значение |
|---|---|
| кадр в браузере | 338 000 точек после обрезки по дальности |
| время кадра | 190–700 мс: разбор CDR, обрезка и раскраска/классификация в Python |
| реальное воспроизведение | ~3.5 кадр/с вместо 10 Гц записи (9 с → 32 кадра) |
| размер кадра | ~4.4 МБ (12 байт заголовка + 12·n позиций + n меток) |
| засорённость коридора | 46 бинов по 1 м; было 27 м красным, стало 5 м (ось 4.05 м) |

Что дало ускорение в Open3D-скриптах (остаются `visualize_bag.py` и `snapshot.py`):

- **`astype(np.float64)` перед `Vector3dVector`** — было 205 мс на кадр, стало
  1.8 мс. `Vector3dVector` ждёт `float64`; на `float32` pybind конвертирует
  поэлементно, и в Open3D 0.19 нет `Vector3fVector`. **Это опровергает
  утверждение о «0.7 мкс/точку» выше: резать точки было не нужно.**
- Парсер: одно непрерывное копирование 16 байт на точку вместо четырёх
  отдельных копий колонок — 58 → 40 мс.

Ограничения:

- 190–700 мс на кадр — узкое место разбор 24 МБ CDR на кадр в Python; чтобы
  вытянуть 10 Гц, разбор нужно выносить в отдельный процесс.
- Засорённость коридора считается по всему bag'у один раз при старте, поэтому
  движущееся препятствие не поймается — нужен детектор по кадрам.
- Ось пути и положение рельсов не подтверждены разметкой (в этих данных рельсы
  не детектируются ни по интенсивности, ни по геометрии): это модель, и её числа
  задаёт человек слайдерами.
