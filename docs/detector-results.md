# Детектор препятствий: результаты на данных `for_hackathon/`

Два обязательных выхода валидации:

* **раздел 1** — таблица ложных срабатываний на 30 кадрах (6 записей × 5 кадров);
* **раздел 2** — FP/час по **всем** кадрам всех 6 записей (2488 кадров) —
  метрика, нормированная на время наблюдения. Один занятый бин на 30 кадрах сам
  по себе ничего не доказывает: важна частота, нормированная на время.

Алгоритм и обоснование порогов — `docs/detector-algorithm.md`.

Команды:

```bash
python -m unittest discover -s tests -q       # тесты, включая tests/test_detector_core.py
python -m validation.fp_per_hour              # FP/час по 2488 кадрам (раздел 2)
```

## 2. FP/час: ложные срабатывания по всему корпусу (2488 кадров)

Раздел 1 смотрел 30 кадров из 2488. Один занятый бин на такой выборке ничего не
доказывает: важна частота, нормированная на время наблюдения. Скрипт
`validation/fp_per_hour.py` прогоняет `detector.core.detect` по **каждому**
кадру всех шести записей `for_hackathon/*/*.db3` и считает FP/час.

Событие = кадр, в котором детектор выдал хотя бы одно препятствие. Нормы
Tagiew (arXiv 2307.02586): **≤ 10⁻² FP/ч** — предупреждение, **≤ 10⁻⁴ FP/ч** —
экстренное торможение.

```bash
python -m validation.fp_per_hour          # 2488 кадров, ~106 с на этой машине
```

Основание: модель оси — сохранённая полилиния (`track_models.json`,
`source=snapshot`), пороги — `DetectorConfig()` по умолчанию. Прогон держит
**единый снимок**: модели всех записей загружаются до первого кадра, а в отчёте
печатаются md5 файлов `detector/` на начало прогона (плюс проверка, что за время
прогона они не менялись). Ревизия, к которой относятся числа (md5 файлов на
момент прогона; совпадает с паспортом `detector_curve.txt`):

* `detector/core.py` — **md5 `f1ff2360d76dc23f23411691504753a3`**;
* `detector/profiles.py` — `1e5897f630656ad78a1dc07bfba48c6c`;
* `detector/track_models.json` — `bc66af685f9211bf951c22633d90525f`.

`detector/` правится параллельно другим агентом, поэтому числа — снимок именно
на эту ревизию. Более ранние ревизии давали другие числа: на прежнем снимке
корпус давал 313 событий, из них 282 — стены и платформы (сейчас их нет).
Прогон занял **219.7 с** (машина загружена; тот же набор раньше проходил за
~106 с — время здесь не метрика, а факт из `fp_per_hour_summary.csv`).

Время T — сумма `duration` из `metadata.yaml` шести записей = **250.17 с =
0.0695 ч**; размах таймстемпов кадров даёт то же самое.

### 2.1 Что это за события: 46 — настоящий человек, ложных нет

**`doubleT_obstacle`, 46 кадров (13–63, все на 55.7–56.5 м)** — это тот самый
человек, который по условию идёт по пути на ~56 м. Это **истинные срабатывания**:

| кадр | дальность, м | u, м | интервал по u, м | высота (span), м | точек |
|---|---|---|---|---|---|
| 13 | 55.8 | 0.90 | 0.62…1.22 | 0.82 | 72 |
| 17 | 55.8 | 0.52 | 0.23…0.91 | 0.90 | 84 |
| 23 | 55.9 | 0.23 | −0.07…0.52 | 0.76 | 69 |
| 29 | 56.0 | −0.22 | −0.55…0.23 | 0.54 | 66 |
| 48 | 56.0 | −0.06 | −0.36…0.32 | 0.64 | 81 |
| 57 | 56.4 | 0.42 | 0.05…0.82 | 0.87 | 86 |
| 63 | 56.4 | 0.91 | 0.63…1.20 | 0.76 | 62 |

Подпись настоящего объекта (все числа — из `validation/out/fp_per_hour_events.csv`,
46 строк):

* силуэт (`span` — от низа кластера до верха) **0.38–0.90 м у всех 46 событий**
  (медиана 0.76) — человек, а не конструкция 2–3 м;
* низ силуэта над УГР **0.362–0.377 м** у всех 46 (медиана 0.370) — предмет стоит
  на пути, а не висит на стене;
* 20–94 точек на событие (медиана 69), интервал по `u` 0.38–0.90 м, максимум
  `|u|` = 0.91 — внутри габарита;
* дальность держится 55.7–56.5 м (медиана 56.1), как в условии;
* главное: `u` **ПЛАВНО едет от кадра к кадру** — +0.90 (кадр 13) → +0.52 →
  +0.23 → −0.22 (кадр 29) → −0.46 (кадры 30–31), пропуск кадров 32–36 и обратно:
  −0.46 (кадр 37) → −0.06 → +0.42 → +0.91 (кадр 63). Человек переходит путь.

**Остальные 2287 кадров пяти записей — ноль событий.** Это и есть главное
изменение против прежней ревизии: там те же записи давали 282 ложных события
(стены и платформы, силуэт 1.5–3 м, `max |u|` = 1.24–1.25, десятки кадров подряд
на статичной сцене). Прежнее правило смотрело один бин: интервал, дошедший до
`|u| = 1.25`, считался стеной только если кончался до `1.07`, и «обрывок» края,
видимый внутри габарита, проходил как объект.

Теперь кластер проверяется на связность занятости в плоскости (y, u)
(`occupancy_components` в `detector/core.py`): компонент помечается `wall`, если
он выходит наружу габарита (`|u| > structure_out_m`) или тянется вдоль пути
дольше `max_structure_y_m`. Мера (из docstring, замерено там же): у человека
компонент **5–14 ячеек и 1–2 м по пути**, у стены/платформы — **45–277 ячеек и
11–46 м**, то есть на порядок больше. Тот же механизм виден в контроле «прямая
ось» (раздел 1: 2 бина вместо 13) и в проверке блока (раздел 9.3: габарит даёт
**0 событий на 314 кадрах** без известного объекта).

### 2.2 FP/час после вычета известного человека

`doubleT_obstacle` — не негатив: в кадрах 13–63 там настоящий человек. Поэтому
его 46 событий исключены, и их время вычтено из наблюдения. Окно берётся **по
таймстемпам**, а не по числу кадров (кадры идут неровно):

* первый кадр окна — 13, `frame_ts` = 1 788 354 624 405 331 031 нс;
* последний — 63, `frame_ts` = 1 788 354 629 398 569 181 нс;
* Δ = 4 993 238 150 нс = **4.993238 с = 0.00138701 ч**;
* время наблюдения без окна человека: 0.06949 ч − 0.001387 ч = **0.06810 ч**.

**События на остатке корпуса — 2287 кадров пяти записей — ноль.** Измеренной
частоты здесь нет, поэтому приводится только верхняя граница по «правилу трёх»
для нуля событий:

* **λ < 2.996 / 0.06810 = 44.0 FP/ч** — это **граница, а не измерение**: ноль
  событий за 0.07 ч совместим с истинной частотой вплоть до 44/ч;
* если считать по всему T, не вычитая окно: 2.996 / 0.06949 = 43.1 FP/ч — тот же
  порядок.

Прежняя ревизия давала здесь измеренное значение (282 ложных события →
4.19·10³ FP/ч). Теперь измерять нечего: ложных событий нет ни одного.

### 2.3 Верхняя граница и что доказуемо, а что нет

**При нуле событий** 95 %-я верхняя граница частоты — «правило трёх»:
`λ < −ln(0.05)/T = 2.996/T`. Это ровно наш случай на остатке корпуса (2.2):
**λ < 44.0 FP/ч** при T = 0.06810 ч.

* смысл: ноль событий за 0.07 ч совместим с истинной частотой вплоть до ~44/ч.
  Такой прогон **исключает только грубые отказы**; норму 10⁻²/ч он не
  подтверждает и не опровергает.

**Сколько часов нужно, чтобы доказать норму** (нулём событий, 95 %):

| норма | нужно наблюдений T ≥ 2.996/норма | наши 0.06810 ч (корпус без окна человека) — это |
|---|---|---|
| 10⁻² FP/ч (предупреждение) | **300 ч** (12.5 суток) | 0.023 % нужного |
| 10⁻⁴ FP/ч (торможение) | **29 960 ч ≈ 30 000 ч** (3.4 года) | 0.00023 % нужного |

То есть корпус `for_hackathon` (0.068 ч чистого наблюдения) **в принципе не может**
доказать ни одну из норм: разрыв в ~4400 раз для предупреждения и в ~440 000 раз
для торможения. Нормы требуют либо непрерывного многосуточного прогона, либо
ускоренной постановки (реплей корпуса в цикле с разметкой и накоплением времени).

Итог раздела: **на 2287 кадрах пяти записей событий ноль, а все 46 событий
корпуса — реальный человек в своём окне.** Цифра 662 FP/ч «по корпусу» — это
целиком истинные срабатывания (46 событий на 0.0695 ч); по негативной части
измеренного значения нет, есть только граница 44 FP/ч. Норму 10⁻²/ч этим корпусом
не доказать — нужно ~300 ч наблюдений.

## 3. Полнота: внесённый объект

Заявленных объектов в записях нет (единственный настоящий — человек в
`doubleT_obstacle`, раздел 2.1), поэтому полнота измеряется внесением
синтетического объекта — вертикальной плиты 0.70 × 1.60 м в габарите, точки на
обращённой к датчику поверхности (`detector.core.synthetic_object`). Всё замерено
на текущем снимке, по кадру 0 каждой записи:

| проверка | результат |
|---|---|
| плита 0.7 × 1.6 м, 6 записей × дистанции 12/20/30 м | **17/18 найдено** |
| ошибка дистанции | ≤ 0.08 м |
| плита при смещении от оси u = 0 / ±0.3 / ±0.6 м | найдена в 5 записях из 6 |
| плита при u = ±0.8 м | найдена в 5 из 6 (при −0.8 м — в 6 из 6); прежнее «не найдена» не воспроизводится |
| стена вдоль пути (6 м), заходящая в габарит краем (6 записей) | **6/6 не найдена** (0 бинов, 0 событий) |
| рельсы, корыто, ложе, лоток, свод, стена за габаритом (синтетика) | не найдены — тесты `tests/test_detector_core.py` |

Единственный пропуск — плита на 20 м в `squareT_platform_squareT_switch`: **все 7
поперечных положений** (0, ±0.3, ±0.6, ±0.8), то есть дело не в смещении от оси, а
в этой записи и этом кадре. Разница против прежней ревизии объяснима: раньше плита
у кромки отбраковывалась по «дошла до полосы кромки», а теперь — по связности
занятости (раздел 2.1), и плита, которая никуда за габарит не выходит, остаётся
объектом.

**Посадка объекта — в системе кадра.** `detector.core.synthetic_object` ставит
объект по МОДЕЛИ (а она в канонической системе, 9.7), а `detect` канонизирует ВСЁ
облако, включая дописанные точки объекта. Поэтому объект надо перенести в систему
кадра на позу кадра (`detector.core.axis_pose` → прибавить `pose.line(y)` к X), и
только тогда его `u` совпадёт с заданным. Замерено: без переноса плита, «поставленная
на ось», находилась детектором на `u` = 0.30…0.73 м (это ровно `−pose(y)`), с
переносом — на `u` = −0.02 м. Числа таблицы выше — с переносом. Протокол инъекций
`validation/synth.py` переноса не требует: он ставит бокс по геометрии САМОГО кадра
(`object_box(rings_meta, ...)`), то есть сразу в системе кадра.

20 повторов на кадр (кадр 0 каждой записи), после разогрева, один поток;
`detector.detect` с моделью текущего снимка (`detector.model_for_db`):

|---|---|---|---|---|
| doubleT_obstacle | 346808 | **12.0** | 14.0 | 18.2 |
| doubleT_platform | 185638 | 9.9 | 10.9 | 11.1 |
| roundT_doubleT | 189502 | 17.0 | 21.1 | 25.4 |
| roundT_pressureGate_roundT | 189864 | 16.1 | 28.8 | 55.3 |
| roundT_squareT_pressureGate_squareT | 185070 | 5.8 | 11.7 | 12.4 |
| squareT_platform_squareT_switch | 181792 | 19.8 | 22.1 | 24.2 |

Повторный замер тем же методом дал медианы в пределах ±1 мс (12.9 / 9.9 / 17.3 /
15.7 / 6.2 / 20.2). Разброс между прогонами — от загрузки машины: выброс 55.3 мс
на этом фоне не повторяется.

Бюджет ТЗ — 10 Гц (100 мс) на весь горячий контур. Ядро на самом большом кадре
(347 тыс. точек) — **12.0 мс медиана, 18.2 мс максимум**: и в бюджет ТЗ, и в
тестовый порог 60 мс (минимум из семи прогонов, `tests/test_detector_person.py`)
укладывается с запасом. Прежние числа (8.8 мс медиана, 10.7 мс максимум) на этом
снимке не воспроизводятся. Порог теста поднят с 30 до 60 мс и считается по
минимуму, а не по медиане: при 30 мс по медиане тест падал на здоровом коде под
нагрузкой машины (замерено 30.8 мс), а регресс в разы (прошлый давал 1.12 с) ловится
и так.

Разбор CDR в это время не входит. Замерено без кэша кадров (`cache_size=1`,
кадры 1..6 каждой записи): **24–70 мс** на кадр. Размер сообщения — 8.00 МБ на
кадр во всех записях, кроме `doubleT_obstacle` (23.99 МБ: 4.8 ГБ на 201 кадр);
по корпусу в среднем 9.29 МБ на кадр. Прежняя оценка «~40 мс на 24 МБ сообщение»
не воспроизводится: у самых больших сообщений разбор 70 мс медиана (88–180 мс по
замерам). В конвейере разбор идёт в фоновом потоке с опережением
(`BagFrames(prefetch_ahead=8)`), поэтому чтение кадров идёт параллельно счёту.

Полный прогон 2488 кадров (раздел 2) занял **106.1 с**, то есть **~42.7 мс/кадр**
вместе с чтением `.db3` — это и есть цена оффлайн-валидации корпуса.

## 5. Дальность: участок, подтверждённый проверкой по всем кадрам

Жёсткого «40 м» нет: длина рабочего участка у каждой записи своя, и задаёт её не
сенсор, а проверка по **всем** кадрам записи. Числа — из
`validation/out/fp_per_hour_summary.csv` (колонка `axis_range_m`):

| запись | участок габарита, м | длина, м | было |
|---|---|---|---|
| doubleT_obstacle | −63.75…−4.0 | 59.75 | −63.75 (без изменений) |
| doubleT_platform | −68.25…−4.0 | 64.25 | −68.25 (без изменений) |
| roundT_doubleT | −60.75…−4.0 | 56.75 | **−45.75, рост на 15 м** |
| roundT_pressureGate_roundT | −62.75…−4.0 | 58.75 | **−52.75, рост на 10 м** |
| roundT_squareT_pressureGate_squareT | −62.75…−4.0 | 58.75 | −62.75 (без изменений) |

Дальний конец (`valid_far_m`) — это ровно то, что подтвердила проверка:
`detector/build_models.py` продлевает ось по измеренной кривизне и уклону, а
участок сокращает шагами, пока на равномерно взятых кадрах записи есть ложные
срабатывания. Ближняя граница −4.0 м одинакова у всех шести записей.

**На двух круглых записях участок вырос именно из-за канонизации позы кадра**
(раздел 9.7). Прежде ось кадра бралась относительно модели-медианы, доворот
датчика копился в разброс: на `roundT_doubleT` он составлял 1.538 м, на
`roundT_pressureGate_roundT` — 1.104 м, и проверка обрезала участок там, где
разброс начинал давать ложные. После канонизации разброс упал до 0.169 и
0.142 м (`_meta.records[*].spread_canon_max_m`), и тот же участок прошёл проверку
на 15 и 10 м длиннее. На остальных записях разброс и до неё был мал
(0.032…0.057 м), поэтому их участки не изменились.

За участком канал габарита данные не рассматривает — поэтому P(габарит) на
75…150 м равна нулю (раздел 9.2). Это граница участка, а не порогов. Что при этом
видит сенсор, показывает столбец «видим» в 9.2 (посадка `ugr`): лучи попадают в
объект в 146 испытаниях из 180 на 75 м, 100 на 100 м, 53 на 125 м и 27 на 150 м,
а точек на объект (медиана) — 10 / 2 / 0 / 0. То есть примерно до 100 м объект
ещё освещён, дальше остаются единичные возвраты.

Целевые 200/300 м из ТЗ этими данными не подтверждаются: самое дальнее измерение
(150 м) даёт 27 попаданий из 180 и медиану 0 точек на объект. Детектор честно
сообщает свою дальность в диагностике (`max_data_range_m`, `corridor_max_range_m`)
и работает только по участку, где ось достоверна.

## 7. Чего не проверено

* **Ревизия детектора в разделе 2 — снимок.** Числа относятся к md5
  `f1ff2360…` (`detector/core.py`), `1e5897f6…` (`detector/profiles.py`) и
  `bc66af68…` (`detector/track_models.json`). Повторить прогон на новой ревизии —
  одна команда `python -m validation.fp_per_hour`.
* **Разметки нет.** Отнесение событий к «человек» сделано по геометрии (высота
  силуэта, низ силуэта над УГР, число точек, движение `u` по кадрам), а не по
  ground truth. «Человек» в `doubleT_obstacle` задан условием задачи; в остальных
  пяти записях событий нуль, так что опровергать там нечего — но и подтвердить их
  чистоту разметкой нечем: 0 событий не доказывает отсутствия объектов, он
  совместим с частотой до 44/ч (2.2).
* **Нормы 10⁻²/10⁻⁴ FP/ч этими данными недоказуемы в принципе** — нужно 300 ч и
  30 000 ч наблюдений соответственно.
* **Docker и ROS 2 вживую не запускались** — по решению заказчика упаковка снята
  с текущего этапа. Пакет `ros2_ws/src/tunnel_detector/` и `docker/` лежат
  готовыми, но сценарий `docker build → ros2 bag play` не прогонялся.
* **Полнота на реальных объектах не измерена** — в предоставленных записях их нет,
  использован внесённый объект. Реальный объект (человек, предмет) может давать
  меньше точек при той же высоте. Единственное исключение — человек на 56 м в
  `doubleT_obstacle`: найден в **46 кадрах из 51** (окно 13–63, дальность
  55.7–56.5 м, медиана 56.1), пропуск — кадры 32–36.
* **Движущиеся объекты** не отслеживаются: разметки нет.
* **Робastность к дождю/пыли/грязи на оптике** не проверялась.
* Дальний контур на записях с движением датчика не доведён (см. раздел 6).

## 9. Три канала цепочки на инъекциях: P(обнаружения) и FP по правилам

Разделы 1–7 мерят детектор габарита и упрощённый критерий `run_range_curve`
(«≥ 5 точек в окне ±1.5 м»), а не каналы цепочки. Здесь в тот же протокол
инъекций поставлены **три канала сразу**, и по каждому снят булев результат:

| канал | что считается | пороги |
|---|---|---|
| `габарит` | `detector.core.detect` (ось — `track_models.json`) | `DetectorConfig()` по умолчанию |
| `фон` | `stitch_bg.per_ray_residual` + `corridor_gate` + `count_clusters` | модуля: ≥ 5 точек, размах ≥ 0.3 м, по высоте ≥ 0.4 м |
| `контур` | `detector.contour.free_width` + `WidthTracker` | модуля: сужение ≥ 0.30 м, `PERSIST_BINS` = 2 бина, история 15 кадров |

Событие — срабатывание в окне **±2 м** от истинного центра объекта; правила
цепочки — **1-из-3** (любой канал) и **2-из-3**. Пороги каналов не подгонялись:
взяты их собственные значения из `DetectorConfig()`, `stitch_bg` и `contour`.

```bash
python -m validation.detector_curve     # 511.5 с: 2160 инъекций + 720 пустых кадров
```

Скрипт `validation/detector_curve.py`; выходы —
`validation/out/detector_curve_summary.csv` (дистанция → вероятности, FP, совместные
пропуски), `validation/out/detector_curve_trials.csv` (сырые испытания),
`validation/out/detector_curve.txt` (таблицы и диагностика). Протокол: 6 записей ×
10 пустых кадров × 3 поперечных положения × дистанции 25/50/75/100/125/150 м;
окно кадров — то же, что у `run_range_curve` (`empty_windows.json`).

**Ревизия.** Числа относятся к снимку `detector/` **до первого кадра**:
`core.py` `f1ff2360d76d…`, `profiles.py` `1e5897f63065…`, `track_models.json`

### 9.1 Датумы посадки: МНК-пол `synth` лежит НИЖЕ УГР детектора

### 9.4 Почему каналы `фон` и `контур` почти молчат (измеренные механизмы)

* **Габарит.** 247 срабатываний на посадке `ugr` (161 на `floor`), ошибка
  дистанции |Δ| — медиана **0.172 м**, p90 0.194 м, максимум 0.196 м; испытаний,
  где детектор нашёл объект ВНЕ окна ±2 м, — **0**. То есть окно не является
  ограничителем, а вся потеря дальности — граница участка оси (`valid_far_m`;
  по записям 56.75…64.25 м, раздел 5).
* **Фон на луч.** Медиана остатка в окне — **0 точек** (25 м; максимум 20 за 180
  испытаний), кластер появляется в **7.2 %** испытаний. Причина — геометрия:
  объект на колее 25…75 м виден ЛУЧАМИ ГРАЗИНГА (низ, elevation −2…−4°), а ячейки
  фона на таких лучах помечены неустойчивыми, и гейт устойчивости (без него
  остаток забит шумом) вырезает объект. Это свойство канала, а не «объекта нет в
  кадре».
* **Контур (свободная ширина).** Объект сужает свободную ширину сильно — медиана
  сужения **2.35 м** на 25 м у сработавших испытаний, — но сужение занимает
  **1 бин** у 122 испытаний из 180, а `WidthTracker` требует `PERSIST_BINS` = 2
  бина подряд. Отсюда «в окне сужено, события нет»: на 25 м ширина сужена в 172
  испытаниях из 180, а сработало 54; 49 из них — при сужении ≥ 2 бинов, 5 — при
  одном бине. Правило рассчитано на помеху длиной ≥ 2 м. Второе: на кадрах блока
  канал даёт **0.946 события/кадр** (297 из 314) — ширина сужена на всех 60 кадрах
  у всех шести записей, событий контура у пяти движущихся 58–60 из 60 (медиана
  сужённых бинов 3…30), а у статичного `doubleT_obstacle` — 11 из 60, из них **0**
  на 14 пустых кадрах записи (все 11 — кадры человека). То есть в поле канал
  шумит тем сильнее, чем сильнее датчик поворачивался между кадрами (это тот же
  эффект, что в разделе 6).
  По этой причине срабатывания контура на 100…150 м — **чисто его шум**:
  P(контур) 5.0 % / 3.3 % / 0 в точности равны FP в том же окне тех же дистанций
  на пустых кадрах (0.050 / 0.033 / 0, раздел 9.3). Считаться обнаружением можно
  только разность с 9.3.
* **Контроль на настоящем объекте.** На 46 кадрах человека в `doubleT_obstacle`
  каналы дают: габарит **46/46**, фон 26/46, контур 11/46, правило 1-из-3 — **46/46**,
  2-из-3 — 34/46. Единственный настоящий объект корпуса цепочка находит на всех
  кадрах, но делают это габарит и (частично) фон — контур срабатывает на 8 кадрах
  из 46.

| `floor` | габарит + фон | 0.851 | 0.851 | 1.00 | 0.788 | 0.788 | 1.00 |
| `floor` | габарит + контур | 0.803 | 0.775 | **1.04** | 0.727 | 0.694 | **1.05** |
| `floor` | фон + контур | 0.911 | 0.911 | 1.00 | 0.881 | 0.881 | 1.00 |
| `floor` | все три | 0.803 | 0.775 | **1.04** | 0.727 | 0.694 | **1.05** |

**Вывод: каналы НЕ независимы, и после канонизации это видно резче.** Там, где
срабатывает габарит, совместных пропусков систематически БОЛЬШЕ, чем даёт
произведение: отношения **1.04–1.06** по всем испытаниям и до **1.09** на
подвыборке, где объект действительно видим (правило «все три», посадка `ugr`).
Прежний прогон давал 1.02–1.04 и 1.06 — направление то же, величина выросла
вместе с ростом P(габарит) (9.2). Пары с фоном без габарита совпадают с
произведением (1.00) — и это ожидаемо: фон молчит почти всегда (9.4), поэтому
произведение по нему повторяет маргинальное значение.

Причина названа и она общая для всех трёх каналов: **один сенсор и одна
геометрия**. Все три канала смотрят одно и то же облако в одном коридоре: если
возвратов объекта на лучах нет (или они не проходят гейт устойчивости фона, как в
9.4), то молчат все три одновременно — и именно это даёт превышение над
произведением. Поэтому цепочку нельзя называть «3-из-3»: заявленное правило может
быть только «1-из-3», а правило «2-из-3» ограничено сверху полнотой второго по
силе канала — у нас это контур, у которого на компактном объекте своё правило
персистентности не срабатывает, а на пустых кадрах 0.946 FP/кадр.

### 9.6 Чего здесь не проверено

* **Дальше 50 м по габариту ничего не измерено:** при `valid_far_m` 56.75…64.25 м
  на 75…150 м в участке оси 0 испытаний из 180. Предел задан данными/моделью оси,
  а не порогами; чтобы его поднять, нужен разбор продления оси (разделы 5–6).
* **FP канала фона почти нулевой (0.00955/кадр), но и P почти нулевой** (7.2 % на
  25 м): «хороший FP» здесь означает «канал не работает», а не «канал точен».
  Оценка одного FP без P обманчива — отсюда обе таблицы рядом.
* **Пороги не подгонялись ни под один канал.** Очевидный следующий шаг
  (сужение гейта устойчивости фона или `PERSIST_BINS` = 1 у контура) здесь НЕ
  делался: это уже тюнинг порогов, и он требует своей проверки на FP.
* **Объект синтетический** (0.30 × 0.30 × 1.00 м); большая помеха (0.5…1 м) даст
  другие числа — площадь силуэта и число бинов сужения растут. Настоящий объект в
  корпусе один (человек, 46 кадров, 9.4).
* **FP/ч по правилам не доказывают нормы** по той же причине, что в разделе 2.3:
  весь корпус — 0.07 ч. Цифры 342 и 3.39·10⁴ FP/ч — это измеренные частоты, а не
  верхние границы.
* **Компенсации рыскания нет**: числа контура в наборе `block` — это цена
  отсутствия компенсации (0.946 FP/кадр), и без неё канал дальнего контура
  остаётся выключенным (раздел 6).
### 9.7 Канонизация позы кадра

**Проблема.** Модель снимка — ось пути в координатах КАДРА (`y_nodes`, `axis_x_m`,
`ugr_z_m`) и колея. Снимок собирается медианой узлов по кадрам записи, а кадры стоят
в РАЗНЫХ позах сенсора относительно пути. Замер по `roundT_doubleT` (лента во всех
кадрах измерена, `node_origin='measured'`, пара из двух нитей):

| кадр | x ленты на 10 м | на 20 м | на 40 м |
|---|---|---|---|
| 0 | −0.52 | −0.26 | **+0.28** |
| 60 | −0.86 | −0.94 | −1.13 |
| 120 | −1.38 | −1.94 | −2.57 |
| 140 | −1.37 | −2.00 | **−3.89** |
| 200 | −1.13 | −1.42 | −2.12 |

В системе кадра лента уезжает на 0.9 м на 10 м и на **4 м на 40 м** — это собственное
движение сенсора (доворот/снос), а не шум геометрии. Медиана по таким кадрам склеивает
вилку, и поиск безопасного участка вынужден укорачивать коридор: на круглых записях
он выходил −45.75 и −52.75 м против −61.75…−68.25 м на прямых. Разброс оси между
кадрами: 0.032 / 0.050 / **1.538** / **1.104** / 0.057 / 0.041 м.

**Решение.** Абсолютная ось кадра измеряется по САМОМУ облаку — по полосам рельсов
(`axis_pose` в `detector/core.py`: сетка по наклону, уточнение МНК, выбор из шести
кандидатов по ТОЧНОМУ счёту полос), и вычитается из облака перед расчётом координат
`u/h`. Снимок и детектор обязаны звать ОДИН вычислитель: в `build_models.median_model`
ось каждого кадра приводится к канонической системе ДО медианы (`_meta.records[*].poses`
— что вычтено, `spread_canon_max_m` — разброс после, `spread_max_m` оставлен «как в
системе кадра»). Иначе каноническая ось снимка и облако расходятся на метры.
`DetectorConfig.canonicalize=True`; `TrackModel.relative()` канонизирует по умолчанию
(поэтому канонизацию нельзя звать на подмножестве точек кадра — только на всём облаке).

**Что дала:**

| запись | участок, м (было → стало) | разброс оси, м (было → стало) |
|---|---|---|
| doubleT_obstacle | −63.75 → −63.75 | 0.032 → 0.035 |
| doubleT_platform | −68.25 → −68.25 | 0.050 → 0.013 |
| **roundT_doubleT** | **−45.75 → −60.75** | **1.538 → 0.169** |
| **roundT_pressureGate_roundT** | **−52.75 → −62.75** | **1.104 → 0.142** |
| roundT_squareT_pressureGate_squareT | −62.75 → −62.75 | 0.057 → 0.058 |
| squareT_platform_squareT_switch | −61.75 → −61.75 | 0.041 → 0.028 |

Ложные не выросли: 2488 кадров, 46 событий, все в `doubleT_obstacle` (человек),
0 на остальных пяти. Человек — 46 из 51 (кадры 13…63), медиана дистанции 56.1 м.

**Честно о первой версии.** В ней на ~20 кадрах стрелочной зоны (запись 6, кадры
780…803) и на круглых (кадры 245…267) поза запрыгивала на ЧУЖУЮ пару линий с той же
колеёй (соседний путь или остряк под ~6° и 0.2…0.45 м в сторону): в облаке там 4+
параллельных линии на высоте головки, широкая полоса давала чужой паре тот же счёт,
а уточнение уводило ось на 0.1…0.25 м от решения сетки. Эти кадры давали ложные на
54…59 м, из-за чего участок укорачивался, а позы кадров разъезжались. Убрано сужением
полосы 0.10 → 0.04 м (замерено: у рельсов счёт 409…475, у чужой пары 30…251), шагом
сетки 0.05 → 0.02 м, физическими рамками (|сдвиг| ≤ 0.30 м, |наклон| ≤ 0.10) и выбором
из шести кандидатов по точному счёту (гистограмма завышает счёт широкой структуре).
После этого траектории кадр-в-кадр гладкие, `squareT_platform` −61.75, `roundT_squareT`
0.058.

**Чего канонизация не делает:** датум УГР не канонизирован (разброс между кадрами
0.003…0.028 м — пренебрежимо); продление оси за измеренный участок по-прежнему берёт
наклон хвоста по разреженной полосе (проверено на окнах 12/20/30 м: ось на −60 м
гуляет на 0.03…0.07 м, ложных не меняет).
