# LiDAR Inspector — семантические зоны (`zones`) — дизайн

Дата: 2026-09-15
Статус: утверждён
Файл реализации: `zones.py` (новый), правка `inspect_bag.py` (только обвязка)

## Проблема

Инспектор (`inspect_bag.py`) уже показывает облако точек контрастно, но туннель
читается как **разрозненная россыпь точек**, а не как объём. Не видно, где пол,
где рельсы, где середина, где потолок: раскраска по Z даёт непрерывную радугу, в
которой уровни не разделены, а контуры (рельсы, кромка балласта, стены) тонут в
шуме точек.

Цель: режим раскраски **`zones`**, который режет сцену на пять семантических
классов и красит каждый **плоским насыщенным цветом**. Тогда туннель читается
как заполненные полосы с различимыми контурами, а не как отдельные точки.
Детекция препятствий — по-прежнему следующая итерация, вне объёма.

## Установленные факты (измерено, не предположения)

Все числа — на `for_hackathon/doubleT_obstacle` (201 кадр, 20.4 с).

Базовое (совпадает с первой спекой):

| параметр | значение |
|---|---|
| топик | `/sensing/lidar/hesai128/pointcloud` (PointCloud2) |
| кадров / длительность | 201 / 20.4 с |
| `point_step` | 26 |
| поля | `x,y,z,intensity` f4 @ 0/4/8/12, `ring` u2 @ 16, `timestamp` f8 @ 18 |
| валидных точек на кадр | 346 808 из 921 600 объявленных |
| габарит кадра | X ∈ [−8.7, 7.1], Y ∈ [−208.7, 3.5], Z ∈ [−7.0, 2.8] |
| направление туннеля | −Y |

### Пол — наклонная плоскость, а не уровень Z = const

Робастная подгонка по нижней огибающей (окно `y ∈ [−60, −2]`, 30 бинов,
перцентиль 4 %):

| величина | значение |
|---|---|
| модель | `z_floor(y) = −1.886 + 0.021585·y` |
| residual rms | 0.104 м |
| residual max | 0.264 м |
| уклон | 2.16 % |

**Следствие:** 2.16 % — это либо спуск пути, либо наклон сенсора на ~1°. Фиксированный
порог по Z для «низа» **неверен**; нижняя полоса обязана считаться относительно
этой плоскости.

### Intensity рельсы НЕ разделяет

| Z-полоса | mean intensity | доля точек с intensity > 25 |
|---|---|---|
| −3.0…+3.0 м (все) | 10–13 | 3–9 % |

Единственная высокоинтенсивная популяция — top 0.5 % (intensity ≥ 205, 1765 точек)
— это **один компактный отражатель** в (x ≈ 5.9, y ≈ 0, z ≈ −0.5), а не рельсы.
**Утверждение `visualize_bag.py` «рельсы = яркая intensity» этим данным не
подтверждается.**

### Рельсы из точек не разрешаются

Верхняя огибающая остатка «высота над полом», бин 5 см по X на 38 м пути, не даёт
двух отдельных гребней. Есть только одна широкая приподнятая полоса шириной
~1.3 м в `x ∈ [0.9, 2.2]` (кандидат — шпальная постель, центр `x ≈ 1.55`).

### Форма балластной призмы

| элемент | диапазон X | высота над плоскостью пола |
|---|---|---|
| левый откос (спуск) | [−2.2, 0.0] | — |
| плоская постель | [0.0, 4.5] | +0.10…+0.25 м |
| правый откос (спуск) | [4.5, 6.2] | — |

### Стены — две доминирующие вертикальные плоскости

| параметр | значение |
|---|---|
| плотные вертикальные структуры | x ≈ −2.7 и x ≈ +6.6 |
| ширина туннеля | ≈ 9.3 м |
| метод | две сильнейшие вершины гистограммы X по точкам **выше постели**, разнесённые > 2 м |

### Потолок неоднороден

`z_max` по Y-полосам падает с 2.24–2.82 м на `y ∈ [−2, −25]` до **1.20 м** на
`y ∈ [−85, −80]`: перекрытие есть только примерно в первых 40 м. Порог потолка
обязан быть регулируемым, глобальным он быть не может.

### Плотность пола низкая из-за скользящего падения луча

45 921 точка уровня пола (`z < −1.4`) на 38 м туннеля.

## Дизайн

### Классы зон

Порядок приоритета: **первое совпадение выигрывает**. Рельс специально стоит
первым, чтобы точка рельса не ушла в постель/середину.

`rail → bed → ceiling → wall → middle`

| класс | правило | плоский цвет (RGB 0..1) |
|---|---|---|
| `rail` | точка лежит на одном из смоделированных рельсов | (1.00, 0.55, 0.00) ярко-оранжевый |
| `bed` (низ) | `z − z_floor(y) < floor_band` (по умолчанию 0.30 м) | (0.35, 0.45, 0.60) серо-голубой |
| `ceiling` (потолок) | `z ≥ ceiling_z` (по умолчанию 2.0 м) | (0.85, 0.30, 0.90) маджента |
| `wall` (стены) | `\|x − x_wall\| < wall_band` (по умолчанию 0.50 м) и выше постели | (0.00, 0.75, 0.70) бирюзовый |
| `middle` (середина) | всё остальное | (0.25, 0.85, 0.35) зелёный |

Пять цветов различимы попарно; ни один класс не должен визуально исчезнуть
(это проверяется, см. Проверку).

### Модель пола

Пол считается не порогом по Z, а плоскостью `z_floor(y) = floor_a + floor_b·y`.
Все «нижние» пороги отсчитываются **от плоскости** — это прямое следствие факта
о наклоне 2.16 %. Коэффициенты по умолчанию `floor_a = −1.886`,
`floor_b = 0.021585`, но их можно менять (и пересчитывать `fit_floor`) — сцена
нерегулярна.

### Детекция стен

`detect_walls` берёт точки **выше постели**, бинит их по X (по умолчанию шаг
0.10 м), ищет две сильнейшие вершины гистограммы, разнесённые не менее чем на
`min_separation` (по умолчанию 2.0 м), и возвращает их X-координаты. Результат
(`x_wall`) прокидывается в `ZoneParams`; классификация считает точку стеновой,
если `|x − x_wall| < wall_band` **и** она выше постели (иначе вся нижняя часть
откосов ушла бы в стены).

### Рельсы — модель по оси пути, а не детекция

Рельсы **намеренно** заданы моделью по оси пути, потому что детекция из точек
доказанно ненадёжна (см. факты: гребней нет, intensity не разделяет). Две
непрерывные линии идут вдоль Y на `x = axis_x ± gauge/2`
(по умолчанию gauge 1520 мм → ±0.76 м) на высоте `z = z_floor(y) + 0.16 м`.

Они рисуются **реальной геометрией** (`open3d.geometry.LineSet`, ярко-оранжевый),
поэтому рельс читается как один непрерывный контур даже там, где точек пола
мало. Дополнительно точки рядом с рельсом классифицируются как `rail`
(полуширина по умолчанию 0.12 м, допустимая полоса высоты относительно
плоскости пола по умолчанию [−0.10, +0.35] м).

`axis_x` по умолчанию берётся из данных (центр приподнятой шпальной постели,
x ≈ 1.6), но выведен слайдером: без аннотации подтвердить его нельзя.

### «Заполненный» вид

- Плоские насыщенные цвета вместо градиента: у класса ровно один цвет,
  поэтому соседние уровни дают резкие границы.
- Размер точки по умолчанию поднят с 3 до **5**, диапазон слайдера расширен до 12.
  Крупнее точка — плотнее заливка полос.

## Интерфейс `zones.py` (контракт)

Модуль: чистый `numpy`; `open3d` — только для линий рельсов.

```python
ZONE_NAMES = ('rail', 'bed', 'ceiling', 'wall', 'middle')   # порядок меток
ZONE_COLORS: dict[str, tuple[float, float, float]]           # таблица цветов выше

@dataclass
class ZoneParams:
    floor_a: float
    floor_b: float
    floor_band: float
    ceiling_z: float
    axis_x: float
    gauge: float
    rail_half_width: float
    rail_low: float
    rail_high: float
    wall_x: tuple          # X найденных стен
    wall_band: float
    detect_walls: bool

floor_profile(y, params)                    # z плоскости пола для скаляра или массива y
fit_floor(xyz, y_min=-60.0, y_max=-2.0, bins=30, percentile=4.0) -> (a, b, rms)
detect_walls(xyz, params, min_separation=2.0, bin_width=0.10) -> list[float]
classify(xyz, params) -> np.ndarray        # uint8-метки, индексируют ZONE_NAMES
zone_colors(xyz, params) -> np.ndarray     # (N, 3) float64 из ZONE_COLORS
classify_counts(xyz, params) -> dict[str, int]
make_rail_lines(params, y_from=-80.0, y_to=0.0, step=1.0) -> open3d.geometry.LineSet
```

Смысл каждого элемента:

| элемент | что делает |
|---|---|
| `ZONE_NAMES` | порядок меток; `classify` возвращает индексы в этот кортеж |
| `ZONE_COLORS` | единственный источник цветов класса (плоские) |
| `ZoneParams` | все пороги; дефолты — измеренные значения выше |
| `floor_profile` | `floor_a + floor_b·y`, скаляр или массив |
| `fit_floor` | робастная подгонка плоскости пола -> `(a, b, rms)` |
| `detect_walls` | X двух доминирующих вертикальных плоскостей |
| `classify` | векторная классификация, `uint8`-метки |
| `zone_colors` | `(N, 3) float64`, индексация `ZONE_COLORS` по меткам |
| `classify_counts` | число точек на класс (для консоли и проверок) |
| `make_rail_lines` | `LineSet` двух рельсов, `z` по профилю пола |

## Управление

`inspect_bag.py` только подключает `zones.py`. В панели появляются:

- новый пункт **`zones`** в селекторе `Color by`;
- слайдеры: `Axis x, m`, `Gauge, mm`, `Floor band, m`, `Ceiling z, m`,
  `Wall band, m`;
- чекбоксы: показ геометрии рельсов и показ стен;
- `Point size` по умолчанию 5, диапазон до 12.

Все пороги регулируемы, потому что сцена нерегулярна; значения по умолчанию —
измеренные числа из «Установленных фактов».

## Производительность

Инспектор сейчас даёт ~8.7 кадра/с (упор в парсинг, не в GPU). Классификация
добавляет **один проход** по точкам. Требование: не сделать воспроизведение
заметно хуже. Поэтому `classify`/`zone_colors` — **один векторизованный проход
numpy без Python-цикла по точкам**; `make_rail_lines` строится один раз и
переиспользуется, а не на каждый кадр. Бюджет добавки — единицы миллисекунд
на 346 808 точек (порядок существующего `colorize`/`astype`).

## Проверка (как доказывается, что работает)

### Юнит-тесты `tests/test_zones.py` (`unittest`, только stdlib)

- `fit_floor` восстанавливает известный синтетический наклон (`a`, `b`, rms).
- `floor_profile` совпадает с `a + b·y` (скаляр и массив).
- По одной синтетической точке на класс — каждая классифицируется верно.
- Точка рельса **побеждает** постель (приоритет `rail` > `bed`).
- Точка чуть выше пола — это `bed`, а не `middle` (порог от плоскости).
- Пять цветов класса попарно различны, и каждый реально выдаётся.
- Сумма `classify_counts` равна N.
- `detect_walls` находит две синтетические вертикальные плоскости с точностью 0.3 м.
- `make_rail_lines` даёт две линии на `axis ± gauge/2`, `z` следует профилю пола.
- Пустой вход -> пустой массив цветов `(0, 3)`.

### Проверка живого окна

- Снять работающее окно в PNG (GDI-захват) и посчитать пиксели, совпадающие с
  каждым из пяти цветов класса. **Все пять обязаны присутствовать** — так
  ловится молчаливое исчезновение класса.
- Консоль печатает число точек по классам — пустой класс видно сразу.
- **Регрессия:** главный вид обязан остаться **≥ 41 %** «зажжённых» пикселей
  (замерено до этой работы). Иначе заливка ухудшила картинку.

## Вне объёма

- Детекция препятствий, боксы, координаты (следующая итерация).
- Правки `visualize_bag.py` — файл не трогается.
- Экспорт/разметка датасета, LAZ/LAS/ROS/Docker.
- Автоматическая аннотация рельсов (модель по оси — сознательный компромисс,
  пока нет разметки).

## Риски

| риск | реакция |
|---|---|
| Дефолт `axis_x ≈ 1.6` не подтверждён аннотацией | слайдер `Axis x, m`; значение меняется в GUI без правки кода |
| Порог `ceiling_z` глобальный, а потолок только в первых ~40 м | слайдер `Ceiling z, m`; при 1.20 м потолок пропадает вдали — это ожидаемо |
| Классификация замедляет кадр | один векторизованный проход numpy; контроль по fps в HUD |
| Один из пяти классов пуст и потому невидим | PNG-проверка на все пять цветов + консольный счёт по классам |
| Крупные точки «съедают» контуры | `Point size` регулируем 5…12; регрессия ≥ 41 % ярких пикселей |
| Стены детектируются неверно на нерегулярной сцене | `detect_walls` можно выключить, `wall_x` задать вручную |
| Захват живого окна даёт чёрное | офскрин-рендер не доказывает перерисовку (урок первой спеки); проверять именно живое окно |

## Приложение: ограничения, которые нельзя нарушать

- Инспектор продолжает работать; `zones` — **дополнительный** режим раскраски,
  не замена. `visualize_bag.py` не трогается.
- Весь текст GUI и вывод в консоль — **ASCII**: в атласе шрифта Open3D нет
  кириллических глифов (`?????`), а консоль Windows искажает не-ASCII (оба
  наблюдались в первой итерации).

## Приложение: исправление после ревью пользователя

Первая реализация рисовала рельсы одной непрерывной модельной линией. Пользователь
возразил по существу: рельсы проходили СКВОЗЬ вертикальные препятствия, а поезд сквозь
них проехать не может. Это не косметика, а признак неверного метода: линия, нарисованная
сквозь препятствие, утверждает "здесь можно ехать".

Что подтвердилось в данных:

- Ось по умолчанию бралась как середина между стенами (`x = 1.95`) -- догадка, разметкой
  не подтверждённая. Пункт спеки "ось из центра приподнятого ложа, x ~ 1.6" тоже был
  неверен: "приподнятое ложе" `x in [0.9 .. 2.2]` оказалось вертикальными конструкциями,
  которые и задрали верхнюю огибающую (поэтому p90 упирался в потолок диапазона).
- Засорённость коридора локальна по Y, а не сплошная. Профиль по замеру: точки выше ложа
  и ниже габарита 3.7 м внутри полосы `|x - 1.95| < 1.06` дают нули везде, кроме узких
  полос `y ~ -16..-17` (8004 точки), `y ~ -34` (3498), `y ~ -9.7` (1734), `y ~ -3` (3431).
  То есть препятствия -- дискретные объекты на пути.
- Средняя вертикальная конструкция занимает `x in [0.9 .. 2.2]` (центр ~1.55), и при оси
  1.95 левый рельс (`x = 1.19`) проходит прямо через неё.

Принятое исправление: физическое ограничение пользователя стало критерием. Добавлены
`corridor_blocked` (засорённость коридора вдоль Y), `blocked_spans` (склейка соседних
бинов в диапазоны) и `BLOCKED_COLOR`; `make_rail_lines(..., blocked=...)` рвёт линии по
узлам Y и красит заблокированные шаги красным. Замерено на `doubleT_obstacle`: блокировано
8.0 м из 45 м -- `[-35.5, -33.5], [-17.5, -14.5], [-5.5, -4.5], [-0.5, 1.5]`.

Проверено на живом окне: красные разрывы дали 769 пикселей против 3753 у оранжевых
рельсов, то есть ровно долю 8/45 длины.

Ещё две вещи, найденные при этой проверке:

- `gui.ScrollableVert` внутри `CollapsableVert` в окне с ручной раскладкой СХЛОПЫВАЕТСЯ:
  панель показывала только заголовок (0.15 % зажжённых пикселей против 34 % на обычном
  `Vert`). Обычный `Vert` возвращён.
- **Filament пересчитывает цвета**: медианное расстояние от отрендеренных пикселей до
  палитры 0.283, гипотеза чистой гаммы 1/2.2 объясняет лишь часть (0.213). Оттенки и
  различимость классов сохраняются, но точного совпадения с заданными значениями нет,
  поэтому приёмочная проверка должна сравнивать по БЛИЖАЙШЕМУ цвету палитры, а не по
  попаданию в допуск.

Ось по-прежнему эвристика (середина между стенами) и по-прежнему правится слайдером;
подтвердить её без разметки нельзя, и это печатается в консоль при старте.
