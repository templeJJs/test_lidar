# LiDAR Inspector — дизайн

Дата: 2026-09-15
Статус: утверждён
Файл реализации: `inspect_bag.py` (новый)

## Проблема

`visualize_bag.py` показывает облако точек из rosbag2 `.db3`, но на
`for_hackathon/doubleT_obstacle` визуально ничего не разобрать: снятое окно даёт
среднюю яркость 0.059 и ~9% «зажжённых» пикселей (и то в основном строка
заголовка). Облако рисуется, но сливается с фоном.

Цель: удобный инспектор туннеля, чтобы глазами находить препятствия. Детектор
поверх инспектора — следующая итерация, вне объёма этой спеки.

## Установленные факты (измерено, не предположения)

Данные `doubleT_obstacle`:

| параметр | значение |
|---|---|
| топик | `/sensing/lidar/hesai128/pointcloud` (PointCloud2) |
| кадров / длительность | 201 / 20.4 с |
| `point_step`, `height`, `width` | 26, 1, 921600 |
| поля | `x,y,z,intensity` f4 @ 0/4/8/12, `ring` u2 @ 16, `timestamp` f8 @ 18 |
| валидных точек на кадр | 346 808 (остальное — нулевой паддинг) |
| габарит | X ∈ [−8.7, 7.1], Y ∈ [−208, 3.5], Z ∈ [−7.0, 2.8] |
| доля точек с \|z\| < 2 м | 90 % |
| intensity | f4, 0…255, медиана 0, mean 15 |

Туннель уходит в **−Y** на ~208 м; лидар стоит ~2–3 м над полом, высота
туннеля ~10 м.

Три подтверждённые причины плохой картинки:

1. **Цвета почти равны фону.** Фон `(0.01, 0.01, 0.03)`, а 74 % точек получают
   цвет ≈0.05–0.2. Порог «рельсов» `intensity > 20` не проходит большинство, т.к.
   медиана intensity = 0.
2. **Прореживание не работает.** Цикл анимации присваивает точки напрямую, минуя
   `prepare()`, поэтому `--max-points` игнорируется.
3. **Кадрирование не подходит.** `lookat [0,−30,0]` / `front [0,1,0]` /
   `zoom 0.015` для коридора 208 × 16 м.

Корневая причина тормозов (замерено на 346 808 точках):

| операция | время |
|---|---|
| чтение из SQLite + парсинг CDR | ~70 мс |
| `colorize_rails` | ~25 мс |
| `Vector3dVector(colors)` (float64) | 1.2 мс |
| `Vector3dVector(xyz)` — **float32 как есть** | **205 мс** |
| `astype(np.float64)` (1.6 мс) + `Vector3dVector` | **1.8 мс** |

`o3d.utility.Vector3dVector` ожидает `float64`; при подаче `float32` pybind
конвертирует поэлементно. В Open3D 0.19 `Vector3fVector` отсутствует.

**Следствие: утверждение в `README.md`, что `update_geometry` стоит ~0.7 мкс на
точку и поэтому нужно резать до 60k точек, неверно.** Один `astype(np.float64)`
убирает 200 мс на кадр (в 112 раз). Все 346 808 точек рисуются на 10 Гц без
прореживания.

Доступность API в pip-сборке Open3D 0.19 (проверено интроспекцией):
`gui.Application`, `gui.Window.set_on_tick_event`, `gui.SceneWidget`
(`scene`, `look_at`, `setup_camera`, `set_view_controls`, `background_color`),
`gui.{Button,Vert,Horiz,CollapsableVert,Combobox,Slider,Checkbox,Label}`,
`rendering.{Open3DScene,MaterialRecord}`, `gui.Widget.background_color`.
Отсутствует: `O3DVisualizer.add_combobox`, `rendering.Material`,
`utility.Vector3fVector`.

## Архитектура

`inspect_bag.py` — самодостаточный файл. Не импортирует `visualize_bag.py`:
тот файл параллельно правит другой агент, зависимость сделала бы инспектор
хрупким. Дублирование парсера (~70 строк) принято сознательно.

Модули (в одном файле, но с чёткими границами):

- `parse_pointcloud2_cdr(data) -> (xyz f4 (N,3), intensity f4 (N,) | None)` —
  переносится из `visualize_bag.py` без изменений (парсер корректен).
  Единственная правка вызывающей стороны: `astype(np.float64)` перед `Vector3dVector`.
- `BagFrames` — доступ к кадрам `.db3` по индексу, кольцевой кэш на 32 кадра.
  Фоновый поток предзагрузки идёт вперёд от текущего индекса со **своим**
  соединением SQLite (объекты `sqlite3.Connection` не потокобезопасны).
- `frame_colors(xyz, intensity, mode, opts) -> float64 (N,3)` — раскраски.
- `make_grid(...)`, `make_axes(...)` — оверлеи (`LineSet`).
- `Viewport` — обёртка над одним `gui.SceneWidget`: камера-пресет, обновление
  геометрии, HUD.
- `Inspector` — окно, панель управления, 4 `Viewport`, транспорт, тик-цикл.
- `main()` — разбор аргументов, запуск.

Поток данных на кадр:

```
BagFrames[idx]  →  обрезка по дальности  →  frame_colors()  →  astype(float64)
                →  PointCloud  →  scene.remove_geometry + add_geometry  (×4 вида)
```

## Виды (дашборд 2×2)

| вид | eye | lookat | up | назначение |
|---|---|---|---|---|
| От лидара | (0, 2, 1.5) | (0, −30, 0) | +Z | как видит сенсор |
| Сверху (BEV) | (2, −30, 80) | (2, −30, 0) | −Y | главный вид: что влезает в коридор |
| Сбоку | (60, −30, 0) | (2, −30, 0) | +Z | продольный разрез, высота препятствий |
| Изометрия | (40, 40, 30) | (2, −30, 0) | +Z | общий план |

Пресеты камеры (кнопки) применяются к виду «От лидара»; остальные три вида
сохраняют свои раскладки:

| пресет | eye | lookat | up |
|---|---|---|---|
| лидар | (0, 2, 1.5) | (0, −30, 0) | +Z |
| сверху | (2, −30, 80) | (2, −30, 0) | −Y |
| сбоку | (60, −30, 0) | (2, −30, 0) | +Z |
| изо | (40, 40, 30) | (2, −30, 0) | +Z |
| сзади | (2, 12, 4) | (2, −40, 0) | +Z |
| Fit | — | центр габарита | +Z |

Каждый вид независимо вращается мышью:
`set_view_controls(gui.SceneWidget.Controls.ROTATE_CAMERA)`. FOV 60°.
Кнопка **Fit** перекадрирует все виды по габариту текущего (обрезанного) облака
через `setup_camera`.

Все четыре вида показывают один и тот же кадр и обновляются вместе.

## Раскраски

Combobox, диапазон значений 0.2–1.0 (не 0.05–0.2). Палитра — таблица якорных
цветов + `np.interp` по каналам (без новых зависимостей):

- **Высота** (по умолчанию) — по Z, диапазон [−7, 3], ноль на полу.
- **Интенсивность** — нормализация по перцентилям 1…99 (а не по max: max = 255
  при медиане 0 «съедает» большинство точек).
- **Дальность** — евклидово расстояние от сенсора, диапазон 0…`max_dist`.
- **По кольцу** — дискретная палитра на 128 лучей, видна геометрия сканера.

## Оверлеи

- Сетка на Z = 0: шаг 5 м, до 200 м вперёд, ±40 м по X. `LineSet`.
  Z = 0 — это плоскость самого лидара, пол туннеля лежит ниже. Уровень пола
  измеряется в первой задаче реализации (мода Z по облаку) и выводится в лог;
  плоскость сетки — параметр, по умолчанию Z = 0.
- Оси X/Y/Z в начале координат (красный/зелёный/синий).
- HUD: в левом верхнем углу каждого вида — имя вида; общий HUD — кадр/всего,
  время bag (с), дальность вперёд (м), время кадра (мс) и сглаженный fps.
- Сетка, оси и HUD отключаются чекбоксами.

## Панель управления

Слева, `CollapsableVert`, сворачивается по Tab.

- 6 кнопок пресетов камеры: лидар / сверху / сбоку / изо / сзади / Fit.
- Транспорт: ▶/⏸, шаг ±1 кадр, ±10 кадров, слайдер кадра.
- Скорость: слайдер 1…30 Гц, чекбокс «реальное время» (темп по таймстемпам bag).
- Раскраска: Combobox.
- Размер точки: слайдер 1…6 (`MaterialRecord.point_size`).
- Чекбоксы: сетка / оси / HUD.
- Слайдер «обрезать дальше N м»: 10…200, по умолчанию 80. Без него коридор в
  208 м делает всё микроскопическим.

Прозрачность панели: сначала пробуем `panel.background_color` с альфой < 1.
Если pip-сборка альфу игнорирует — панель остаётся узкой и сворачивается по Tab.
Решение принимается по факту (см. Проверку), а не по предположению.

## Производительность

- Кэш распарсенных кадров: кольцевой, 32 кадра.
- Фоновый поток предзагрузки вперёд; шаг ±1 и пауза мгновенны.
- Бюджет кадра: ≤100 мс (парсинг 70 + раскраска 25 + аплоад 4), целевые 10 Гц.
- Тик-цикл `window.set_on_tick_event`; перерисовка только при необходимости
  (`window.post_redraw()`), не постоянный spin.
- Если замер покажет, что 4 вида × 346k точек не тянут: авто-прореживание до
  ~150k точек на вид с индикацией в HUD и слайдером «полнота». **Включается
  только по результату замера.**

## Проверка (как доказывается, что работает)

1. Замер: время кадра и fps выводятся в HUD; приёмка — **≥8 Гц** на всех
   346 808 точках без прореживания.
2. Визуально: окно снимается в ASCII-арт (инструмент `ascii_window.py`,
   GDI `PrintWindow` + `BitBlt`, luminance-статистика). Приёмка — облако яркое и
   занимает кадр, а не ~9 % пикселей как в текущем `visualize_bag.py`.
3. Ни один из 4 видов не пуст: для каждого считается доля «зажжённых»
   пикселей в его прямоугольнике.
4. Все 6 пресетов камеры и все 4 раскраски отрабатывают без исключений.
5. Парсер: количество валидных точек и габарит сверяются с таблицей фактов
   выше (346 808; X ∈ [−8.7, 7.1]; Y до −208).

Вспомогательные скрипты проверки живут в

| риск | реакция |
|---|---|
| 4 вида × 346k не тянут по GPU | авто-прореживание до 150k + индикация; включается по замеру |

## Приложение: фактические находки реализации

Записано после реализации, чтобы не повторять ошибок. Три допущения спеки
оказались неверными.

1. **Прореживание не понадобилось.** Замер: 4 вида × 345 063 точки, аплоад
   18.8 мс суммарно (≈4.7 мс на вид), 20.4 fps на чистом рендере. Причина —
   `astype(np.float64)`: без него 205 мс, с ним 1.8 мс. Итоговый fps 8.7
   ограничен парсингом, а не GPU. Формулировка риска «не тянут по GPU» была
   неверной.

2. **Альфа панели не проверяется захватом.** Спека предполагала проверку
   фактом. Оказалось, что `gui.Application.render_to_image(scene, w, h)`
   рендерит `Open3DScene`, то есть 3D-слой без виджетов, а оконного захвата в
   API нет. Панель сделана непрозрачной и сворачиваемой по `Tab`; альфа
   выставлена best-effort.

3. **GDI-захват окна работает** — вопреки промежуточному выводу. Первые захваты
   давали чёрное, и это было принято за ограничение DWM/GPU. На деле окно
   **действительно было чёрным**: колбэк `set_on_tick_event` возвращал `False`,
   а его контракт — «True, если нужна перерисовка». Геометрия обновлялась, окно
   не перерисовывалось. `render_to_image` рендерит по требованию, поэтому
   офскрин-снимки были яркими, а живое окно — чёрным. Это и увидел
   пользователь. **Урок: офскрин-рендер не доказывает, что видимое окно
   перерисовывается.**

Плюс две вещи, которых спека не предусмотрела:

- `gui.Window.set_on_key` требует колбэк, возвращающий **bool**;
  `EventCallbackResult` допустим только у `gui.SceneWidget.set_on_key`.
  Возврат `EventCallbackResult` роняет приложение на первом нажатии
  (`Unable to cast ... to C++ type`).
- Атлас шрифта Open3D собирается по Latin-глифам, кириллица не рендерится
  (подписи выводились как `?????`). Текст интерфейса и консольный вывод
  переведены на ASCII; заодно убран принудительный UTF-8 для stdout, который
  давал мусор в консоли Windows.

Ещё одна отвергнутая гипотеза, зафиксированная замером: перенос обрезки и
раскраски в поток предзагрузки (`BagFrames.set_prepare`) выигрыша не дал —
hit rate упал с 27 % до 5-9 %, fps не изменился. Генератор кадров упирается в
GIL, а не в главный поток; увеличение окна предзагрузки до 24 ухудшило
результат. Хук откачен.
