# Симулятор туннеля и лидарных данных — дизайн

Дата: 2026-09-15. Область: новый пакет `sim/` (Python 3.12), выход — rosbag2 `.db3`
того же формата, что наши записи, плюс манифест со сценами и разметкой.
Эталон для сверки — `for_hackathon/doubleT_obstacle` (и остальные 5 записей).

## Зачем

В наших данных нет препятствий: на 6 записей единичные объекты, и они не размечены.
Обучать и проверять детектор на таком материале нельзя — нужен генератор сцен с
**точной эталонной разметкой** и с той же физикой сенсора, что у нас.

## Установленные факты (замерено на эталоне)

Сенсор (вытащено из bag'а, не из даташита):

| параметр | значение |
|---|---|
| колец | 128 (все присутствуют) |
| угол места | кольцо 0 → +14.40°, 64 → −3.02°, 127 → −25.12° (FOV ≈ 39.5°) |
| шаг по вертикали | медиана 0.168°, но неравномерный: 0.086…0.893° |
| точек на кольцо | медиана 2787 (1386…3894) |
| азимутальных колонок на кадр | ≈ 2709 (= 346 808 / 128) |
| дальность | медиана 6.9 м, 95 % — 28.2 м, максимум 208.7 м |
| интенсивность | медиана 11, 90 % — 26, максимум 255, доля > 25 — 10.9 % |
| кадр / запись | 346 808 точек, 201 кадр, 10 Гц, 20.4 с |

Сцена: стены в системе лидара на `x = −2.62` и `+6.62` (≈9.2 м, два пути),
пол — плоскость `z = −2.1208 + 0.017916·y` (уклон 1.79 %), полосы рельсов на
`x ≈ −0.5` (левая нить) и `≈ 2.9…4.8` (правая), сенсор в `x = 0` — то есть над
левой нитью. **Запись статична:** стены и распределение по Y не меняются от кадра
к кадру, значит движение в MVP не нужно.

Формат: тема `/sensing/lidar/hesai128/pointcloud`, тип `sensor_msgs/msg/PointCloud2`,
CDR little-endian, `point_step = 26`, поля `x,y,z` float32 @ 0/4/8, `intensity`
float32 @ 12, `ring` uint16 @ 16, `timestamp` float64 @ 18.

## Разные записи (проверено на всех шести)

Прогон тех же замеров по всем bag'ам в `for_hackathon/` — картина распалась на две
группы, и симулятор обязан уметь обе:

| запись | точек/кадр | колонок | ширина туннеля | пол `a` | уклон | доля `I>25` |
|---|---|---|---|---|---|---|
| `doubleT_obstacle` | 346 787 | 2709 | **9.2 м** (два пути) | −1.82 | 2.34 % | 10.7 % |
| `doubleT_platform` | 171 218 | 1337 | узкий (≈4 м) | −1.33 | 0.51 % | 9.5 % |
| `roundT_doubleT` | 189 670 | 1481 | узкий | −1.32 | 0.60 % | 2.0 % |
| `roundT_pressureGate_roundT` | 189 658 | 1481 | 4.3…5.0 м | −1.32 | 0.77 % | 3.2 % |
| `roundT_squareT_pressureGate_squareT` | 185 535 | 1449 | ≈4.3 м | −1.32 | 0.72 % | 0.8 % |
| `squareT_platform_squareT_switch` | 177 548 | 1387 | ≈4.3 м | −1.31 | 1.47 % | 4.4 % |

Выводы, которые меняют конструкцию:

1. **Сенсор общий:** во всех шести 128 колец, те же `+14.40°`/`−25.12°`, тот же
   медианный шаг `0.168°`. Модель сенсора одна.
2. **Разрешение по азимуту — параметр:** 2709 колонок на кадр у `doubleT_obstacle`
   против ~1400 у остальных (то есть 347 тыс. точек против 180 тыс. при тех же 10 Гц).
   В `SensorModel` число колонок задаётся, проверяем оба режима.
3. **Две семьи сцен:** широкий двухпутный туннель 9.2 м и узкий однопутный 4.3–5 м.
   Генератор должен уметь обе, иначе синтетика покроет только одну реальность.
4. **Сенсор висит на 1.3–1.8 м над полом**, уклон 0.5–2.3 % — это параметры сцены,
   а не константы.
5. **Интенсивность нельзя калибровать по одной записи** (доля `>25` от 0.8 % до 10.7 %):
   модель подбирается так, чтобы давать весь этот диапазон в зависимости от
   отражательных свойств сцены и объектов.

## Что на выходе

1. `bag/sim_<scene>_<seed>/sim_<scene>_<seed>_0.db3` — запись того же формата;
2. `manifest.json` — сцена, сенсор, объекты с разметкой, список кадров, зерно;
3. `frames/frame_%04d.npz` — поточечные метки (0 = сцена, k = объект k) для
   обучения сегментации; опционально, включается флагом.

## Архитектура

```
sim/
  sensor.py     SensorModel: таблица углов места, азимуты, шум, интенсивность;
                from_bag(path) -- вытащить модель из настоящей записи;
                save/load -- артефакт sensor_hesai128.json
  scene.py      SceneParams (dataclass) + build_scene() -> Scene
                Scene: mesh (o3d.t.geometry.TriangleMesh), tracks, sensor_pose, objects
  objects.py    библиотека объектов: меш + материал (отражательная способность) +
                правила размещения (на рельсе / в колее / у стены / в габарите)
  scanner.py    scan(scene, sensor, frame_idx) -> Frame(xyz, intensity, ring, timestamp)
                трассировка лучей через o3d.t.geometry.RaycastingScene
  writer.py     write_bag(frames, manifest, out_dir): CDR-энкодер PointCloud2 + .db3
  cli.py        генерация датасета: --scene, --bags, --frames, --seed, --out
  check_sim.py  метрики «сим похож на реал» против эталонной записи

```

## Сенсор

Модель строится из записи (таблица углов места по кольцам, число азимутальных
колонок, распределения дальности и интенсивности, оценка шума) и **не берётся из
даташита**: у нас сенсор конкретный, и воспроизводить надо его.

Интенсивность: модель `I = f(отражательная способность, угол падения, дальность)`,
параметры подбираются так, чтобы синтетические распределения совпали с эталонными
(медиана 11, p90 26, доля >25 ≈ 10.9 %). Абсолютные значения важны: в разборе
данных мы уже опирались на порог `intensity > 25` как на признак. Калибровать
надо по нескольким записям: доля точек выше 25 в них гуляет от 0.8 % до 10.7 %,
по одной записи модель получится «под неё».

Шум: дальность — гауссов шум по замеру остатка плоскости пола; случайные пропуски
возврата (процент оценивается по «дырам» в эталонных кадрах).

## Сцена

Параметрическая: сечение (прямоугольное / круглое), уклон, **кривые и стрелки**
(без них детектор переобучится на идеальную геометрию и развалится на реальной),
один или два пути, балласт, рельсы R65 и шпалы — **по профилям ГОСТ из
`track_geometry.py`** (не дублировать их, а импортировать), лотки, контактный
рельс, платформа, ворота.

Все случайные величины — с зерном, сцена воспроизводима побайтово при том же
зерне и той же версии кода (зерно пишется в манифест).

## Объекты и разметка

MVP: два класса — **человек** и **чемодан/мешок**; дальше тележка, ящик, обломок,
инструмент. Каждый объект — параметрический меш (примитивы) со скалярной
отражательной способностью, чтобы интенсивность была осмысленной.

Правила размещения: на рельсе, в колее, у стены, внутри габарита / снаружи.
Для каждого объекта в манифесте: класс, 3D-бокс, положение вдоль пути, смещение
от оси, «в габарите или нет», номера кадров, где он виден (по окклюзии).

Поточечные метки (`.npz`) — для обучения сегментации и для честной оценки
«сколько точек объекта реально достигло сенсора».

## Сканирование

Луч на каждую пару (кольцо, азимут): 128 × 2709 ≈ 347 тыс. лучей на кадр.
Трассировка — `o3d.t.geometry.RaycastingScene` (уже установлен): окклюзия
считается честно, объекты за препятствием в облако не попадают.

Порядок точек в кадре и разбивка по кольцам — как в эталоне (кольцо 0 сверху),
`ring` = индекс кольца, `timestamp` = момент кадра + порядковый сдвиг по азимуту.

Производительность: цель — **не дольше 5 минут на запись из 201 кадра**.
Если не укладывается — уменьшаем число колонок на кадр (с оговоркой в манифесте)
или распараллеливаем по кадрам.

## Запись

`writer.py` собирает CDR ровно так, как его читает `bag_reader.parse_pointcloud2_cdr`,
и пишет SQLite со схемой rosbag2: таблицы `topics(id, name, type)` и
`messages(id, topic_id, timestamp, data)`, таймстемпы — наносекунды по возрастанию и **от фиксированного времени начала**
(оно задаётся в параметрах сцены, а не берётся из системных часов — иначе
критерий «побайтово одинаковый .db3» недостижим).
Совместимость проверяется round-trip-тестом: записали → прочитали нашим
`bag_reader` → значения, кольца и интенсивность совпали.

## Проверка (критерии приёмки)

1. **Round-trip формата:** наш `bag_reader` читает синтетическую запись, поля и
   типы совпадают; число точек, кольца, интенсивность — те, что подавали.
2. **Наш конвейер работает на синтетике без правок:** `web_viewer.py` поднимается
   на синтетическом bag'е, зоны находят пол и стены в ожидаемых местах (допуск 0.1 м),
   коридор считается, клиент рисует.
3. **Sim-vs-real метрики** (по 30 кадров **двух эталонов — по одному из каждой
   семьи**: `doubleT_obstacle` и, например, `roundT_doubleT`): число точек на кадр,
   гистограмма по кольцам, таблица углов места, покрытие азимута, распределение
   интенсивности (медиана и p90 в пределах ±20 %), положение пола (±0.05 м),
   положение стен (±0.1 м), доля точек в полосе рельсов.
4. **Семантика:** объект, поставленный на известном `y`, детектируется **ровно
   на этом участке** (precision/recall считает `score.py`); объект, поставленный
   вне габарита, не даёт ложного срабатывания.
5. **Воспроизводимость:** два запуска с одним зерном дают побайтово одинаковый `.db3`.
6. **Производительность:** ≤5 минут на запись из 201 кадра (замер фиксируется в отчёте).

## Фазы

1. **MVP:** сенсор из данных (**оба режима колонок** — 2709 и ~1400) +
   прямолинейный туннель **в двух сечениях: широкий двухпутный 9.2 м и узкий
   однопутный ≈4.3 м**, рельсы/шпалы/балласт по ГОСТ-профилям, два класса
   объектов, запись + манифест, проверки 1–3.
2. Кривые и стрелки (та самая геометрия, которой не хватает в реальности).
3. Платформа и напорные ворота.
4. Остальные классы объектов, движение сенсора (позже, если понадобится).
5. `score.py`: скорборд детектора, интеграция в проверки.

## Риски

| риск | что делаем |
|---|---|
| интенсивность не совпадёт с реальной (медиана 11 — низкая) | калибруем распределение, а не абсолют; доля >25 проверяется отдельно |
| неравномерный шаг по вертикали (0.086…0.893°) сгладим | таблица углов берётся из данных, не усредняется |
| «стерильные» меши дают идеальные поверхности | добавляем шум по нормали и пропуски возврата |
| трассировка не укладывается в 5 минут | сокращаем колонки или параллелим кадры |
| сцена без кривых → детектор переобучен на прямые | фаза 2 обязательна до обучения |
| генератор разойдётся с эталоном по формату | round-trip-тест в приёмке (критерий 1) |

## Вне объёма

- совместимость с `ros2 bag play` (пишем файл, который читаем своим кодом;
  проверка в ROS — отдельная задача);
- физика движения и динамика: запись статична, движение сенсора — необязательное
  расширение (фаза 4), а не часть MVP;
- текстуры и материалы кроме скалярной отражательной способности;
- обучение моделей детектирования — только генерация данных и скорборд.
