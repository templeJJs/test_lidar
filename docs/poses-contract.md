# Контракт запечённых поз (`assets/_poses/**`)

Дата: 2026-09-23. Кто владеет: линия `tools/**` + `assets/_poses/**` (данные не в git:
`assets/*` в `.gitignore`, исключены только `LICENSES.md` и `manifest.json`).
Кому нужно: тому, кто подключает движение объектов и анимации людей в сцене.

Сейчас в `labeling.py` (`POSE_POSE_ROTATION`, комментарий «честный минимум — жёсткий наклон»)
поза объекта — это поворот примитива. Настоящие позы уже запечены и лежат рядом; это
описание того, как их подключить, не трогая чужую линию.

## Что лежит на диске

```

assets/_poses/<asset>/<clip>/frames.npz     # весь клип одним файлом (предпочтительно)
assets/_poses/<asset>/<clip>/clip.json      # метаданные клипа
```

Сводка (27 клипов, 455 моментов):

|---|---|---|---|---|---|
| `rigged_animated_humanoid` | 18 | 296 | FBX (three FBXLoader) | 2688 / 896 | ×0.008716 |

## Ключевые правила

1. **Вершины уже в метрах.** Запекание шло с `--scale <calibrated_scale_to_meters>`.
   В пофайловом `.json` лежит `scale_applied` — это уже применённый множитель,
   **второй раз умножать нельзя**. Рост стоящего человека в данных 1.7492…1.7504 м.
2. **Оси.** Меш Y-up (как в исходном glTF/FBX), кадр — Z-up:
   `(x, y, z)_mesh -> (x, -z, y)_frame`. Начало координат в стойке — под ногами.
3. **Формат тот же, что уже умеет вьюер.** `{"vertices": [[x,y,z]...], "faces": [[i,j,k]...]}`
   (`web/track3d.js`, `meshFromArrays`; `objects/to_viewer.py`, докстрока). Никакого GLB и
   загрузчиков в браузере не нужно: см. раздел «Почему не GLB» ниже.
4. **`frames.npz` предпочтительнее** пофайловых моментов: один клип = один файл,
   `vertices (T,N,3) float32`, `faces (M,3) int32`, `times (T,) float32`.

## Проигрывание

```python
# выбрать клип по классу разметки
spec = manifest['class_map'][cls]                    # {'asset':..., 'clip':..., 'samples':...}
assets = {a['id']: a for a in manifest['assets']}
clip = next(c for c in assets[spec['asset']]['clips'] if c['name'] == spec['clip'])
z = numpy.load(Path('assets/_poses') / clip['bundle_npz'])
V, F, T = z['vertices'], z['faces'], z['times']     # (T,N,3), (M,3), (T,)
d = clip['duration_s']

# индекс момента по времени (loop -> [0,d) без дубля кадра; нецикл -> [0,d])
frac = (t % d) / d if clip['loop'] else min(max(t / d, 0.0), 1.0)
i = min(int(frac * T), T - 1) if clip['loop'] else int(round(frac * (T - 1)))
V0, V1 = V[i], V[min(i + 1, T - 1)]
w = 0.0 if clip['loop'] else frac * (T - 1) - i   # линейная интерполяция между моментами
mesh = V0 * (1 - w) + V1 * w                      # далее: (x,-z,y) + сдвиг на место объекта
```

* Шаг между моментами 26–55 мс у коротких клипов и 250–830 мс у длинных; максимальное
  смещение вершины за шаг — `vertex_move_between_samples_m` (у ходьбы 0.151 m, у бега
  0.220 m, у стояния 0.011 m). Это и есть ошибка линейной интерполяции: линейная
  интерполяция здесь достаточна, интерполяция по костям (AnimationMixer) дала бы
  меньше, но требует GLB-загрузчика, которого в клиенте нет.
* У циклических клипов расхождение конца и начала `loop_wrap_pop_m` (для всех клипов
  `rigged_animated_humanoid` оно ровно 0.0000 m, у `Human Armature|Walk` 0.1440 m):
  если `loop_needs_crossfade = true`, склейку конца с началом надо смешивать за один шаг.

Классов без подходящего клипа **два**, и это честно:

* **`lying`** — отдельного клипа «лежит» нет ни в одном ассете. Ближайшее — последний
  кадр `Death` (0.374 m). Альтернатива из человеческого ассета — `Armature|SwimMove`
  (единственный клип-человек с горизонтальным телом: высота 0.703…0.837 m, длина
  2.141…2.219 m), но это плавание: руки и ноги гребут.
* **`fallen`** — отдельного клипа «упал» тоже нет; берутся моменты падения из `Death`.
  Клипы `Crouch*` на роль «лежит/упал» не годятся: их высота 1.3831 m — это присед.

Про `bbox_height_hint` в `class_map.unknown`: высота bbox объекта из разметки позволяет
угадать класс без клипа (`≥1.55 m` — стоя/идёт, `1.30…1.55` — присед, `<0.70` — лежит).

## Что решить интегратору: как поза доедет до браузера

Замерено на этой машине:

* один кадр позы в формате вьюера (`{"vertices": ..., "faces": ...}`) — **76.4 KiB JSON**
  на объект (2688 вершин, 896 треугольников). Это тот же порядок, что уже ходит по
  `/track`: `web/models/doubleT_platform_100.json` — 565 832 B того же формата.
* `frames.npz` одного клипа — 70…350 KiB (2.0 MiB на все 18 клипов humanoid),
  пофайловые моменты — 13.0 MiB.

Отсюда два варианта, и выбор — за линией фронтенда (эти файлы я не трогаю):

1. **Сервер отдаёт меш кадра** (как `/track` сейчас): +76 KiB на человека на кадр.
   Для 1–3 объектов на кадр это в пределах того, что уже шлётся; для 20 человек —
   1.5 MiB/кадр, уже много.
2. **Клиент берёт клип один раз и интерполирует сам**: 18 моментов ходьбы = 1.37 MiB
   JSON, дальше по кадру едет только `(клип, время)` — единицы байт. Тогда нужен либо
   разбор `.npz` в браузере (это zip: `DecompressionStream('deflate')` есть в современных
   браузерах, но нужен код), либо отдельный маршрут, отдающий `Float32Array` моментов
   (например `vertices` одним бинарём в порядке T×N×3 + список индексов, как в `frames.npz`).

Практичный компромисс: пока людей на кадре мало — вариант 1 (правок в клиенте ноль,
он уже умеет `meshFromArrays`), а кэш по ключу `(клип, индекс момента)` не даст гонять
одни и те же позы повторно: у ходьбы всего 18 различных поз.

## Почему не GLB + `THREE.AnimationMixer`

Ответ: **запечённые вершины**. Причины, каждая проверяема в файлах:

1. **В браузерном бандле нет `GLTFLoader`.** `web/index.html:165-167` — import-map
   объявляет только `three` (`./three.module.min.js`); `GLTFLoader` как модуль не
   подключён (`grep -c GLTFLoader web/three.module.min.js` → `0`; в `app/client`
   (React-клиент) `GLTFLoader` тоже не встречается). `AnimationMixer` в ядре three
   есть — можно было бы, но клип неоткуда загрузить.
2. **Сервер не раздаёт файлы ассетов.** `web_viewer.py:1897` маршрут `/assets/*` —
   это НЕ `assets/` репозитория, а собранный React-клиент: `web_viewer.py:1849-1857`
   (`_client`, корень `app/client/dist`). Маршрута для `assets/**` или `web/models/**`
   нет; геометрия приходит только через JSON-API (`/track`, `/objects`).
3. **У вьюера ровно один формат меша.** `objects/to_viewer.py:1-5`: «Вьюер умеет ровно
   ОДИН формат меша: JSON `{"vertices": ..., "faces": ...}`»; потребитель —
   `web/track3d.js:152`, `meshFromArrays`. Запечённые вершины ложатся в него без правок
   на стороне клиента.
4. **Одни и те же данные нужны лидару.** Синтетика лидара трассирует лучи по мешу
   (см. `tools/README.md`, `o3d.t.geometry.RaycastingScene`) — ей нужны вершины, а не
   рендер. Запечённый меш закрывает оба потребителя, GLB — только браузер, и заставил бы
   править `web/index.html`, `web/app.js` и `web_viewer.py` (чужая линия, сейчас в работе).

Оговорка: GLB+AnimationMixer даёт более гладкую интерполяцию (по костям, а не по вершинам)
и меньше данных по сети. Если когда-нибудь появятся раздача ассетов и `GLTFLoader`,
переключение возможно — но это отдельное решение и правки в чужой линии.

## Проверка

```bash
PYTHONIOENCODING=utf-8 $PY tools/check_poses.py --independent
```

Проверяет: `.npz` читается numpy, форматы совпадают с манифестом, лица у моментов
одинаковые, вершины между моментами меняются, `frames.npz` не расходится с пофайловыми,
габариты классов попадают в ожидаемые (стоя 1.6…1.9 m, лежа 0.3…0.5 m), а перепечённый
в свежем процессе момент совпадает с сохранённым (расхождение — только шум float32,
измерено 5.3e-7 m).
