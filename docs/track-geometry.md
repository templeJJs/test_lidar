# Геометрия пути: что строится, чем проверяется, где грабли

Дата: 2026-09-17. Файлы: `track_geometry.py` (модуль), `check_track_geometry.py`
(численная проверка, GUI не нужен). Данные: `for_hackathon/` — 6 записей, ~2500 кадров.
Python **только 3.12** (в 3.13 нет open3d), скрипты запускать с `PYTHONIOENCODING=utf-8`
(иначе проверка падает на печати `Δ` в cp1251).

## 1. Что отдаёт `build_track(db, frame)`

JSON маршрута `/track?bag=<запись>&frame=<кадр>` (кэш по паре bag+frame):

| ключ | что это |
|---|---|
| `rails[left\|right]` | `head` (верх, ширина, внутренняя грань), `mesh` (ТЕЛО Р65: головка, шейка, подошва, подуклонка), `mesh_measured` (только измеренная площадка), `nodes` |
| `nodes` | `[[y, x_оси, z_верха], ...]` — ось нити для маски точек, шаг 0.5 м |
| `node_origin` | происхождение каждого узла: `measured` / `sparse` / `walls` / `tangent` / **`predicted`** (дальний участок, дорисованный по измеренной кривизне и уклону: колея и форма постоянны, высота по линии измеренного пола) |
| `floor_mesh` | пол как ПРОФИЛЬ (полки, стенки, дно лотка) по облаку, экструзия вдоль оси пути |
| `meta.rail_mesh` | `polyline`, `tunnel_axis`, `axis_smooth`, `floor_profile`, `link`, `reach`, метрики, пояснения |
| `meta.gauge_*` | колея: по внутренним граням и «ось-ось», с указанием источник (измерена / зажата) |

Главное прочтение: узлы — единственный вход для потребителей (маска точек во вьюере,
клиентская перекласка, разрезы). Меш — для показа формы. Колея — ЖЁСТКАЯ ПАРА на кадр:
центр по среднему обеих нитей, нити = центр ± G/2, поэтому колея постоянна и внутри
данных, и в продолжении.

## 2. Чем проверяется (норма приёмки)

```
PYTHONIOENCODING=utf-8 <py3.12> check_track_geometry.py          # ~10 мин, 12 кадров
PYTHONIOENCODING=utf-8 <py3.12> check_gauge.py                   # колея отдельно
py -3.12 -m unittest tests.test_core tests.test_detector_core tests.test_detector_person \
    tests.test_validation tests.test_zones -q                    # 168 тестов
```

Ключевые метрики раздела «СВЯЗЬ РЕШЕНИЙ ПО КАДРАМ» (кадры считаются ПОДРЯД, как в вьюере):

- `dlen_m` — изменение длины ленты за кадр (машина едет ~1.2 м/кадр);
- `shift_m` — боковой сдвиг оси СО СНЯТЫМ ДОВОРОТОМ (доворот берётся по измеренным
  линиям нитей, не по `axis.s` — см. грабли 7);
- `dev_m` / `dev_rail_m` — НЕЖЁСТКАЯ часть: насколько разность профилей `x(y)` соседних
  кадров ушла от прямой (то есть как изменилась ФОРМА за кадр);
- `far_cur_m` — конец ленты.

Состояние на 2026-09-17 (после третьего прохода, кадры 100..130 `roundT_doubleT`):
`dev_m` медиана 0.102 / макс **0.540** м, `dev_rail_m` 0.059 / **0.341** м,
`shift_m` макс 0.120 м, `dlen_m` макс **1.2** м, размах дальнего конца 4.0 (левая
нить) / 7.0 (правая) м. Сводка по записям: колея внутр. 1507…1529 мм при норме
1520 ± 10; высота верха над прилегающей 0.148…0.176 м; «внутри контура» 0.761…0.833
(порог 0.8), разбор провалов — в конце `check_track_geometry.py`.

Через САМ сервер (`check_track_server.py`, это то, что видит браузер, 2026-09-17):
меш пола покрывает ленту на всех шести записях (недобор 0.0 м), верх ленты стоит над
полом на **0.106…0.250 м** по всей длине; `air_gap` по составной опоре ≤ 0.12 м;
лента доходит до −85 м там, где измерима форма (`roundT_doubleT`, `roundT_squareT`,
`roundT_pressureGate`), доля `predicted` на таких кадрах 24…60 %; метка рельса на
ХОЛОДНОМ кадре — 100 % `rail`, 0 % `middle`; время `/track`: 0.02 с из кэша,
0.5…1.5 с на кадр, которого в кэше нет (остаток — чтение и разбор CDR кадра).

## 3. Грабли, на которые мы уже наступили (числа замерены)

1. **`?record=` сервер молча игнорирует.** Правильный параметр — `?bag=`; с `record=`
   отдаётся запись по умолчанию (`doubleT_obstacle`) при любом запросе. Из-за этого один
   «замер по шести записям» оказался замером одной записи, повторённой шесть раз.
2. **Превышение верха над полом нельзя мерить кольцом.** Правильно — под САМОЙ осью
   рельса (`|Δx| ≤ 0.15` м от x узла, брать максимум z меша в полосе): получается
   0.122…0.168 м по всей ленте. Кольцо ±1.0 м даёт 0.26…0.65 м, потому что попадает в
   ДНО ЛОТКА (глубина лотка 0.26…0.36 м).
3. **Меш пола нельзя тянуть вдоль прямой оси** (`x = s·y + i`): путь изгибается, и на
   40–85 м пол уезжал в сторону от рельса на **1.3–2.4 м** (f126: узел y=−39.75 при
   x=−3.49, прямая ось даёт −1.18). Тянуть надо по оси пути (среднее нитей).
4. **Меш пола нельзя ограничивать ИЗМЕРЕННЫМ участком нитей**: он короче ленты на
   **7…49 м** (до правки: пол −31..−3 при ленте до −85), и рельс висел в пустоте. Пол
   обязан покрывать весь диапазон узлов ленты — сейчас покрывает и даже шире.
5. **Дальняя часть решается по 1–4 точкам на полосу 0.5 м** (замерено по 5-метровым
   полосам: пол ≥20 точек на полосу измерим до −45…−70 м, ≥4 — до −55…−95 м, стены
   ≥50 точек — до −75…−140 м). Посекционное сечение по таким точкам неустойчиво: форму
   продолжения надо брать модельно и наследовать ИЗМЕРЕННЫЕ кривизну и уклон. Именно
   этого не было: продолжение выходило втрое прямее (c2 −0.08 против −0.27 мм/м²), а по
   z — вообще плоским (верх стоял на −1.164 м от −40 до −80 м, пока пол падал).
6. **`roundT_doubleT` выходит из круглого тоннеля в камеру.** Габарит по x (p1..p99 точек
   выше пола+1 м): кадры 0…80 — 5.3…5.9 м, f90 — 6.77, f100 — 10.58, f140…180 —
   12.7…13.4 м. На f89…f128 продолжение «по форме стены» строилось по ЗАЛУ, а не по
   стене: отсюда 1.257 м флапа формы и «рельсы сквозь стены». Форму стены надо
   гейтить (параллельность, стабильность ширины) и падать на измеренную кривизну.
7. **`axis.s` в тёплой сборке залипает** на значении затравки (f117…f130 = +0.03442).
   Опираться на него нельзя: доворот и наклоны брать по измеренным линиям нитей.
8. **Два сервера на одном порту.** Windows `SO_REUSEADDR` позволяет двум процессам
   слушать 127.0.0.1:8765, и запросы уходят то в один, то в другой — с разными сборками
   `track_geometry`. Один и тот же кадр отдаётся по-разному. Перед показом проверяй
   `netstat -ano | grep 8765` и держи ОДИН процесс.

## 4. Чего нет и почему

- **Шпал нет.** Их не видно в облаке: между рельсами идёт встроенный лоток, периодических
  структур в поле нет — проверено Фурье по полосам 5 см (амплитуда 0.3–1.0 м равна
  0.0 мм при пороге обнаружения ~13–16 мм; инъекция 20 мм даёт 10–13 мм). В /track
  `sleepers.instances` пуст, `source` так и пишет: «не наблюдаются (встроенный путь)».
- **Разметки нет.** Ось, колея и контур профиля сверяются с ГОСТ Р 51685-2022 (ширина
  головки 74.59 мм на 13 мм ниже верха) и между собой, но не с истиной: числа дают
  сами данные.
- **Покулонка и возвышение не выравниваются:** высота каждой нити — своя измеренная
  коронка, поэтому «ось-ось» гуляет 1588…1611 мм при норме 1592…1595.

## 5. Чистка и скорость (18.09)

Два яруса чистки `track_geometry.py` после аудита: **ярус 1** — мёртвое (`6ba860a`),
**ярус 4** — скорость (`49e3586`, `0949fcd`). Геометрия вывода (узлы обеих нитей и
меши) не изменилась ни на одном шаге; метрики, где алгоритм всё же менялся, — с
точностью до последних бит (чем это проверено — ниже).

**Что убрано (ярус 1).** 12 неиспользуемых констант — хвостов заменённых реализаций
(`POLY_FOOT_DROP_M`, `POLY_REACH_SLOPE_BLEND`, `POLY_TUN_*`, `LINK_LEN_STEP_M` …),
мёртвая функция `_tunnel_form_sh` (её формула собрана в одного помощника
`_tun_form_inc`), мёртвый параметр `support_fn` с недостижимой веткой в 22 строки,
16 мёртвых локальных переменных (в том числе счётчик `fb_run` в `_floor_anchor`),
умножения на ноль (`cc[2] + y0*0`, `c0 + beta*(yr - yr)`). Знание из комментариев
перенесено в докстринги живых функций, а не выброшено; перед каждой константой —
повторный grep по живому дереву.

**Скорость (ярус 4, замеры).** ВАЖНО про методику: числа ниже — из **контролируемого A/B
в одном процессе** (две версии модуля загружены рядом, кадры чередуются, берётся медиана
по 8 новым кадрам). Первые замеры яруса 4 были помечены «с/кадр», но фактически это была
сумма за все измеренные кадры, то есть завышение примерно в 3 раза — так их брать нельзя.
Контролируемый A/B против состояния до яруса 4 (`41738db`): **0.295 → 0.275 с на кадр,
то есть 1.07×**; профиль того же A/B даёт на `_ridge_candidates` 0.111 → 0.038 с за три
кадра (2.9× на функции). То есть пакетирование гребней реально, но экономия на кадре —
порядка 0.02 с, а не 0.13 с, и абсолютное время сильно зависит от загрузки машины: та же
«до»-версия сейчас идёт 0.295 с, а при замере на тихой машине шла 0.180 с.

| статья | было | стало | ускорение |
|---|---|---|---|
| `_ridge_candidates` | 0.111 с / 3 кадра | **0.038** | 2.9× |
| `_nodes_supported` | 0.121 с / 3 кадра | 0.108 | ~1.1× |
| `_tun_ransac_quad` | 0.0209 → см. оговорку | 0.0086 | 2.4× |
| `_node_outlier_stats` | (замеры яруса 4 с тем же дефектом методики) | — | 3.8× |
| `_axis_local_quad_dev` | — | — | 5.2× |
| `np.polyfit`, вызовов/кадр | 809 | **264** | — |
| **весь кадр, A/B в одном процессе** | **0.295 с** | **0.275 с** | **1.07×** |

Протокол, которым это надо мерить (и которым мерилось): один процесс, две версии рядом,
чередование кадров, медиана по N новым кадрам, рядом — загрузка CPU; **никогда не
складывать времена функций** — они не аддитивны.

Что для этого сделано: подготовка гребней считается ОДИН раз на всё поле полос
(`_ridge_prep`, 87 вызовов → 1; сглаживание и скользящие минимумы больше не
повторяются в каждой полосе), `_nan_med3` вместо `np.nanmedian` под
`catch_warnings`; `np.add.at` и максимумы по узлам → `np.bincount` +
`np.maximum.reduceat`; три `_pctl(10/60/90)` → один `_pctl3` (одна сортировка, те же
порядковые статистики и та же интерполяция); предфильтр облака по поперечине до
полосы узлов (±0.45 м) один раз на вызов `_floor_band`; парабола через 3 точки
разделёнными разностями вместо `np.polyfit` (36 → 1.7 мкс) и ручной Горнер вместо
`np.polyval`; скользящий МНК в `_node_outlier_stats` — префиксными суммами; квадрат
в `_axis_local_quad_dev` — нормальными уравнениями и Крамером.

**Тёплый кадр.** Замерять это надо только контролируемым A/B (см. выше): эталонные
«0.180 → оценка 0.05–0.09 с» из первых замеров яруса 4 **не подтвердились** — они были
получены из сумм по функциям с завышением примерно в 3 раза. Контролируемо: **0.295 →
0.275 с на кадр (1.07×)** в одном процессе с чередованием кадров, при загрузке CPU ~50 %.
Та же «до»-версия на тихой машине шла 0.180 с, поэтому пересчёт на тихую машину даёт
порядка 0.17 с — но это именно пересчёт, а не замер, и его надо подтвердить отдельно.

**Чем гарантировано, что это чистка, а не правка.** Побитовым совпадением: после
КАЖДОГО шага `meta.rail_mesh` (с вырезанными строками) и узлы обеих нитей на
**18 кадрах шести записей × 10–12 полей** — `|Δ| = 0` (ярус 1 — 12 полей,
ярус 4 ч.1 — 12 полей, ч.2 — 10 полей; эталон проверен на воспроизводимость двумя
прогонами). Там, где алгоритм всё же менялся (батч-редукции, замкнутая парабола,
префиксные суммы), гарантия другая и слабее: **`max|Δ|` по узлам = 0 м**, а у метрик
расходятся последние биты (`dev_local_mm` ≤ 4.3·10⁻⁷ мм, `trend_dev_max_m` ≤
5.8·10⁻¹⁵ м).

**Две попытки ускорения откачены по замеру** — обе в одном шаге: замена полного
прохода `np.isnan(arr).any()` на проверку хвоста через `np.partition`. `np.partition`
сортирует частично, положение NaN не гарантировано, поэтому расхождение в двух
вариантах шага: **578 из 2400** (`_pctl`) и **52 из 400** (`_med`); в коде оставлен
комментарий с этими числами. Отдельно откачена оценка, а не код: прежние 1.9× для
`_nodes_supported` были сравнением прогонов под разной нагрузкой, правдивая — 1.15×.

**Тонкость, всплывшая при переписывании.** Высоту пика `_bands` берёт по
НЕсглаженному максимуму полосы, а сам пик ищет по сглаженной строке (в оригинале
`_ridge_candidates` сглаживала свою копию, а вызывающий держал исходную). Если это
не воспроизвести, гейт 0.08…0.45 отбрасывает валидные пики и геометрия едет —
воспроизведено, поэтому числа и совпали.

**Честно не сделано:** сужение окна ±2.5 м по y и батчинг последовательного цикла
`_floor_anchor` (оба меняют числа, а допуск требовал побитовости); остатки всех 100
RANSAC-кандидатов одной матрицей (меняет порядок суммирования и может переключить
выбор лучшей кривой); медиана внутри `_node_outlier_stats` осталась — она не
аддитивна.

**Батарея.** Полный unittest под Python 3.12 на текущем дереве — **247 OK**
(перепроверено 19.09, 78 с), из них набор раздела 2 (core/detector/validation/zones)
— 168 OK. По паспорту pytest под Python 3.13: 184 прошло,
**7 падений** — те же open3d, что и до правок (baseline); на этой машине 3.13 нет,
перепроверить нечем. Тогда же (на момент чистки) `check_track_geometry` давал «не
сошлось 58», переходов вне критерия 0, `dev_m` 0.360, `dev_rail_m` 0.179 — это
другой набор кадров, чем в разделе 2, поэтому числа там и не совпадают с
0.102/0.540.
