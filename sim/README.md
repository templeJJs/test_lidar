# Симулятор туннеля и лидарных данных

Строит синтетические записи метро-туннеля **в том же формате, что наши
`for_hackathon/*.db3`** (rosbag2 + CDR PointCloud2, тема
`/sensing/lidar/hesai128/pointcloud`), поэтому весь существующий код —
`bag_reader`, `zones`, `web_viewer`, детектор — работает на синтетике без правок.

Зачем: в шести реальных записях нет размеченных препятствий, обучать и проверять
детектор не на чем.

## Быстрый старт

```bash
# 0) интерпретатор: только 3.12 (в 3.13 нет open3d)
PY="C:/Users/K4ler/AppData/Local/Programs/Python/Python312/python.exe"

# 1) снять модель сенсора с настоящей записи (артефакт уже лежит в репозитории)
"$PY" -m sim.cli sensor --bag for_hackathon/doubleT_obstacle --out sim/sensor_hesai128.json

# 2) собрать датасет: сцены из профилей всех записей, с поворотами и наклонами
"$PY" -m sim.cli dataset --out sim_out --seed 42 --bags 3 --frames 201 \
      --section facts --kind curve \
      --obstacle person:-20:0 --obstacle suitcase:-32:2.6:by_wall

# 3) сверить синтетику с реальностью по метрикам
"$PY" -m sim.check_sim --sim sim_out/sim_facts_0042 --real for_hackathon/doubleT_obstacle
```

## Что внутри

| файл | ответственность |
|---|---|
| `sensor.py` | модель лидара **из наших данных**: 128 колец, углы места `+14.40…−25.12`, число азимутальных колонок, шум, статистика интенсивности |
| `dataset_facts.py` | замеры по всем шести записям → `dataset_facts.json` (диапазоны для генератора) |
| `scene.py` | случайный туннель: труба по изогнутой оси, профили из записей, повороты, уклоны, боковой наклон, шероховатость ложа |
| `track_geometry_adapter.py` | рельсы R65 и шпалы по ГОСТ (профиль берётся из `track_geometry`, не дублируется) |
| `objects.py` | объекты на пути (человек, чемодан) и флаг «в габарите» |
| `scanner.py` | трассировка лучей `open3d.RaycastingScene`, окклюзия, интенсивность, шум |
| `writer.py` | CDR-энкодер PointCloud2 и запись `.db3` (round-trip проверен нашим `bag_reader`) |
| `manifest.py` | разметка: сцена, сенсор, объекты (класс, бокс, `y`, «в габарите», видимые кадры) |
| `cli.py` | сборка датасета одной командой |

## Числа (замерено)

Сцена рисуется по диапазонам из `dataset_facts.json`, ничего не выдумано:

| параметр | диапазон | откуда |
|---|---|---|
| ширина туннеля | 3.6 … 9.2 м | стены шести записей |
| уклон | 0.31 … 1.94 %, знак случайный | фит пола по записям |
| высота сенсора над полом | 1.36 … 1.86 м | `floor.a` записей |
| радиус поворота | 500 … 4500 м, знак случайный | выведен из дрейфа оси 0.1…0.9 м на 30 м |
| боковой наклон (возвышение) | до ±25 мм | проектная величина (в записях кривых почти нет) |
| шероховатость ложа | ±6 см (rms 0.022…0.024 м) | реальные записи дают 0.007…0.106 м |
| колонок на кадр | 1338 … 2709 | берётся из профиля записи |

Проверка «сим ↔ реал» на `doubleT_obstacle`: точек на кадр 343 540 против 346 787,
стены совпадают до 0.05 м, интенсивность медиана 9 против 11, доля выше 25 — 7 %
против 10.8 %. Скорость: **73…107 мс на кадр** (128 × 2709), то есть 201 кадр ≈
15…22 с при цели 5 минут.

## Известные расхождения и что не сделано

1. **Хвост интенсивности у узких записей тоньше** (доля выше 25: 0.9…4.4 % против
   10.8 % у широкой), а синтетика даёт 7…8 % на всех сценах — модель пока
   откалибрована на объединение записей, а не по каждой. Ручки:
   `BASE_INTENSITY` и `INTENSITY_SIGMA` в `scanner.py`.
2. **Балластной призмы нет** — её роль играет шероховатое ложе трубы, шпалы
   утоплены в него на 12 см.
3. **Моделируется один путь**; второй путь широкого туннеля не строится.
4. **Пропуски возврата отключены** (`dropout = 0.0` в артефакте сенсора).
5. Платформы и напорные ворота (они есть в записях) в сценах пока не строятся.
6. Движение сенсора не моделируется: записи статичны, и MVP тоже.
