# Симулятор туннеля и лидарных данных

Строит синтетические записи метро-туннеля **в том же формате, что наши
`for_hackathon/*.db3`** (rosbag2 + CDR PointCloud2, тема
`/sensing/lidar/hesai128/pointcloud`), поэтому весь существующий код —
`bag_reader`, `zones`, `web_viewer`, детектор — работает на синтетике без правок.

Зачем: в шести реальных записях нет размеченных препятствий, обучать и проверять
детектор не на чем.

## Быстрый старт

```bash
# 0) интерпретатор: только 3.12 (в 3.13 нет open3d)
PY="C:/Users/K4ler/AppData/Local/Programs/Python/Python312/python.exe"

# 1) снять модель сенсора с настоящей записи (артефакт уже лежит в репозитории)
"$PY" -m sim.cli sensor --bag for_hackathon/doubleT_obstacle --out sim/sensor_hesai128.json

# 2) собрать датасет: сцены из профилей всех записей, с поворотами и наклонами
"$PY" -m sim.cli dataset --out sim_out --seed 42 --bags 3 --frames 201 \
      --section facts --kind curve \
      --obstacle person:-20:0 --obstacle suitcase:-32:2.6:by_wall

# 3) сверить синтетику с реальностью по метрикам
"$PY" -m sim.check_sim --sim sim_out/sim_facts_0042 --real for_hackathon/doubleT_obstacle

# 4) воспроизвести КОНКРЕТНУЮ запись: профиль туннеля и поле зрения прибора
#    берутся из неё, без дрожания стен и уклона -- такая сцена обязана сойтись
#    с записью по всем допускам сверки
"$PY" -m sim.cli dataset --out sim_pin --seed 77 --frames 5 \
      --section facts --kind straight --profile doubleT_obstacle
"$PY" -m sim.check_sim --sim sim_pin/sim_facts_0077 \
      --real for_hackathon/doubleT_obstacle --frames 5
```

## Что внутри

| файл | ответственность |
|---|---|
| `sensor.py` | модель лидара **из наших данных**: 128 колец, углы места `+14.40…−25.12`, число азимутальных колонок и поле зрения по азимуту (247° у широкой записи, 101° у узкой), шум, статистика интенсивности |
| `dataset_facts.py` | замеры по всем шести записям → `dataset_facts.json` (диапазоны для генератора: ширина, уклон, колонки, поле зрения, **форма сечения**) |
| `scene.py` | случайный туннель: труба по изогнутой оси, профили из записей, повороты, уклоны, боковой наклон, балласт |
| `track_geometry_adapter.py` | рельсы R65 и шпалы по ГОСТ (профиль берётся из `track_geometry`, не дублируется) |
| `objects.py` | объекты на пути (человек, чемодан) и флаг «в габарите» |
| `scanner.py` | трассировка лучей `open3d.RaycastingScene`, окклюзия, интенсивность, шум |
| `writer.py` | CDR-энкодер PointCloud2 и запись `.db3` (round-trip проверен нашим `bag_reader`) |
| `manifest.py` | разметка: сцена, сенсор, объекты (класс, бокс, `y`, «в габарите», видимые кадры) |
| `cli.py` | сборка датасета одной командой |
| `check_sim.py` | сверка «сим ↔ реал»: одни и те же метрики считаются по синтетике и по записи |

## Числа (замерено)

Сцена рисуется по диапазонам из `dataset_facts.json`, ничего не выдумано:

| параметр | диапазон | откуда |
|---|---|---|
| ширина туннеля | 3.6 … 9.2 м | стены шести записей |
| уклон | 0.48 … 1.94 %, знак случайный | фит пола по записям |
| высота сенсора над полом | 1.36 … 1.86 м | `floor.a` записей |
| радиус поворота | 500 … 3000 м, знак случайный | выведен из дрейфа оси 0.15…0.9 м на 30 м |
| боковой наклон (возвышение) | до ±25 мм | проектная величина (в записях кривых почти нет) |
| балласт | 0…6 см **вверх** от плоскости пола; разброс нижней огибающей 0.008…0.010 м | у записей 0.007…0.106 м |
| колонок на кадр | 1320 … 2706 | берётся из профиля записи |
| поле зрения по азимуту | 100.5 … 247.0° | у записей хвостовой сектор не снимается вовсе |
| шаг колонок по азимуту | 0.068 … 0.092° | колонки на поле зрения (у записей 0.0675 и 0.0915) |
| высота свода | 4.60 … 5.10 м над ложем, у записи со станцией 8.5 м | `section` в замерах; форма (арка, наклонная плита) — тоже из него |
| полка у стены (ниша) | 1.41 … 1.58 м над ложем, наружу на 0.40 … 0.76 м | замерено у **всех шести** записей |
| ось пути по рельсам | −0.123 … +0.018 м от нуля | замерено по нитям (`sim/rails.py`), колея 1.49 … 1.64 м |
| пропуски возврата | 1.06 … 6.53 % слотов сетки | по промежуткам колонок в кольцах (`sim/sensor.py`) |

Проверка «сим ↔ реал» пришпиленным профилем -- **по всем шести записям**
(`--frames 5`, столько же кадров, сколько в замере профиля; все допуски пройдены):

| запись | точки на кадр | пол `a`, м | стены, м | медиана яркости | свод, м | свод по X, м | полка, м | азимут, ° |
|---|---|---|---|---|---|---|---|---|
| `doubleT_obstacle` | 0.1 % | 0.017 | 0.004 | 1.1 % | 0.04 | 0.06 | 0.05 | 247.5 / 247.0 |
| `doubleT_platform` | 0.2 % | 0.018 | 0.036 | 11.8 % | 0.02 | 0.13 | 0.06 | 101.0 / 100.5 |
| `roundT_doubleT` | 0.1 % | 0.012 | 0.019 | 13.1 % | 0.04 | 0.08 | 0.07 | 101.5 / 101.0 |
| `roundT_pressureGate_roundT` | 0.1 % | 0.011 | 0.013 | 13.4 % | 0.04 | 0.11 | 0.08 | 101.0 / 100.5 |
| `roundT_squareT_pressureGate_squareT` | 0.1 % | 0.009 | 0.018 | 13.4 % | 0.03 | 0.04 | 0.06 | 101.0 / 100.5 |
| `squareT_platform_squareT_switch` | 0.1 % | 0.011 | 0.041 | 12.5 % | 0.03 | 0.08 | 0.07 | 101.0 / 100.5 |

Расхождения: точки, пол, стены, медиана яркости, уровень свода над осью (допуск
0.40 м), форма свода по X (0.04…0.13 м при допуске 0.20) и полка у стены
(0.05…0.08 м при допуске 0.35). Прочие допуски: пол 0.05 м, стены 0.10 м, точки
25 %, медиана яркости 20 %. Скорость сцены:
**60…113 мс на кадр** (128 × 2706), то есть 201 кадр ≈ 12…23 с при цели 5 минут.

Форма свода проверяется отдельной метрикой, потому что иначе плоский потолок
проходит: замерено, что плоский свод на верной высоте даёт 0.32 м расхождения на
арочной записи и 0.55 м на наклонной, а свод по профилю записи — 0.04…0.13 м.
Метрика считает худшее расхождение по ячейкам профиля, пропуская ячейки с крутым
перепадом (у станции профиль зубчатый: 5.6 → 8.2 → 7.0 м, и там замер неустойчив
сам по себе — проверено на синтетике против её собственного меша: 0.02…0.06 м на
гладких участках и до 0.94 м на ступенях).

Кадров в сверке берём столько же, сколько в замере профиля, и это не придирка: у
части записей геометрия гуляет по длине (платформа, напорные ворота, стрелка -- их
видно в именах записей), и другое подмножество кадров даёт другое среднее. При
`--frames 3` расходятся 4 записи из 6 (пол до 0.02 м, стены до 0.04 м) -- это
свойство ЗАПИСИ, а не сцены.

Свод мерится по точкам ДАЛЬШЕ 8 м, и это тоже не придирка: в ближней зоне точек
ложа на порядок больше, и перцентиль по смешанному окну показывает ложе. Замер
«95-й перцентиль в окне y = −14…−2» давал «свода над осью нет, 0.4 м» -- ошибка
оценщика, а не свойство данных: правильный замер (99.5-й перцентиль по дальним
точкам) даёт гребень 4.6…5.1 м у всех шести записей.

## Известные расхождения и что не сделано

1. **Свод повторяется по профилю записи** (высота, наклон, арка), и это
   проверяется допуском по ячейкам профиля: худшее расхождение 0.04…0.13 м при
   допуске 0.20. Что осталось: у записи со станцией (`doubleT_platform`) профиль
   зубчатый (5.6 → 8.2 → 7.0 м на двух метрах) -- это уже отдельные конструкции
   (рёбра, светильники), а не свод, и воспроизводить их трубой нельзя. Метрика
   «свод у стен» (медиана по полосе) для таких записей врёт (0.89 м) и оставлена
   справочной: медиана по зубчатому профилю зависит от того, сколько точек замерло
   в каждой ячейке, а не от геометрии.
2. **Хвост интенсивности** подобран по каждой записи (доля выше 25 расходится на
   9…21 %), σ считается из медианы и доли своей записи формулой
   `ln(25 / медиана) / z(1 − доля)` (`scene.intensity_sigma_for`). Но это подбор
   ОДНОЙ величины под ОДНУ метрику: форма распределения (p90, доля выше других
   порогов) отдельно не сверялась.
3. **Балластной призмы нет** — её роль играет балласт на ложе трубы (0…6 см вверх),
   шпалы утоплены в пол на 12 см. Нижняя огибающая ложа у сцены глаже реальной
   (0.005…0.008 м против 0.014…0.118 м): у записей ложе гуляет по длине, у нас —
   ровная плоскость с камнями.
4. **Рельсы найдены, второго пути по ним не видно.** Работающий признак -- головка
   ВЫСТУПАЕТ над своим ложем (`sim/rails.py`: высота точек бина против уровня ложа
   в 0.25…0.60 м рядом, порог 0.06 м). На синтетике, где сцена сама ставит рельсы
   на `ось ± колея/2`, детектор находит обе нити с ошибкой ≤ 0.04 м и колею
   1.50 против проектных 1.52 (`tests/test_sim_rails.py`). На записях он даёт ось
   −0.123…+0.018 м и колею по нитям 1.49…1.64 м -- то есть путь действительно стоит
   на `x ≈ 0`, как и предполагала сцена, а не «где-то там». Второй пары нитей на
   расстоянии колеи нет НИ В ОДНОЙ записи, включая двухпутную: во второй половине
   её сечения нити есть (x ≈ +3.4 и +5.4…+5.8), но колею они не образуют.
   **Второй путь в сцене так и не строится**: детектор не даёт для него
   доказательства, а рисовать путь «на глазок» -- значит врать про данные.
   Прежнее поле `rail_bands` в артефакте (убрано как мусор) давало у
   `doubleT_obstacle` восемь «нитей» на 2.5 м при стенах 9.2 м.
5. **Пропуски возврата отключены** (`dropout = 0.0` в артефакте сенсора).
6. **Станции и ворота по длине пути не строятся**, и это уже осознанное решение, а
   не пропуск. Полка у стены (1.41…1.58 м, наружу на 0.40…0.76 м) оказалась
   свойством ВСЕХ шести записей: за нитью стены на этом уровне есть поверхность в
   каждой из них, тысячи точек, на обеих сторонах. То, что в `doubleT_platform`
   выглядело платформой станции, -- тот же уровень: в кадрах этой записи плита
   стоит на 1.40…1.60 м в 18 проверенных кадрах из 18, обе стороны. А вот станция
   и напорные ворота -- это ПРОТЯЖЁННЫЕ объекты в конкретном месте пути: у
   `doubleT_platform` плита видна в одних кадрах и почти не видна в других
   (20800 точек против 611) -- сцена там меняется по составу, а не по движению.
   Сцена же однородна и статична, поэтому ни станцию, ни ворота, ни стрелку она
   воспроизвести не может: для этого нужно менять состав сцены между кадрами.
   Замеры для этого уже есть: `section` и `ledge` в `dataset_facts.json`.
7. **Движение сенсора не моделируется -- и не нужно.** Это проверено, а не
   заявлено: профиль ложа по дальности не смещается между кадрами ни у одной
   записи (замер `frame_shift_m`: 0.00 м/кадр). Кадры при этом бывают разными по
   составу сцены -- у `doubleT_platform` структура станции видна в одних кадрах и
   почти не видна в других (20800 точек в кадре 0 против 611 в кадре 40), -- но это
   не движение сенсора. Такие «кадры с разным составом» наша сцена не
   воспроизводит: она однородна и статична, а в записях сцена местами меняется.
