# LiDAR Rail Detection & Visualization

Детекция рельсов и измерение колеи по облакам точек LiDAR из ROS 2 bag-файлов (.db3). Работает без ROS — читает SQLite напрямую, рендерит через Open3D.

## Главные файлы

| Файл | Что делает | Когда нужен |
|---|---|---|
| **`rail_detection.py`** | Поиск рельсов, маска точек, измерение колеи, 3D-меши. Линейный фит `x = slope*y + intercept`. | По умолчанию |
| **`rail_geometry.py`** | Адаптер: та же детекция, но полилинией через `test/track_geometry.py`. Включается флагом `--polyline` (см. ниже). | Кривые, стрелки |
| **`test/track_geometry.py`** | Геометрия пути по кадру: нить полилинией, измеренное сечение рельса, профиль пола с лотком, ось тоннеля. Своя связь кадров и тёплая сборка. | Через `--polyline` |
| **`visualize_bag.py`** | 3D-анимация облаков точек + рельсы красным. `--accumulate-speed` для обогащения дальних точек. `--rail-labels` для предрассчитанных масок. `--polyline` для детекции полилинией. | Смотреть данные |
| **`speed_estimator.py`** | Оценка скорости по отражателям (яркие точки). Матч между кадрами по XZ, консенсус по dY. | Скорость, аккумуляция |
| **`odometry.py`** | SE(2)-одометрия: поза `(x, y, θ)` каждого кадра по отражателям (Кабш + отбраковка выбросов). | Всегда, база для карты |
| **`track_map.py`** | Карта пути: сшивка ближних наблюдений колеи через позы в единую линию на весь бэг. | Разметка пути |
| **`eval_extrapolation.py`** | Замер: насколько точно путь предсказывается вперёд по пройденному участку. Ответ: недостаточно точно (см. «Габарит на дальности»). | Эксперименты |
| **`eval_wall_range.py`** | Замер: до какой дальности видны обе стены тоннеля — граница, до которой габарит строится по стенам. | Габарит, планирование |
| **`wall_corridor.py`** | Габарит по стенам: ведение коридора бинами по 5 м, слои высоты, поиск препятствий в габарите. Даёт дальность, до которой габарит ПОДТВЕРЖДЁН. | Габарит на 100 м |
| **`eval_wall_corridor.py`** | Замер: сколько из потолка по стенам берёт реальное ведение коридора + счётчик срывов на второй путь. | Габарит, замеры |
| **`rail_mapper.py`** | ⚠️ УСТАРЕЛ, содержит баг (см. ниже). Заменён на `odometry.py` + `track_map.py`. | Не использовать |

## Алгоритм детекции рельсов (`rail_detection.py`)

1. **Плоскость земли** — grid-based RANSAC по 5-му перцентилю Z в ячейках (векторизовано через `searchsorted` + `argsort`)
2. **Поперечные Z-профили** — поиск пиков 3-40 см над землёй (головки рельсов). Порог 40 см нужен для участков с поперечным наклоном пути — на повороте один рельс может быть на 10+ см выше другого (виражный подъём)
3. **Субпиксельный центр пика** — положение пика берётся как взвешенный по высоте центроид точек головки в окне ±60 мм вокруг вершины, а не как X бина с максимумом. Бин 50 мм иначе квантует результат: измеренная колея принимала только значения 1400/1500/1550/1650 мм
4. **Пары по колее** — расстояние между пиками = 1520 ± 150 мм, midpoint в пределах `own_x_range` от лидара. На срез берётся **одна** пара — с колеёй, ближайшей к номиналу (прежде конкурирующие гипотезы в одном срезе обе шли в фит)
5. **Фильтры пар** — три ступени (см. «Детекция на поворотах»):
   `_filter_pairs_self_gauge` (колея, не совпадающая с колеёй этого кадра),
   `_filter_pairs_continuous` (оторванный по дальности хвост),
   `_filter_pairs_consensus` (несогласованные с опорной **кривой** midpoint)
6. **Кластеризация** (DBSCAN) — разделение пар на отдельные пути
7. **Фит колеи как целого** — осевая линия фитится прямой или параболой, нити строятся как осевая ± полколеи (см. ниже)
8. **Робастный фит** — два режима в зависимости от дальности:
   - **Ближняя (<30 м)**: polyfit с MAD-фильтрацией выбросов → tuple `(a2, a1, a0)`
   - **Дальняя (≥30 м)**: скользящее окно по узлам каждые 10 м, взвешенная медиана X с MAD-фильтрацией → `{'knots_y', 'knots_x'}`, между узлами `np.interp` (плавная кривая без разрывов)

### Фильтр консенсуса (`_filter_pairs_consensus`)

Главный источник срывов детекции в ближней зоне — единичные ложные пары
(кабель, край платформы, чужой путь), которые МНК-фит тянул за собой.

Отделить их по признакам **одиночного пика нельзя** — замер показал, что
распределения перекрываются почти полностью:

| Признак | верные (med) | ложные (med) |
|---|---|---|
| точек в пике | 18 | 10 |
| высота z | 0.25 | 0.21 |
| ширина по X | 0.14 | 0.13 |
| intensity | 5 | 8 |

Разделяет пространственная согласованность: рельс непрерывен, поэтому
midpoint колеи — гладкая функция дальности, а ложная пара от неё отскакивает.
Опорная линия строится робастным фитом midpoint(y) и уточняется итеративно.

Сравнение с общей линией, а не с долей ближайших соседей: на 25-30 м пар мало
(у каждой 2-4 соседа), и подсчёт доли выбрасывал верные пары — покрытие на
30 м падало со 100% до 74% при той же точности.

**Стрелки.** На развилке midpoint раздваивается, и фит по всем парам ложится
между ветками, не совпадая ни с одной: на кадре 255 `roundT_pressureGate_roundT`
это давало 30 плохих пар из 34 и остаток до 0.87 м, хотя обе ветки детектированы
верно. Поэтому линия сначала привязывается к ближней зоне (`seed_range`, 12 м),
где путь поезда однозначен, и ветка выбирается по близости к затравке
(`branch_tol`). Габарит ведётся по своей ветке.

### Фит колеи как целого: линия повторяет поворот

Раньше две нити фитились **независимо прямой** `x = slope*y + intercept`,
поэтому на повороте линия шла по хорде, а не по дуге, и «не повторяла профиль».

Теперь фитится **осевая линия колеи**, а нити строятся как осевая ± полколеи.
Рельсы жёстко параллельны, поэтому вся форма пути живёт в осевой: независимый
фит тратил две степени свободы на то, что физически одна, вдвое усиливал шум и
допускал непараллельные нити, чего в пути не бывает.

Осевая фитится параболой (`_fit_curve_robust`), но **квадратичный член берётся
только если он реально улучшает остаток** (на 15% и больше) и если пары
покрывают ≥ 8 м по Y. Иначе возвращается прямая. Это важно: на прямом участке
парабола по шумным парам изгибается на пустом месте — ровно тот эффект, из-за
которого прежняя попытка «фитить параболой» на дальности делала хуже. Здесь
она применяется к осевой (вдвое меньше шума, чем у нити) и только в ближней
зоне, где пары плотные.

Селективность на 6 бэгах (кадров с параболой / с прямой, изгиб линии на 30 м):

| Bag | парабол | прямых | изгиб@30 med | max |
|---|---|---|---|---|
| doubleT_platform (прямой) | 11 | 24 | 0.08 | 0.36 |
| roundT_pressureGate_roundT | 17 | 10 | **0.70** | 1.70 |
| roundT_squareT_pressureGate_squareT | 15 | 40 | **0.69** | 1.74 |

На прямом участке изгиб 8 см (то есть парабола почти вырождается в прямую),
на поворотах — 0.7 м на 30 м. Остаток пар от фита при этом не вырос.

`rail_x(line, y)` понимает оба формата: 2-tuple `(slope, intercept)` и
3-tuple `(a2, a1, a0)`. Все потребители (`apply_rail_lines`, `measure_gauge`,
`build_rail_meshes`, `_find_own_track`, проверка консистентности в
`visualize_bag.py`) переведены на него.

### Робастный фит (`_fit_rail_robust`)

На дальних дистанциях одна парабола через все пары дёргается из-за шума. Вместо этого:

- Каждые 10 м по Y создаётся **узел** (knot)
- Для каждого узла берутся точки в скользящем окне ±15 м
- Веса — треугольное ядро (ближе к узлу → больший вес)
- **MAD-фильтрация** выбросов (3σ) в каждом окне
- **Взвешенная медиана** → X узла
- `np.interp()` между узлами → плавная кривая

Результат: ближние узлы (много точек) точные, дальние (мало точек) шумнее, но **не влияют на ближние**. `rail_x()` автоматически обрабатывает оба формата (tuple и dict).

### Адаптивные срезы по дальности

На дальних дистанциях (100-200 м) облако точек разреженное. Алгоритм автоматически адаптирует параметры:

| Параметр | Вблизи (< 10 м) | Вдали (200 м) | Зачем |
|---|---|---|---|
| Ширина среза (полу) | 0.25 м | 2.0 м | Больше точек в срезе |
| X-бин | 0.05 м | 0.15 м | Бин не пустой |
| Порог группировки пиков | 0.15 м | x_bin × 2.5 | Адаптивен к X-бину |
| Мин. точек в срезе | 30 | 10 | Не отбрасывать дальние |

Параметры задаются константами в начале цикла в `find_rail_lines()` — можно менять:

```python
SLICE_HALF_NEAR = 0.25       # полуширина среза вблизи, м
SLICE_HALF_FAR = 2.0         # полуширина среза на макс. дальности, м
XBIN_NEAR = 0.05             # ширина X-бина вблизи, м
XBIN_FAR = 0.15              # ширина X-бина на макс. дальности, м
ADAPT_NEAR = 10.0            # дальность начала адаптации, м
ADAPT_FAR = 200.0            # дальность конца адаптации, м
```

### Ключевые функции

- `find_rail_lines(points, intensity, fit_range=30.0)` — поиск рельсов, возвращает линии + плоскость земли. `fit_range` — предел дальности пар, по которым строится фит (дальше линия экстраполируется)
- `apply_rail_lines(points, rail_lines, ground_plane)` — маска рельсовых точек по найденным линиям
- `measure_gauge(points, rail_mask, rail_lines, ground_plane)` — измерение колеи (оси + внутренние грани)
- `rail_x(line, y)` — X рельса в точке Y: 2-tuple `(slope, intercept)` или 3-tuple `(a2, a1, a0)`. Узловые линии (`dict` с `knots_y`/`knots_x`) он **не** понимает — они есть в `old/rail_detection.py` и в `rail_geometry.py`; при `--polyline` `rail_x` подменяется на knots-совместимый (`rail_geometry.patch_rail_detection`)

### Завал плоскости земли (исправлено)

Прежний допуск на уклон плоскости был 0.2, и он пропускал явно ложные оценки:
на 22-43% кадров поперечный уклон `a` выходил за 0.05, доходя до 0.18, при
медиане около нуля. Завал плоскости смещает `dz`, а по `dz` ищутся головки
рельсов — профиль в срезе переставал быть профилем пути (значения доходили
до +4.8 м, то есть в срез попадали стены).

Теперь допуск наращивается ступенями `(0.06, 0.12, 0.2)` вместе с коридором.
Реальный вираж метро даёт уклон до ~0.1, поэтому 0.06 отсекает выбросы, не
трогая настоящие кривые:

| Bag | было \|a\|>0.05 | стало |
|---|---|---|
| roundT_pressureGate_roundT | 22% | **0%** |
| roundT_squareT_pressureGate_squareT | 36% | **13%** |
| doubleT_platform | 43% | **9%** |

### Аккумуляция кадров ломала детекцию (исправлено)

С `--accumulate-speed 5` число найденных пар падало в разы (38 → 6). Три
причины, все исправлены в `accumulate_with_speed`:

1. **Провал оценки скорости давал `dy = 0`**, то есть кадр клался в аккумулят
   несмещённым — это размазывает рельсы сильнее, чем пропуск кадра. Теперь
   такой кадр отбрасывается (`nan` вместо `0.0`).
2. **Выбросы скорости.** На кадре 250 `roundT_pressureGate_roundT` оценка
   давала 27 км/ч вместо реальных 55, и пар находилось 4 вместо 33. Поезд не
   меняет скорость рывком за 0.1 с, поэтому оценка, выпадающая из ряда
   соседних больше чем вдвое, отбраковывается.
3. **Игнорировался поворот.** Кадры совмещались только сдвигом по Y, хотя на
   кривой кадр ещё и повёрнут: при реальных 0.2°/кадр за 5 кадров набегает
   ~1°, что на 30 м даёт полметра. Теперь применяется полное SE(2)-
   преобразование — поворот берётся из `odometry.estimate_motion_from_frames`.
   Это та же ошибка, что описана ниже для `rail_mapper.py`.

Кроме того, `--max-y-distance` не доходил до маски: детекция шла по заданной
дальности, а `apply_rail_lines` вызывался с дефолтом 40 м, поэтому при
`--max-y-distance 30` линия экстраполировалась на 10 м за пределы данных.

### Колея 1550-1580 мм — это норма, а не шпала

Проверено, что детектор ловит именно головку рельса, а не шпалу. Профиль
найденных нитей на `roundT_squareT_pressureGate_squareT`:

| Дальность | высота над землёй | ширина верха |
|---|---|---|
| 5 м | 0.265 м | 99 мм |
| 10 м | 0.262 м | 88 мм |
| 20 м | 0.247 м | 98 мм |
| 30 м | 0.231 м | 58 мм |

Ширина 88-103 мм соответствует головке Р65 (75 мм) с учётом разрешения;
шпала дала бы 200+ мм и высоту около нуля (вровень с балластом).

Измеренная колея 1548-1580 мм против номинала 1520 мм — ожидаемое
систематическое завышение: пик берётся по **вершине головки**, а расстояние
между осями головок больше расстояния между внутренними гранями. Нормативная
база (внутренние грани на 13 мм ниже поверхности катания, ПТЭ п.45) считается
отдельно в `measure_gauge` как `inner`.

### Известные особенности

- На участках с поперечным наклоном пути (повороты) рельсы на разной высоте — для этого верхний порог высоты 40 см (а не 25 см). Виражный подъём: наружный рельс может быть на 10+ см выше внутреннего
- Позиция пика берётся по X бина с максимальным Z (вершина головки), а не как среднее — иначе шпала/балласт сдвигает центр
- При переобнаружении рельсов (`--redetect-every`) проверяется консистентность: колея не скачет >100 мм, midpoint не сдвигается >150 мм, плоскость земли не прыгает >100 мм

### Shadow-детектор (провалы плотности)

Дополнительный детектор пар рельсов через провалы в гистограмме плотности по X. Рельс выпирает → лидар не видит за ним → характерный провал. Пара провалов с расстоянием колеи = рельсы. Работает как fallback когда пиковый детектор не нашёл пару в срезе (`_extract_shadow_pairs`).

### Детекция на поворотах: перескоки исправлены

Симптом — на повороте линия «перескакивала» между кадрами и уходила в сторону
(на стену или соседний путь). Замер по карте пути как эталону показал, что
причина не одна, а четыре, и все — геометрические, а не «мало точек».

**1. Коридор поиска был прямым, а путь изогнут.** Предел по X был постоянным
(`own_x_range` + полколеи), то есть прямой трубой в системе лидара. Но путь
уходит вбок как `y²/2R`: при радиусе метро 300 м это 1.5 м уже на 30 м и
2.7 м на 40 м. Замер по карте на `roundT_pressureGate_roundT` — центр колеи
выходит за `own_x_range = 1.5 м`:

| Дальность | доля кадров вне коридора | макс. вынос |
|---|---|---|
| 30 м | 13% | 1.79 м |
| 40 м | 28% | 2.58 м |
| 50 м | 35% | 3.57 м |

То есть настоящие рельсы оказывались **вне окна поиска**, и внутри оставались
только стены, кабели и соседний путь. Теперь допуск растёт как `y²/2R` при
R = 250 м (с запасом к самой крутой кривой метро). Вблизи это почти ничего не
меняет (на 10 м прибавка 0.2 м), поэтому ложные пары у лидара отсекаются
по-прежнему.

**2. Опорная линия фильтра консенсуса была прямой.** `_filter_pairs_consensus`
сравнивал пары с прямой, а на повороте midpoint — кривая. Остаток верных пар
рос с дальностью чисто от неучтённой кривизны и не проходил допуск 0.12 м.
На кадре 231 `roundT_pressureGate_roundT` (путь уходит с 0.04 м на 2 м до
1.89 м на 39.5 м) выбрасывались **все** верные пары дальше 28 м, а среди
уцелевших дальних оставались пары соседнего пути (вынос −1.3 м), случайно
легшие близко к прямой, — они и тянули фит. Теперь опорная линия
квадратичная, когда пары покрывают плечо ≥ 8 м: проходит 40 пар из 45,
и отвергнутые пять — ровно те пять, что лежат в стороне от пути.

**3. Номинальный допуск колеи не отсекал дальние ложные пары.** Допуск
±150 мм вокруг 1520 мм слишком широк: на кадрах 237/240 ложные пары на
39-42 м давали 1400-1450 мм и проходили фильтр, хотя настоящая колея в кадре
1573 ± 8 мм. Добавлен `_filter_pairs_self_gauge` — колея оценивается по
ближней зоне **этого же кадра** (разброс между кадрами 8 мм против 130-180 мм
у ложных пар) и служит куда более острым признаком, чем номинал.

**4. Фит шёл по всем парам, включая дальние.** Дальние пары почти не несут
сигнала, но сидят на самом длинном плече. Замер точности самих пар по карте:

| Дальность | \|откл\| med | доля с откл > 0.2 м |
|---|---|---|
| 0-5 м | 0.013 | 0.0% |
| 15-20 м | 0.028 | 0.0% |
| 30-35 м | 0.045 | 3.1% |
| 35-40 м | 0.047 | **7.5%** |

Медиана растёт умеренно, а вот доля грубых промахов взрывается. Поэтому фит
строится по парам не дальше `fit_range = 30 м`, а за ней линия
**экстраполируется**; плюс вес пары падает с дальностью
(`w = 1/(1 + (y/18)²)`). Отбрасывание дальних пар не ухудшает, а срезает хвост:
ошибка осевой на 30 м p95 0.461 → 0.139, max 1.007 → 0.226.

Это подтверждает и независимый замер (см. «Предсказание пути вперёд»):
экстраполяция параболы по чистой ближней зоне точнее, чем фит по шумной дальней.

#### Результат

Эталон — карта пути, построенная **прежним** кодом (карта использует только
ближнюю зону 15 м, которую правки не трогают, так что эталон не смещается;
проверено: карта до и после идентична — 401 узел, колея 1576 ± 6 мм).

`roundT_pressureGate_roundT` (повороты, одометрия 75% прямых оценок):

| D | err p95 было→стало | err max было→стало | jump p95 было→стало | jump max было→стало |
|---|---|---|---|---|
| 10 м | 0.053 → **0.048** | 0.117 → **0.089** | 0.092 → **0.051** | 0.271 → **0.117** |
| 20 м | 0.150 → **0.097** | 0.444 → **0.155** | 0.434 → **0.056** | 0.792 → **0.174** |
| 30 м | 0.189 → **0.177** | 0.782 → **0.332** | 1.075 → **0.147** | 1.677 → **0.544** |

приведённый одометрией к одной точке пути. На 30 м p95 упал **в 7 раз**,
максимум — втрое. На прямом `doubleT_platform` метрики не ухудшились

поэтому карта на повороте сама уезжает. Видно по тому, что «ошибка» появляется
уже на 3-9 м, где детекция заведомо точна. На кадрах этого бэга с надёжной
локальной одометрией ошибка на 30 м — med **0.011**, max **0.098** м.

## Детекция полилинией (`--polyline`, `rail_geometry.py`)

Альтернативная детекция из `test/track_geometry.py`. Включается флагом, по
умолчанию работает прежняя.

```bash
python visualize_bag.py for_hackathon/roundT_doubleT --max-y-distance 40 --polyline
python track_map.py     for_hackathon/doubleT_platform --polyline
```

Флаг набирать дефисами: `—-polyline` с длинным тире (автозамена macOS,
копирование из мессенджера) argparse отвергает целиком — `error: unrecognized
arguments`.

### Чем отличается

Прежняя детекция фитит колею **как целое**: осевая линия прямой или параболой,
нити как осевая ± полколеи (см. «Фит колеи как целого»). Это одна-две степени
свободы на всю длину, поэтому коридор поиска стоит прямым в системе лидара, а
путь изогнут — отсюда расширение коридора на `y²/2R` и три ступени фильтров
против перескоков.

Полилиния держит нить **узлами через 0.5 м**: каждый следующий ищется в окне от
предсказания по предыдущим, с отбраковкой по MAD и остановкой об стену. Коридор
едет за нитью, поэтому `--own-x-range` при этом флаге не действует.

При `--polyline` из `rail_detection.py` не вызывается **ничего** — заменяются все
четыре точки тракта:

| функция | по умолчанию | с `--polyline` |
|---|---|---|
| поиск нитей | фит прямой/параболой | полилиния, узлы 0.5 м |
| маска точек | полоса от плоскости земли | полоса у измеренного верха головки |
| колея | пересчёт по точкам маски | измерена по головкам на уровне ПТЭ |
| меши | прямоугольник 75×150 мм | развёртка измеренного сечения, подуклонка 1:20 |

`rail_geometry.enable(full=False)` оставляет `rail_detection` маску, колею и меши,
подменяя только поиск нитей — режим сравнения, из CLI не выведен.

### Что это даёт

Маска чище, потому что окно по высоте отсчитывается **от узла нити**, а не от
плоскости земли: у каждого узла своя высота верха головки, и на вираже, где нити
разнесены по высоте, общий порог `dz` над землёй срезал одну из них.

Замер на `roundT_doubleT` f150:

| | точек в маске | не головка (`dz` < 0.16) | дальность |
|---|---|---|---|
| по умолчанию | 3374 | **43%** (шпалы, балласт) | 39.7 м |
| `--polyline` | 1441 | **0%** | 44-48 м |

Маска вдвое меньше не из-за потери рельса, а из-за отказа от шпал.

Карта пути на `doubleT_platform` (весь бэг, 345 кадров):

| | колея в карте | СКО | наблюдений на узел | время |
|---|---|---|---|---|
| по умолчанию | 1570 мм | 10 мм | 171 | 63 с |
| `--polyline` | **1518 мм** | **1 мм** | 212 | 49 с |

Эталон 1520 мм. Прежняя детекция давала +50 мм: ловила не только головку (те же
43% шпал в маске).

Обобщение — 48/48 кадров на всех шести бэгах, колея 1517-1525 мм.

### Плоскость пола считается по полному облаку

`_floor_plane` в `track_geometry` набирает ячейки в полосе `y ∈ [-60, -2]`. При
обрезке до ближней зоны (`track_map` зовёт с `max_y_distance=15`) ячеек остаётся
вчетверо меньше, и край платформы на `|x| = 3..5` м — он на 0.06-0.80 м выше
пути — перекашивает МНК: поперечный уклон `a` доходил до **+0.38** против −0.017
по полному облаку (`doubleT_platform` f64, f111; `|a| > 0.20` на 9% кадров).

Поэтому адаптер считает плоскость по **полному** облаку, а нити — по
обрезанному. Скачок Z в карте: p95 **52 мм** против 415 без этой поправки (у
прежней детекции 62 мм).

У `rail_detection.estimate_ground_plane` этой проблемы нет — там коридор
`x_half_width=2.5` м поставлен ровно против платформы (см. «Завал плоскости
земли»).

### Ограничения

- **Настроено под метро Р65.** `GAUGE_INNER_NOMINAL_MM = 1520` (ПТЭ п. 45),
  коридор пары по осям 1.580-1.610 м, `Y_SEARCH_M = 45`, подуклонка 1:20
  (ВСН 94-77). На другой колее или профиле рельса константы надо менять.
- **Своя связь кадров.** `track_geometry` держит собственные кэши тёплой сборки
  и связи решений (`LINK_*`, `_warm_*`) с ключом «запись + номер кадра»; это
  дублирует роль `odometry.py`, и чей ответ главный — открытый вопрос. Ключи
  передаются через `rail_geometry.set_frame_context(bag_key, frame_index)`, без
  него каждый кадр идёт холодным проходом (0.3 с против 0.16 с).
- **Узлы полилинии — оси нитей**, между ними ~1587 мм (`gauge_axis`), а
  `track_map` отбраковывает пары по 1520 ± 120 мм. Адаптер сдвигает пары на
  полширины головки внутрь (ширина измеренная, не из ГОСТа); отключается
  `pairs_inner=False`.
- `track_map.py --polyline` использует только поиск нитей — маска и меши там не
  применяются.

## Габарит на дальности: чем его строить (`eval_wall_range.py`, `eval_extrapolation.py`)

Целевой вопрос кейса — «есть ли препятствие в габарите поезда на 100 м».
Ответ упирается в то, откуда на такой дальности взять положение пути.
Здесь собраны замеры по трём возможным источникам.

### Экстраполяция пути не работает

`eval_extrapolation.py` меряет боковую ошибку предсказания по короткому окну
наблюдений против истины (будущие позы того же бэга). На `roundT_doubleT`:

| модель | 100 м | 150 м | 200 м |
|---|---|---|---|
| прямая | 2.76 м | 10.91 м | 19.51 м |
| дуга | **1.61 м** | 5.78 м | 11.38 м |
| клотоида | 8.91 м | 29.32 м | 63.39 м |

Полуширина габарита — **1.7 м**. Лучшая модель (дуга) на 150 м ошибается в 3.4
раза больше габарита, p95 = 16 м. Решение «упирается или нет» на таких числах
строить нельзя.

Причина не в модели: на 150 м вперёд в текущем кадре просто нет информации о
том, начнётся ли там кривая. Нейросеть её тоже не извлечёт. Клотоида худшая
именно потому, что экстраполирует производную кривизны и улетает.

### Карта знает путь точно, но только пройденный

`track_map.npz` — не предсказание, а память: путь на 170 м впереди был измерен
вблизи, когда поезд туда доехал. Ошибка против будущих поз (`roundT_doubleT`):

| дальность | med | p95 |
|---|---|---|
| 25 м | 0.062 м | 0.199 м |
| 100 м | 0.087 м | 0.268 м |
| 170 м | **0.107 м** | 0.287 м |

10 см на 170 м — в 6 раз меньше полугабарита, и с дальностью почти не растёт
(против 5.78 м у дуги на 150 м, разница в 50 раз).

Ограничение: карта покрывает только то, где поезд **уже проехал**. Для realtime
на новом участке её нет, и последние ~170 м любого бэга дальнего прогноза не
имеют.

Замер сравнивает карту с позами, из которых она же построена, поэтому часть
общей ошибки одометрии взаимно сокращается. Абсолютная точность в мире может
быть хуже; для габарита нужна относительная — она такая.

### Стены тоннеля — рабочая опора до ~90 м на прямой

Стены параллельны пути и на дальности плотнее рельсов. `eval_wall_range.py`
меряет, до какой дальности видны ОБЕ стены (≥8 точек на стену в бине 10 м,
полоса высот −1…+2 м, поиск в 1.2-6 м от оси пути):

| бэг | прямая med / p10 | кривая med / p10 |
|---|---|---|
| doubleT_platform | 50 м / 40 м | — |
| roundT_doubleT | 95 м / 30 м | 30 м / 0 м |
| roundT_pressureGate_roundT | 90 м / 60 м | 70 м / 36 м |
| roundT_squareT_pressureGate_squareT | 100 м / 59 м | 60 м / 50 м |
| squareT_platform_squareT_switch | 95 м / 35 м | 40 м / 40 м |
| **итого** | **70 м / 0 м** | **40 м / 20 м** |

Выводы:

- **На прямой стены дают 90-100 м** на четырёх бэгах из пяти — это та самая
  целевая дальность. Рельсы столько не дают (полилиния кончается на 40 м).
- **В кривой дальность падает вдвое** (70 → 40 м). Это физика, а не алгоритм:
  лидар светит в наружную стену, внутренняя уходит из поля зрения. Отдельной
  веткой кода это не чинится — но и не мешает: место, которое не видно за
  поворотом, поезд достигнет не скоро, и к тому времени оно окажется в поле
  зрения.
- **Хуже всего p10, а не медиана.** У `roundT_doubleT` в кривой p10 = 0 м:
  каждый десятый кадр не видит обеих стен вовсе. Для решения о безопасности
  важен худший случай, а не типичный.
- **`doubleT_platform` — 50 м против 95 у остальных**: у платформы с одной
  стороны вместо стены её край, геометрия другая.
- **`doubleT_obstacle` — 0 м, это артефакт замера**, а не свойство данных.
  Точки там есть (2434 на 40-60 м), но карта бэга битая (колея 3581 мм), ось
  пути считается нулевой, и окно поиска промахивается: путь там смещён до
  X = +6.8 м.

### «Стен не видно» ≠ «там свободно»

Главная ловушка задачи. Замер обрывает дальность на первом бине без стен, но
дальше точки обычно есть СНОВА. `roundT_doubleT` f60, полоса стен по бинам:

```
 80- 90 м: 145 точек
 90-100 м:  21 точка     <- провал
100-110 м: 144 точки     <- стены вернулись
110-120 м: 150 точек
130-140 м:  32 точки
```

Лучи лидара расходятся веером, и на дальности между кольцами появляются дыры;
отражение под скользящим углом слабеет. Провал — свойство сенсора, а не конец
тоннеля.

Поэтому отсутствие точек значит **«не наблюдается»**, а не «пусто». Для
обнаружения препятствий подмена одного другим — худший возможный отказ:
препятствие, которое лидар не добил по дальности, выглядело бы как свободный
путь. Правильная выдача — «габарит подтверждён до N м, дальше данных
недостаточно».

Косвенное подтверждение, что дальние точки — это стена поворота, а не пустота:
их медиана по X уходит +1.2 → −1.1 → −3.6 м на 80-90, 110-120 и 130-140 м, то
есть ровно туда, куда уходит путь.

### Итоговые зоны достоверности

| зона | источник | прямая | кривая |
|---|---|---|---|
| рельсы (полилиния) | измерение | 0-40 м | 0-40 м |
| стены по бинам | измерение | до 90-100 м | до 40-70 м |
| карта пути | память о проезде | весь бэг | весь бэг |
| дальше | — | «не наблюдается» | «не наблюдается» |

`zones.detect_walls` из `test/zones.py` для этого не годится как есть: там одна
гистограмма по X на **весь кадр**, на кривой она размазывается. Опора на стены
должна идти по бинам дальности, с окном вокруг оси пути.

> `test/zones.py` и `test/web_viewer.py` — внешний код (браузерный вьюер со
> своей классификацией точек по зонам), в репозиторий не входит и нашим трактом
> не импортируется. Ссылки на него здесь — для сверки решений, а не зависимость.

| squareT_platform_squareT_switch | 68 / 34 м | 35 / 30 м | 3.25 ± 0.48 м | 1/42 |
| **итого** | **60 / 30 м** | **40 / 32 м** | 3.25 ± 1.07 м | **6/215** |

Против исходных 40 м по рельсам — рост в полтора раза на прямой, и главное:
**p10 поднялся с 0 до 30 м**, то есть худший кадр перестал быть слепым.

Потолок метода (`eval_wall_range.py`: 90-100 м на прямой) взят не полностью —
ведение останавливается раньше, чем кончаются точки. Это честный запас на
следующий заход, а не провал: reach считает только ПОДТВЕРЖДЁННЫЕ бины.

#### Что оказалось не так, как ожидалось

**Стена — не одна линия, а дуга по высоте.** Главная находка. Замер
`roundT_doubleT` f60, вынос кромки по слоям 0.25 м:

```
z -1.50: 1.3 м     z +0.50: 2.7 м (максимум)     z +2.75: 1.3 м
```

Полоса высот −1…+2 м (как в `eval_wall_range.py`) смешивает весь этот разброс
в один перцентиль, и он гуляет на метр между соседними бинами. Из-за этого
первая версия теряла стену уже на 30 м. Поэтому стена ведётся **по слоям 0.5 м
отдельно**, а границей габарита становится худший слой в пределах высоты
поезда: поезд упрётся именно туда, где тоннель уже всего.

**Верх габарита важен не меньше низа.** Слой z+2.5 в
`squareT_platform_squareT_switch` — это дуга потолка, она заходит внутрь до
1.3 м. Пока он попадал в габарит, худший слой давал коридор ±1.25 м вместо
±1.8 м, то есть поезд «не проходил» в собственном тоннеле. Высота габарита
отсчитывается от **измеренного в кадре пола** (лидар стоит на 1.65-1.73 м над
головками — замер по трём бэгам), а не от нуля лидара.

**Низ тоже.** На 0.35 м над полом вдоль пути идут лоток и плечо балласта, они
дают «стену» в 0.69 м от оси. Поиск начинается с 0.6 м, где профиль уже
чистый (1.41 м).

**Брать надо внутреннюю кромку, а не медиану стены.** Габарит ограничивает
ближайшая помеха, а не плоскость за ней. `squareT_..._switch` f100 справа:
p10 держится 1.50-1.67 м по всем бинам, а медиана скачет 1.53 → 2.93 → 3.34,
потому что за стеной открывается ниша. Медиана дала бы «свободно до +3.3 м»
там, где на +1.6 м уже конструкция.

**Окно нельзя центрировать по предыдущему бину.** Если центр окна брать по
ответу предыдущего бина, ответ становится центром следующего, и на стене без
резкой кромки окно храповиком сползает внутрь (замерено −2.16 → −1.68 за пять
бинов), после чего настоящая стена выходит за окно. Предсказание строится по
медиане последних 5 принятых бинов плюс ограниченный наклон.

#### Защита от второго пути работает

Ради чего всё и затевалось. Замер пиков по X в полосе высот:

| бэг, кадр | ближняя зона | на дальности |
|---|---|---|
| doubleT_platform f120 | −1.7 м | 30-40 м: **−5.7 м** (соседний объём) |
| squareT_..._switch f100 | −2.1 м | 40-50 м: **−7.5 м** (появился скачком) |

Самый сильный пик (так делает `zones.detect_walls`) увёл бы границу габарита
на 4-5 м наружу. Ведение с проверкой непрерывности не берёт эти пики ни разу.

Критерий срыва пришлось переопределить: сначала им была ширина > 5 м, и она
давала 17 срывов из 215 — но все на `roundT_doubleT`, который **с кадра ~150
реально въезжает в двухпутный участок** (правая стена честно уходит с +2.5 на
+5.5 м). Широкий коридор там не ошибка. Правильный признак — **разрыв**: своя
стена между соседними бинами не прыгает, чужая появляется скачком. По разрыву
> 1 м срывов 6 из 215 (2.8%).

#### Препятствия в габарите (`obstacles_in_gauge`)

Проверено на `doubleT_obstacle` — бэг с двумя людьми, где человек A на ~55 м
ходит поперёк габарита. Детектор находит его в **21 кадре из 21**, и
координата повторяет замеренную траекторию:

| кадр | 0 | 20 | 40 | 70 | 90 | 130 | 190 |
|---|---|---|---|---|---|---|---|
| найдено x | +0.26 | −1.20 | −1.83 | −0.09 | +0.90 | +0.75 | +0.82 |
| эталон x | +0.21 | ≈−1.2 | ≈−1.8 | −0.09 | +0.95 | +0.79 | +0.79 |

Ширина 0.5-0.8 м, высота 1.1-1.4 м во всех кадрах — профиль человека.

Три вещи, без которых это не работало:

1. **Считать точки в габарите бесполезно.** В каждом бине есть ровный фон от
   пола, лотка и дальней стены (~30 точек на ячейку 0.25 м по всей ширине).
   Человек виден как локальный ИЗБЫТОК над фоном, а не как факт наличия точек.
   Фон берётся 40-м перцентилем, не медианой: сам объект входит в выборку и
   завышает её (f190 — медиана 20 при фоне 2-6 в соседних окнах).
2. **Окна должны перекрываться.** При шаге, равном длине окна, человек на
   стыке делится пополам и не набирает порог — терялся в 5 кадрах из 9.
3. **Высота объекта — не max(Z) колонки.** Над человеком в той же ячейке
   лежат точки свода, и высота у всех находок подряд получалась 3.70 м, то
   есть признак «человек ниже 1.5 м, стена до свода» не работал вовсе. Берётся
   верх сплошной снизу части колонки, разрыв ищется по гистограмме.

Бины со статусом `hole` в поиске препятствий **не пропускаются**: в
`doubleT_obstacle` человек попадает ровно в такой бин, и при пропуске
единственное настоящее препятствие набора исчезало. Габарит там держится
клампом ±1.7 м, а находка помечается `confirmed=False`.

#### Ограничения, которые надо знать

- **`doubleT_obstacle` — зал 7.5 м, а не тоннель.** Карта бэга битая (6 узлов,
  траектория 11 м: поезд стоит, одометрии не из чего строиться), поэтому оси
  пути нет и габарит центрируется на лидаре, а не на пути. Перестроение карты
  через `track_map.py --polyline` не помогает — проблема в одометрии, а не в
  детекции нитей. CLI печатает об этом предупреждение.
- **Ширина коридора на двухпутном участке — не габарит.** Стены там дальше
  габарита, и границу задаёт кламп ±1.7 м. Тоже печатается предупреждением.
- **Флаг «в габарите» считается по ближнему краю объекта.** Человек на
  x = −1.8 с краем до −1.34 помечается «в габарите», потому что край внутри.
  Для безопасности это правильная сторона ошибки.

#### Нужна ли здесь нейросеть

По-прежнему нет, и теперь это подтверждено работой: всё, что чинилось выше, —
геометрия и статистика, объяснимые на защите. Блокер остаётся в данных (на
75-100 м в кадре 314 точек против 181 тыс. вблизи), разметки на стены нет, и
сеть его не снимает.

Где сеть уместна: искать **дальние рельсы** на облаке, используя карту пути
как бесплатную разметку (`map_to_frame` + `rail_dz` дают x/y/z меток). Это
улучшение детекции, а не путь к 100 м.

#### Что делать дальше

1. **Добрать дальность с 60 до 90 м.** Потолок по точкам есть
   (`eval_wall_range.py`), ведение до него не доходит. Смотреть, на чём именно
   останавливается: не хватает точек в слое или окно уходит.
2. **Сшивка коридора между кадрами.** Сейчас каждый кадр считается с нуля.
   Одометрия есть, и накопление подтверждённых бинов по нескольким кадрам
   должно поднять именно p10 — худший кадр перестанет быть худшим.
3. **Починить одометрию `doubleT_obstacle`** — это единственный бэг с реальным
   препятствием, и он же единственный без карты.

## Детектор препятствий: блоки (`guard/`)

Новый тракт, пишется с нуля по блокам. Цель — **не видеть препятствий там,
где их нет**, и определять препятствия до 110 м. Сделаны все блоки: ось
прямого пути (1), её ведение стеной вдаль на кривых (1б), коридор по стенам
(2), штатные конструкции внутри коридора (2б) и препятствия из остатка
необъяснённого (3). Отдельно — многопутность: все ветки пути в кадре
(`guard/multitrack.py`).

Блок 1 сознательно даёт только прямую ось (жёсткий предел наклона);
кривые достаются блоку 1б, который ведёт ось стеной, и коридор блока 2
строится уже от неё.

```bash
python -m guard.run for_hackathon/doubleT_platform --frame 100
python -m guard.run for_hackathon/doubleT_platform --sweep 10 [--accum-pts]
python -m guard.obstacles for_hackathon/doubleT_obstacle --sweep 10
python guard/eval_axis_far.py --step 5     # замер оси вдаль против карты
```

| `guard/axis_wall.py` | Блок 1б: ось вдаль — её ведёт стена (повороты) |

### Блок 1: ось прямого пути

Два замера по данным задали конструкцию — оба против интуиции.

**Головка рельса не на 0.25 м над «полом».** Пол как 2-й перцентиль Z под
поездом — это низ балласта и лотка, а не уровень катания. Гистограмма высот
в срезе 6-12 м (`doubleT_platform` f100) двугорбая:

```
h 0.00-0.10:  994 точки   <- низ (балласт)
h 0.10-0.30:   92 точки   <- провал
h 0.30-0.45: 2054 точки   <- верх пути (головки)
```

Полоса поиска 0.10-0.40 попадала в провал. Взято 0.28-0.50.

**Пару нельзя выбирать по близости к номиналу колеи.** В срезе 8-12 м
находится до 36 пар пиков, проходящих допуск: соседний путь и кромка
платформы дают такие же. Разделяет **непрерывность**: своя пара повторяется
во всех срезах подряд (−0.85/+0.60 держится с 4 до 29 м во всех проверенных
кадрах), чужие рвутся. Поэтому строятся ветки по срезам, и берётся самая
длинная из ближних к лидару.

**Ближний срез исключён.** На 5 м в полосу высот головки лезут шпальная
решётка и крепёж: центр там +0.37/−0.37 против −0.10 на всех остальных
срезах, и один этот срез разворачивал наклон оси до 0.018 (2 м на 110 м).
Зона измерения начинается с 7 м.

Уточнения связывания (замеры этой сессии). Внутри среза пары привязываются
к веткам жадно по паре (свежесть ветки, расстояние), а не в порядке
перебора: дальняя пара, идущая первой в списке, перехватывала живую ветку
раньше ближней (f30 doubleT_platform). Длиной ветки считается самый длинный
**непрерывный прогон** внутри неё, и ветка без прогона ≥ `MIN_BRANCH`
срезов отбраковывается: чужая рваная ветка, оставаясь единственной, угоняла
ось (f170 roundT_pressureGate, +0.77 м от истины), а своя ветка с дырой от
колец лидара (f30/f40 doubleT_platform) при этом выживает. Плато-дубли
пиков (равные счётчики соседних бинов) сливаются в один с центроидом по
всему плато. Последний срез обрезан границей зоны (`NEAR_FWD`), чтобы не
лезть за 30 м. Ветка, отвергнутая как чужая (`OWN_LAT`), не даёт ни оси,
ни колеи (`gauge=None`).

Запасной уровень пола при нехватке точек — `FLOOR_FALLBACK = -2.0` в
`geom.py`: это уровень ПОЛА (лидар на 1.65-1.73 м над головками, пол ещё на
0.30-0.45 м ниже), а прежнее −1.65 было высотой головок и смещало полосу
поиска выше рельсов — ось терялась.

Результат на `doubleT_platform` (69 кадров): ось измерена на 67, `lat0` med
+0.011 м при std 0.056, разброс оси на 110 м — std **0.11 м** при
полугабарите 1.7 м.

Колея по осям пиков выходит 1405 ± 53 мм против номинала 1520: пик садится
ближе к внутренней грани, а не на ось головки. Для оси пути это неважно —
нужен центр пары, и он верен. Не подгонялось.

### Блок 2: стены и коридор

**Граница — внутренняя кромка, а не медиана стены.** Замер `doubleT_platform`
f100: слева p10 держится 1.69-1.79 м на всех бинах, а медиана скачет
1.79 → 5.34 м, потому что за стеной открывается второй путь. Медиана дала бы
«свободно до 5 м» там, где на 1.8 м уже конструкция. Берётся 10-й перцентиль.

**Стена ведётся по слоям высоты 0.5 м.** Тоннель круглый, вынос кромки
зависит от высоты; один перцентиль на всю полосу смешивает дугу стены.
Границей габарита становится худший (ближайший к оси) слой в пределах высоты
поезда — поезд упрётся именно туда.

**Непрерывность вместо самого сильного пика.** Слева на 50-90 м самый плотный
отклик приходит с 5.0-5.4 м (соседний объём), своя стена там даёт единицы
точек. Поэтому в каждом бине стена ищется в окне ±0.5 м вокруг предсказания
по последним принятым бинам, а не по всему профилю.

**Пустой бин — «не наблюдается», а не «свободно».** Коридор в дыре ведётся
предсказанием, но дальность подтверждения на ней не растёт. На f100 дыра
62-72 м пережита, и после неё стена вернулась — провал между кольцами лидара
концом тоннеля не является.

Результат (шесть бэгов, шаг 10 кадров, с агрегацией точек прошлых кадров
`--accum-pts`):

| бэг | ось изм. | подтверждено med / p10 / min |
|---|---|---|
| doubleT_platform | 35/35 | 90 / 70 / 70 м |
| doubleT_obstacle | 21/21 | **115 / 115 / 115 м** |
| roundT_doubleT | 26/26 | 110 / 62 / 50 м |
| roundT_pressureGate_roundT | 27/27 | 95 / 64 / 40 м |
| squareT_platform_squareT_switch | 84/88 | 100 / 88 / 15 м |
| roundT_squareT_pressureGate_squareT | 35/55 | 95 / 40 / 35 м |

На кривых бэгах коридор ведётся от ведомой стеной оси: блок 1б подаётся в
блок 2 (`walls.trace(far=...)`), и коридор повторяет изгиб пути.

#### Что добавлено в блок 2 за сессию

- **Одностороннее ведение.** Измеренная одна сторона подтверждает бин
  (статус `gauge`), вторая ведётся клампом габарита; поле `lead` помечает
  ведущую сторону (`left/right/both/gauge`). На двухпутке, где правая стена
  честно уходит, ведущей становится правая (замерено) — раньше такой бин
  ронялся в дыру целиком.
- **Оценка кромки — гибрид Harrell-Davis / percentile** (`n >= 8`, зажим к
  соседним порядковым статистикам): HD снижает шум кромки на 10-17%, но на
  крошечном n крайние точки получают слишком большой вес.
- **Кольцевая модель Pandar128.** По гистограмме вертикальных углов кадра
  восстанавливаются кольца, и бин-дыра, куда принципиально не попадает
  кольцо пола, помечается `uncovered`: «не покрыт сенсором» отличается от
  «покрыт, но пуст».
- **`reach_bridged`** рядом с консервативным `reach`: мост через ≤ 2 дыры
  подряд, если после дыры стена согласованно вернулась (кромка в пределах
  `GATE` от предсказания цепочки). Сам `reach` не меняется.
- **Окно поиска зажато в `MIN_OFF`**: иначе оно строилось от 0.7 м от оси —
  внутри габарита — и кабель на 0.7-1.2 м мог стать «стеной».
- **Поздняя затравка слоя**: слой, не давший кромки в ближней зоне,
  затравляется из точек полного окна на первом бине, где они есть.
- **`reach` считается от первого наблюдаемого бина**, а не от нулевого:
  бин 0-5 м под поездом — слепое пятно сенсора, и пустым бином под собой
  нельзя обнулять подтверждённую дальность впереди.
- **`trace(..., extra=)`** принимает точки прошлых кадров, перенесённые
  полным SE(2) из `trajectory.npz` (CLI-флаг `--accum-pts`): агрегат идёт
  только в оценку кромок стен (стены неподвижны, точки ложатся друг на
  друга), в конструкции и препятствия — нет: движущийся объект размазывается
  одометрией в полосу.

**Срывов на соседний путь нет.** После клампа габаритом ±1.7 м скачок
полуширины коридора между соседними бинами: med 0.011 м, p95 0.362 м,
max 0.577 м, доля скачков > 1 м — **0.00%** (`doubleT_platform`, 69 кадров).
Широкая стена на открытом участке коридору не вредит: там его ограничивает
габарит, и это верно.

На `doubleT_obstacle` стены стоят на −3.2/+5.3 м (зал 7.5 м, не тоннель),
коридор держится габаритом, и человек на 55 м границу стены не сместил —
он честно остался для блока 3.

| зелёный | габарит подтверждён измерением стен в этом бине |
| жёлтый | бин ведётся предсказанием: «не наблюдается», НЕ «свободно» |
| серый | найденные стены — видно, за что зацепилось ведение |
| синий | ось пути |

Флаги: `--guard-no-walls` убирает серые стены, `--guard-quiet` — строку в
консоли.

**2. Строка на кадр в консоли** — работает без окна и по SSH:



Полоса — статус по дальности (5 м на символ): зелёный подтверждён, жёлтый

f100 — первая версия показывала четыре разрыва там, где коридор непрерывен.

### Межкадровое накопление (`guard/accum.py`)

Каждый кадр `trace` считает коридор с нуля, и подтверждённая дальность
скачет: соседние кадры дают 115 и 85 м на одном участке пути. Причина не в
тоннеле, а в дырах между кольцами лидара — бин, пустой сейчас, был измерен
кадр назад, когда поезд стоял на метр позади.

Накапливаются **не точки, а результаты**. Копить точки (как
`accumulate_with_speed`) для габарита неверно: движущийся объект
размазывается в полосу вдоль пути, а он-то и нужен. Бин же несёт вывод
«стена здесь», и у неподвижной стены выводы разных кадров совпадают.

Позы берутся из `trajectory.npz` (`odometry.py`) — кэш есть на всех шести
бэгах, считать ничего не надо. Замер сноса на `doubleT_platform`: за 4 кадра
вбок ≤ 0.04 м, поворот ≤ 0.06°, то есть на порядок меньше бина 5 м — на
прямой достаточно сдвига вдоль пути. Голосование медианой, бин подтверждён
от двух голосов. На кривых кадр, съехавший вбок больше чем на полбина или
повёрнутый сильнее `MAX_TURN` (порог выведен из геометрии бина: arctan(2.5 м
/ 115 м) ≈ 1.2°), в голосовании не участвует. Ближняя зона, где голосов
физически не набрать, считается от БЛИЖАЙШЕГО голосующего кадра, а не от
старейшего: иначе при большом `--sweep` бины до 50 м проходили с одним
голосом. Голоса раскладываются в ближайший центр бина (round, не floor), и
требуемое число голосов применяется к реально голосующим кадрам.

```bash
python -m guard.run for_hackathon/doubleT_platform --sweep 5 --accum
python visualize_bag.py for_hackathon/doubleT_platform --guard --guard-accum
```

#### Совместимость с `--accumulate-speed`

Конфликта нет: флаги можно ставить вместе.

```bash
python visualize_bag.py for_hackathon/roundT_pressureGate_roundT \
    --accumulate-speed 5 --max-y-distance 50 --guard --guard-accum
```

`--accumulate-speed` обогащает облако ТОЧЕК для показа, `--guard` считает
габарит **всегда по чистому кадру**. Так сделано намеренно: склейка по
скорости размазывает головки рельсов на повороте (замер
`roundT_pressureGate_roundT` f140: ось скачет −0.48 → +0.12 м, колея
1398 → 1322 мм), а движущийся объект растягивает в полосу вдоль пути — то
есть ровно то, что детектор препятствий должен увидеть как объект.
Накоплением габарита занимается `--guard-accum`, и оно копит результаты, а
не точки.

`--max-y-distance` на габарит тоже не влияет: он ограничивает показ и
детекцию рельсов, а коридор всегда ведётся до 115 м.

Все кадры шести бэгов, подтверждённая дальность med / p10 / min:

| бэг | по кадру | с накоплением |
|---|---|---|
| doubleT_platform | 50 / 35 / **0** | 60 / 35 / **35** |
| doubleT_obstacle | 105 / 100 / 90 | **110 / 110 / 105** |
| roundT_doubleT | 70 / 0 / 0 | 75 / **30** / 0 |
| roundT_pressureGate_roundT | 55 / 35 / 30 | 60 / 35 / 30 |
| squareT_platform_squareT_switch | 35 / 30 / **0** | 35 / 35 / **10** |
| roundT_squareT_pressureGate_squareT | 60 / 25 / **0** | 70 / **30** / 0 |

Главное — **min перестал быть нулём** на трёх бэгах: худший кадр больше не
слепой. Дрожание полуширины между кадрами упало до p95 0.099 м
(`doubleT_platform`), на `doubleT_obstacle` — до 0.035 м.

#### Две ошибки, найденные замером

**Знак сдвига.** `_shift_along_path` возвращала положение старого кадра
относительно нового (оно отрицательное), а `update` трактовал это как
пройденный путь и вычитал. Бины сдвигались назад вместо вперёд, и голоса
ложились мимо своих бинов. Ловится проверкой: соседние кадры
`doubleT_platform` должны давать около +1.0 м. Первые замеры накопления были
сделаны на этой ошибке и в истории правок неверны.

**`reach` прыгал через дыру.** Дальность считалась по последнему измеренному
бину, а не по непрерывному участку: на `doubleT_platform` 63 кадра из 69
заявляли reach за дырой (кадр 20: 105 м при 7 неподтверждённых бинах внутри).
Для задачи «не пропустить препятствие» это неверная сторона ошибки — выдача
утверждала знание о том, что лежит за неизвестным участком. Теперь `reach`
обрывается на первой дыре, последний измеренный бин остался в `reach_last`.

**Ближние бины голосов набрать не могут** — прошлые кадры стояли позади, и
их бины сюда не дотягиваются. Зона под поездом измерена надёжнее всего,
поэтому там хватает голоса текущего кадра.

### Блок 2б: конструкции внутри коридора (`guard/structures.py`)

Блок 2 ищет внешнюю границу и возвращает одно число на бин; всё, что внутри
коридора, для него не существует. А там стоят штатные конструкции: замер
`doubleT_obstacle` f40 — в бине 30-35 м внутри габарита 235 точек, при том
что граница стены найдена на +5.51 м (зал, а не тоннель). Отдать их блоку 3
как есть — значит объявить препятствием нишу и портал.

Порядок работы поэтому такой: **сначала объясняем, потом тревожим**.
Препятствие — это не «что-то есть», а «не удалось отнести ни к чему
штатному».

Признак замерен, а не подобран под ответ:

```
структура d ≈ +1.5, h 2.0-3.5: бины 30,35,40,45,50,65,70,75 м — 8 из 12
человек   d ≈ −1.47, h 0.1-1.0: бин 55-60 м, соседние ПУСТЫЕ
```

Конструкция тоннеля идёт **вдоль** пути (ниша, кронштейн, откос — тоннель
сам протяжённый), препятствие локально. Плюс второй тип, найденный по
остатку: **вертикальная колонна до свода** в одном бине (пилон, портал) —
сплошные ячейки от пола до 3+ м, тогда как человек обрывается на 1-1.8 м.

Результат объяснения (`doubleT_obstacle` f40, точки в габарите
всего / остаток):

| бин | всего | остаток |
|---|---|---|
| 30-35 м | 235 | 19 |
| 45-50 м | 196 | 12 |
| 75-80 м | 133 | 6 |
| **55-60 м (человек)** | **78** | **66** |

У штатного остаётся 6-19 точек, у человека 66 — разрыв вчетверо, поэтому
порог блока 3 не требует подгонки.

### Блок 3: препятствия в габарите (`guard/obstacles.py`)

Блок больше не «откачен» — реализован заново по принципу объяснения:
препятствие — избыток над фоном в ОСТАТКЕ точек после того, как блоки 2 и
2б объяснили стены и штатные конструкции. Метод поиска — проверенный
`obstacles_in_gauge` (см. «Препятствия в габарите» выше: избыток над фоном
40-го перцентиля, перекрывающиеся окна, высота колонки без свода); поверх
него пять правил-объяснений кластеров остатка — колонна до свода (пилон,
портал), рябь в полосе у измеренной кромки стены, «пыль» (точки размазаны
по дальности > 1 м), «не стоит на полотне» (низ колонны выше 0.5 м),
фрагмент уже объяснённой конструкции. Все правила про геометрию, а не про
конкретный объект: прежний блок 3 был откачен именно за описание человека
порогами.

Ось отсчёта габарита — ведомая ось коридора; в зале, где обе стены дальше
габарита, а ось измерена рельсами, — прямая ось блока 1: ведение стеной с
постоянным отступом там теряет смысл (замер: ось на 55 м гуляла
−0.4..−1.7 м между кадрами при стоящем поезде).

Итог: человек на doubleT_obstacle найден в **21 кадре из 21**, ложных
находок на чистых бэгах ~0. CLI: `python -m guard.obstacles
for_hackathon/doubleT_obstacle --sweep 10`. В `run.analyze` блок 3 включён
по умолчанию (результат — `wall['obstacles']`, 8-28 мс на кадр).

### Многопутность и стрелки (`guard/multitrack.py`)

Блок 1 сознательно выбирает одну ветку — ближнюю к лидару; на стрелке и
двухпутке в кадре ДВА пути, и этот блок находит все: широкое окно пиков
(±6 м, межосевое двухпутки ~4 м) с проверкой «рельсовости» пика по доле
точек его столбца в полосе высот головки (рельс ≥ 0.66, стена/бордюр ≤
0.16), слияние дублей по центру (оси двух разных путей ближе полколеи быть
не могут), отброс перекрёстных пар-фантомов (центр ровно посередине двух
настоящих), и пометка `blocked`, если между своим путём и веткой стоит
стена кадра: соседний путь сквозь проём — не маршрут.

Находит перевод на squareT_platform_squareT_switch (f812-824) и двухпутку
roundT_doubleT (f150+). Коридор ветки считается штатным `walls.trace` с
осью ветки (`branch_corridor`). Выбором «нашей» ветки блок не занимается:
до перевода стрелки она из облака не определить. CLI: `python -m
guard.multitrack <bag> [--frame N | --sweep N] [--corridors]`; в `run.py` —
флаг `--branches`.

### Блок 1б: ось вдаль ведёт стена (`guard/axis_wall.py`)

Блок 1 продолжает ось **прямой**, потому что рельсов дальше 50-75 м физически
нет. На кривой это промах: замер против карты на
`roundT_pressureGate_roundT`, **только кривые кадры** (31 кадр, ось от прямой
против оси от стены):

| d | блок 1 med / p95 / max | блок 1б med / p95 / max |
|---|---|---|
| 30 м | 0.71 / 1.15 / 1.38 | **0.44** / 1.15 / 1.38 |
| 50 м | 2.33 / 2.90 / 2.91 | **0.34 / 0.49 / 0.65** |
| 70 м | 4.56 / 5.15 / 5.19 | **0.33 / 1.40 / 1.48** |
| 90 м | 7.37 / 7.73 / 7.78 | **0.54 / 0.94 / 0.98** |

Полугабарит 1.7 м: прямая ось выходит за габарит уже на 50 м и на 70 м врёт
**втрое** больше него — габаритом накрывается не тот кусок тоннеля. Ось от
стены на 70 м врёт на 0.33 м, в пять раз меньше полугабарита.

На прямых кадрах того же бэга метрики не тронуты (0.03 / 0.07 / 0.12 против
0.03 / 0.05 / 0.12 на 30/50/70 м), на `doubleT_platform` ведение включается
в 5% кадров, на `roundT_pressureGate_roundT` — в 74%.

#### Идея: стена ПЕРЕДАЁТ ось вдаль

Стена параллельна пути и на дальности плотнее рельсов, поэтому знание «где
стена» переносится в «где путь». Ось не заменяется стеной и не выбрасывается:
в ближней зоне её по-прежнему ведут рельсы, а стена подхватывает её там, где
рельсы кончились.

**Ведение включается по бинам, а не на весь кадр.** Ближние бины прямая
описывает точнее, поэтому стена берёт только тот участок, где прямая
перестала объяснять сцену, и отдаёт обратно, когда снова объясняет
(`RESID_RUN = 2` бина на включение, `BACK_RUN = 3` на возврат). Медиана
перехода — 32-45 м по бэгам.

#### Четыре замера задали конструкцию

**Отступ «стена -> путь» постоянен, но его надо ИЗМЕРЯТЬ.** Кромка стены
против истинного пути (карта), `roundT_pressureGate_roundT`, прямые кадры,
слева: −1.69 / −1.70 / −1.71 / −1.71 / −1.72 / −1.71 / −1.69 м на
10/20/30/40/50/60/70 м (50 кадров, std 0.14-0.18). Медиана не сдвигается
больше чем на 3 см на плече 60 м. **Но** на `doubleT_platform` тот же отступ
−1.44…−1.57 м: тоннели разной ширины, и константа сломала бы один из бэгов.
Поэтому отступ измеряется в ближней зоне **каждого кадра**.

**Привязка окна к нулю лидара в кривой умирает между 40 и 50 м.** Тот же
замер, кривые кадры, слева: −2.15 / −2.04 / −2.07 / −2.05 м на 10-40 м, на
50 м std подскакивает до **2.06**, а на 60 м медиана **переворачивается** в
+2.75. Знак сменился: путь ушёл в дугу левее окна поиска, и кромка оказалась
по другую сторону пути — отступ считался бы от стены, стоящей не с той
стороны. Поэтому окно едет за осью бин за бином, а сторона наследуется из
бина, где была известна.

**Ведение стеной не должно заменять прямую ось.** На `doubleT_platform`
прямая ось лучше: max 0.19 / 0.26 / 0.28 / 0.29 м на 30/50/70/90 м против
1.01 / 0.99 / 3.63 / 0.46 у сплошного ведения стеной. У прямой оси 50
наблюдений рельсов на коротком плече, у кромки — 4 точки в слое.

**Переключать надо по измерению, а не по дальности.** Порог «с 40 м» был бы
подгонкой. Прямая ось предполагает постоянный отступ до стены; если
измеренный отступ от неё уезжает, прямая больше не верна. С тех пор
критерий пересмотрен: отступ законно меняется там, где тоннель сходится или
расширяется (pressure gate, выход на двухпутку), и невязка растёт без
всякого поворота. Первичным стал признак ФОРМЫ — стрелка кромки (вторая
разность) с аналитическим z-тестом значимости: |sag| > 2·sigma_sag, где
sigma_sag выводится из rms линии стены через псевдообратную дизайн-матрицу
параболы (константа SAG_TOL удалена как подогнанная). Невязка оставлена
вторым триггером: переходы, где стена сходится почти прямой (стрелка ~0),
а путь уходит (f185 roundT_doubleT), ловит только она. Сама невязка
замерялась так:

| d | прямые кадры | кривые кадры |
|---|---|---|
| 30 м | med +0.00, p95 0.39 | med **+0.82**, p95 0.99 |
| 40 м | med +0.02, p95 0.37 | med **+1.46**, p95 1.82 |
| 50 м | med +0.04, p95 0.41 | med **+2.06**, p95 2.73 |

На прямых — ноль с точностью до сантиметров, в кривой растёт монотонно.
Порог 0.60 м лежит в разрыве между p95 прямых (0.41) и медианой кривых
(0.82).

#### Что оказалось не так, как ожидалось

**Окно ±0.60 м не впускало сигнал поворота, и ведение не включалось НИ РАЗУ
на 251 кадре.** Первая версия искала кромку в окне вокруг ожидаемого отступа.
Замер f240: кромка справа широким окном идёт 2.37 / 2.76 / 3.33 / 4.13 м на
30/35/40/45 м при ожидаемом отступе 1.66 — то есть стена уезжает из окна уже
на первом бине после затравки, бин становится `hole`, и ведение умирает на
35 м. Невязка не может сработать, если окно её не впускает. Окно расширено до
1.60 м и центрируется по **последней принятой кромке**.

**Возврат на прямую нельзя мерить той же невязкой.** После перехода окно едет
за стеной, поэтому невязка падает сама собой, и возврат срабатывал на самом
повороте: переключений 15 вместо 39, медиана перехода 68 м вместо 38,
выигрыш в кривой исчезал. Кромка приводится к прямой оси, а не к предсказанию.

**Порог разрыва проверен по истинной оси.** Кромка от пути из карты, 1736
переходов на двух бэгах: своя стена med 0.10, p95 0.50-0.66, max 1.04 м;
чужой объём med **3.50**, p95 3.78 м. `JUMP_LIM = 0.70` выше p95 своей стены
и втрое ниже медианы чужой.

**Одометрия как признак поворота НЕ годится** — проверено и отвергнуто.
Кривизна в окне 20 кадров даёт на `roundT_pressureGate_roundT` 0.02 °/10 м,
то есть **меньше**, чем на прямом `doubleT_platform` (0.02) и стрелочном
(0.06). Причина: требование «все кадры окна валидны» выбрасывает ровно те
окна, где поезд поворачивает — на кривой одометрия и слабеет. Признак
недоступен там, где он нужен.

**Зал отделяется по разбросу отступа внутри затравки, а не по сдвигу
коридора.** В `doubleT_obstacle` (зал 7.5 м) правый отступ выходил 5.87 м —
бин затравки попал на дальнюю стену. Замер std кромки по бинам затравки:

| бэг | слева | справа |
|---|---|---|
| doubleT_platform | 0.03 | 0.01 |
| roundT_pressureGate_roundT | 0.17 | 0.09 |
| roundT_doubleT | 0.17 | 0.34 |
| **doubleT_obstacle** | 0.12 | **1.85** |

`OFF_MAX_STD = 0.60` лежит между p90 тоннеля (0.32) и залом (2.03). После
этого на `doubleT_obstacle` отступ с двух сторон не измеряется ни в одном
кадре (было 100%), и ось ведётся по одной честной левой стене.

## Карта пути: одометрия + сшивка (`odometry.py`, `track_map.py`)

Основной рабочий тракт разметки пути. Заменяет `rail_mapper.py`.

### Постановка

Детектировать рельсы на 100+ м напрямую нельзя — их там физически не видно
(замер ниже). Но поезд едет по рельсам, поэтому **траектория лидара и есть
осевая линия пути**, измеренная точно. Если знать позу каждого кадра, ближние
надёжные наблюдения колеи можно сшить в единую карту на весь проезд — включая
участки, где с текущего кадра рельсы уже не различить.

### Запуск

```bash
# 1. Одометрия -> trajectory.npz
python odometry.py for_hackathon/roundT_squareT_pressureGate_squareT --save

# 2. Карта пути -> track_map.npz (шаг 1 запустится сам, если нет кэша)
python track_map.py for_hackathon/roundT_squareT_pressureGate_squareT

# 3. Просмотр: зелёные линии рельсов из карты
python visualize_bag.py for_hackathon/roundT_squareT_pressureGate_squareT \
    --track-map --max-y-distance 150
```

Полезные флаги: `--start N` (кадр), `--track-map-radius 0.3` (шире окно маски),
`--accumulate-speed 5`, `--fps 3`.

### SE(2)-одометрия (`odometry.py`)

Матчинг отражателей между кадрами даёт пары соответствующих точек; по ним
методом Кабша считается полное плоское преобразование `(dx, dy, dθ)`, а не
только сдвиг вдоль пути. Выбросы отбрасываются итеративно по остатку —
одна ошибочная пара разворачивает решение.

| Bag | Путь | Курс | Прямых оценок |
|---|---|---|---|
| doubleT_platform | 215 м | −0.7° | 332/344 |
| roundT_pressureGate_roundT | 400 м | −8.4° | 165/267 |
| roundT_squareT_pressureGate_squareT | 695 м | +41.6° | 308/544 |

Косвенная проверка корректности: оценённые радиусы кривизны — 288–437 м (p5),
что совпадает с реальными радиусами метро (300–600 м), хотя нигде в алгоритм
не заложено.

#### Стеновой фолбэк для длинных дыр

Отражатели есть не на каждом кадре, и дыра заполняется интерполяцией — но
курс внутри дыры линеен только на прямой. Дыры длиннее 20 м пути
(`HOLE_MIN_M`) дополнительно перезаполняются по стенам: по профилям
**внешней** кромки стен пары кадров Гаусс-Ньютоном оцениваются dx/dθ (dy
стены не видят — остаётся интерполированным; по одной стене поворот
вырожден, нужны обе).

Почему внешняя кромка — замер, а не вкус: оценка по ВНУТРЕННЕЙ кромке
систематически смещена — кромка есть нижний квантиль выноса и садится
внутрь тоннеля тем сильнее, чем меньше точек (та же `Q_RANK`-проблема
`guard/walls.py`). Биас мал покадрово (dx −0.004…−0.010 м), но
интегрируется: −0.0042 м/кадр это −0.29 м на 100 м пути — именно этот
дрейф стал причиной отката прежней версии фолбэка. На внешней кромке
(зеркальный квантиль; её задаёт сама стена, навесное её не сдвигает) биас
исчезает: ±0.003 м / ±0.007° против отражателей.

Дыра f192-215 `roundT_doubleT` (33 м) закрыта: излом курса карты на ней
4.76° → **2.97°**. На прямых бэгах дыр такой длины нет (doubleT_platform
максимум 13 м), и траектория там не меняется — интерполяция на прямой
точнее стен.

### Сшивка карты (`track_map.py`)

С каждого кадра берутся **только сырые пары пиков** из ближней зоны (15 м),
без промежуточного фита в линию — фит теряет информацию о каждом срезе.
Пары переводятся в глобальную систему полным преобразованием SE(2) и
привязываются к узлам по пройденному пути (шаг 1 м). В узле — взвешенный
lstsq с одним раундом асимметричного тримминга левых 15% остатков
(`TRIM_LEFT_Q`): соскоки на соседний путь образуют левый хвост и смещали
медиану узла (замер: bias −7.8 → +2.3 мм, RMSE 19.5 → 15.3 мм).

При 1.5 м на кадр каждый участок пути попадает в надёжную ближнюю зону
десятки раз, с разных ракурсов, поэтому робастная оценка узла (взвешенный
lstsq с триммингом) гасит промахи отдельного кадра.

| Bag | Узлов | Длина | Набл./узел | Колея |
|---|---|---|---|---|
| doubleT_platform | 214 | 215 м | 36 | 1572 ± 20 мм |
| roundT_pressureGate_roundT | 399 | 400 м | 32 | 1577 ± 9 мм |
| roundT_squareT_pressureGate_squareT | 695 | 695 м | 32 | 1565 ± 29 мм |

#### Соскоки на соседний путь (исправлено)

Второй источник кривизны карты — кратковременные «соскоки» детекции на
параллельную пару рельсов сбоку, с возвратом обратно. Их **нельзя отличить
по одному наблюдению**: колея у них правильная (1570 мм против 1577 у своих),
высота головки правильная, пары настоящие — это просто соседний путь или
ветка стрелки.

Замер на `roundT_pressureGate_roundT`: 747 наблюдений из 6434 (11.6%) с
выносом меньше −0.30 м, сгруппированы в зонах s ≈ 105, 280–320 и 380–400 м.
Гистограмма поперечного смещения асимметрична — хвост тянется влево до
−0.95 м, вправо обрывается на +0.40 м. **В 51 узле из 400 такие наблюдения
составляли больше половины и перетягивали медиану узла** — отсюда и изгибы.

Отличает их непрерывность: свой путь под поездом непрерывен (поезд по нему
едет), поэтому `lat(s)` — гладкая функция, а ветка от неё отходит.
`filter_branch` строит опорную линию медианой в скользящем окне 25 м и
итеративно (4 прохода) отбрасывает всё, что дальше 0.25 м от неё. Опора
намеренно осталась медианой: замер на `roundT_doubleT` показал, что
asym-trim опоры (правый хвост не тримуется) в зонах с параллельным путём
СПРАВА перетягивает опору на чужой путь — осевая уходила на +447 мм от
траектории поезда (s=283-317); на roundT_pG замена опоры не меняла
keep-сет вовсе. Поэтому асимметричный тримминг применяется только в
оценивателе узла (`TRIM_LEFT_Q`, см. выше).

| | lat std | lat max | колея СКО |
|---|---|---|---|
| roundT_pressureGate_roundT было | 0.176 | 0.752 | 9 мм |
| roundT_pressureGate_roundT стало | **0.120** | **0.466** | 9 мм |
| doubleT_platform было | 0.083 | 0.313 | 20 мм |
| doubleT_platform стало | **0.075** | **0.252** | **16 мм** |
| roundT_squareT... было | 0.130 | 0.514 | 28 мм |
| roundT_squareT... стало | **0.112** | **0.455** | 28 мм |

По проблемным зонам `roundT_pressureGate_roundT` (смещение осевой):

| зона | было | стало |
|---|---|---|
| s 100–120 м | −0.370 ± 0.123 | **−0.198 ± 0.082** |
| s 285–315 м | −0.443 ± 0.139 | **−0.350 ± 0.078** |
| s 380–400 м | −0.248 ± 0.303 | **+0.024 ± 0.065** |

Отсеивается 9.2% наблюдений, узлов без данных становится 14 из 401.

Порог 0.25 м выбран между собственным разбросом детекции внутри своего пути
и самым тесным соскоком (0.30 м); окно и допуск — `BRANCH_WIN` / `BRANCH_TOL`.

**Ограничение:** фильтр всегда оставляет ОДНУ ветку — ту, по которой поезд
фактически проехал. Для габарита на стрелке этого мало (нужны все ветки),
но для разметки пройденного пути это именно то, что требуется.

#### Параметризация: ближайшая поза → проекция на отрезок (исправлено)

Линия карты ломалась не из-за одометрии. Наблюдение привязывалось к
**ближайшей позе**, поэтому `s` принимал только столько значений, сколько
кадров: 267 значений на 6434 наблюдения при шаге поз 1.5 м. Узлы идут через
1 м, то есть чаще этой сетки, — соседние узлы получали один и тот же набор
наблюдений, и продольное положение узла определялось не путём, а тем, какой
кадр случайно оказался ближе.

Вторая половина проблемы — медиана бралась по глобальным X и Y по отдельности.
На повороте облако наблюдений в окне узла вытянуто вдоль пути, и покоординатная
медиана смешивает продольный разброс с поперечным.

Исправлено двумя изменениями: проекция на **отрезки** ломаной траектории
(`project_to_path`, `s` непрерывен — 6287 различных значений вместо 267) и
сборка узла в **базисе пути** (`path_frame`): вдоль пути узел стоит там, где
его ставит сетка `s`, медиана берётся только поперёк.

Замер на `roundT_pressureGate_roundT` (повороты) и `doubleT_platform`:

| | шаг узлов, med | шаг p95 | шаг max | излом med | излом max | колея СКО |
|---|---|---|---|---|---|---|
| roundT было | 0.904 | 1.532 | 5.968 | 0.71° | **103.7°** | 11 мм |
| roundT стало | **1.000** | **1.002** | **1.009** | **0.24°** | **8.2°** | **9 мм** |
| doubleT было | 0.929 | 1.611 | 7.398 | 0.64° | 160.1° | 42 мм |
| doubleT стало | **1.000** | **1.001** | **1.017** | **0.28°** | 169.8° | **20 мм** |

Шаг узлов стал ровно 1 м вместо «0.9 м с выбросами до 7.4 м». Изломов
свыше 20° на бэге с поворотами **не осталось ни одного**; у `doubleT_platform`
остаётся один — на последнем узле бэга.

Попутно: узлы больше не строятся за концом траектории. `np.interp` там
отдаёт одну и ту же точку, касательная вырождается (норма 0.018), нормаль
становится произвольной — такие узлы давали колею 13 и 737 мм. Касательная
считается по базе ±3 м, а не по соседним узлам, чтобы не ловить дрожание
одометрии на шаге 1 м.

Колея — метрика качества сшивки: если позы врут, она поплывёт. Систематическое
завышение относительно 1520 мм объясняется тем, что пик берётся по вершине
головки, а не по внутренней грани; важно, что разброс мал.

### Плоскость земли: платформа ломала детекцию

Найденная и исправленная причина срывов детекции в ближней зоне. Платформа
возвышается над путём примерно на 1.4 м и даёт больше точек, чем сам путь,
поэтому RANSAC по всей ширине облака фитил плоскость **через платформу**:
поперечный уклон `a` скакал от −0.35 до +0.42 со сменой знака, плоскость
отвергалась по порогу `|a| > 0.2`, и детекция возвращала `ground=None`.

Исправление — считать землю только в коридоре ±2.5 м вокруг лидара
(`estimate_ground_plane` с расширением коридора при неудаче):

| | было | стало |
|---|---|---|
| Отказы детекции (3 бэга) | 7/35 | **0/167** |
| Поперечный уклон | −0.35…+0.42 | ≈ 0 |

## Эксперименты и ограничения

### Докуда видно рельсы

Ключевой замер: сколько точек реально попадает на головку рельса на каждой
дальности (проверка по карте пути — известно, где рельс, и проверяется, есть
ли там точки в текущем кадре).

| Дальность | Точек в срезе 4 м | Из них у рельса | Кадров с попаданием |
|---|---|---|---|
| 25 м | ~2500 | 72–150 | 100% |
| 50 м | ~370 | 6–9 | 74–81% |
| 75 м | ~130 | **0** | 11–18% |
| 100 м | ~50–80 | **0** | 0–3% |
| 150 м | ~20 | **0** | 0% |

**Вывод:** обрыв резкий и наступает между 50 и 75 м. Рельс лежит горизонтально,
луч идёт по касательной — отражений на большей дальности не приходит вообще.
Дело не в разреженности: в срезе на 150 м всего ~20 точек на всю ширину тоннеля.

Отсюда следует, что детектировать рельсы на 100+ м нельзя никаким алгоритмом,
включая нейросеть: восстанавливать нечего, сигнал отсутствует, а не слаб.
Это же объясняет, почему прежний детектор на дальности «цеплялся за стены» —
в срезе есть только они.

### Бэг с препятствием (`doubleT_obstacle`)

Единственная запись с людьми на путях. Топик отличается от остальных бэгов:
`/sensing/lidar/hesai128/pointcloud` (у прочих — `/lidar_points`), поэтому
топик нужно определять по типу сообщения, а не по имени.

**Поезд в этой записи почти стоит** — 11 м за 201 кадр (20 с). Это съёмка
на препятствие, а не проезд, поэтому дальность первого обнаружения при
движении по ней замерить нельзя.

**Человек A — ходит поперёк пути, на дальности ~55 м.** Ширина кластера
~0.5 м, высота 1.6–1.78 м, 105–140 точек, виден во всех кадрах. Дальность
держится 54.8–56.7 м, а X меняется — человек ходит поперёк пути и обратно:

| t, с | x, м | положение |
|---|---|---|
| 0 | +0.21 | в центре пути |
| 3–4 | −1.8 (край до −2.4) | **вышел за левую границу габарита** |
| 7 | −0.09 | вернулся в центр |
| 9–11 | +0.95 | у правого края габарита |
| 13–20 | +0.79 | остановился, стоит |

Центр колеи под лидаром — x = −0.19, то есть габарит ±1.7 м это примерно
от −1.9 до +1.5. На кадрах 30–40 человек выходит **за** габарит слева и в
эти моменты препятствием не является. Это делает бэг хорошим тестом: детектор
должен переключаться «в габарите / вне габарита» в такт движению человека,
а не просто «вижу объект».

**Человек B — проходит вплотную, вдоль поезда.** Появляется на 17 м
(кадр ~150), затем виден на 3.5 м и удаляется до 16 м за 4 с (≈3 м/с),
x ≈ +1.9, 1500–3800 точек, высота до 2 м.

**Штатные конструкции в коридоре ±1.8 м** (НЕ препятствия): 10–15 м (x −1.7),
15–20 м (x +1.4), 30–35 м (x +1.6), 45–50 м (x +1.2), 75–80 м (x −0.4),
105–110 м (x −0.9). Отличаются профилем высот: тянутся до свода (z ≈ 2.5 м),
тогда как у человека масса точек на 0.2–1.4 м с обрывом выше 1.5 м.
Признак «обрыв профиля высот» работает уже на 19 точках и не требует обучения.

### Докуда видно препятствие (в отличие от рельсов)

| Дальность | Точек у рельса | Точек на вертикальном объекте |
|---|---|---|
| 50 м | 8–10 | сотни |
| 75 м | **0** | 48 |
| 105–110 м | **0** | **19–24** |

Причина разницы — угол падения луча: рельс лежит горизонтально, луч идёт по
касательной и не возвращается; человек или ящик стоит вертикально и отражает
нормально.

**Практический вывод:** обнаружение препятствий на 100 м возможно, хотя
рельсы на этой дальности невидимы. Значит, детектор не должен зависеть от
детекции рельсов вдаль — достаточно габаритного коридора, построенного по
ближней зоне с расширением по дальности.

Наблюдения:
- **Модели сложнее дуги работают хуже.** Клотоида на 150 м даёт 8.6 м против
  2.4 м у дуги: лишние степени свободы усиливают шум, а не ловят кривизну.
- **Ошибки концентрируются на входах в кривые** — узкие диапазоны кадров
  (146–153, 325–332), корреляция ошибки с кривизной +0.82. Предсказать будущее
  *изменение* кривизны из прошлого участка нельзя в принципе: этой информации
  нет во входных данных. Нейросеть здесь тоже не поможет.
- p95 заметно хуже медианы (на 150 м — 10.4 м против 2.4 м), поэтому габаритный
  коридор должен **расширяться с дальностью**, а не претендовать на точную линию.

### Ось тоннеля как предиктор — проверено и отвергнуто

Гипотеза: тоннель — труба, центроид поперечного среза даёт осевую линию.
Замер: ошибка 1.5–5 м против 0.06–0.3 м у экстраполяции, то есть **хуже**.
Причина в том, что тоннель трубой не является — многопутные участки, заезды
на платформу, ответвления смещают центроид. Гипотеза закрыта.

### Известные дефекты карты пути

- **Квантование колеи.** X-бин Z-профиля равен 0.05 м, поэтому измеренная колея
  принимает дискретные значения (пики на 1500/1590/1600 мм). Остаточный разброс
  9–29 мм — это в основном дискретизация, а не дрейф сшивки.
- **Участки с аномальной колеёй — в основном были той же ошибкой сшивки.**
  Прежде списывалось на стрелки: 110 узлов из 695 на
  `roundT_squareT_pressureGate_squareT` и 41 из 214 на `doubleT_platform`.
  После перехода на проекцию к отрезку и сборку в базисе пути осталось
  **3 из 694** и **0 из 214** соответственно — то есть основной причиной была
  параметризация карты. Остаток действительно оказался соседним путём и
  снимается `filter_branch` (см. «Соскоки на соседний путь»).
- **Многопутность.** Свой путь выбирается как кластер с midpoint ближе всего
  к X=0 (`own_x_range`). На стрелке, где пути расходятся постепенно, этот
  критерий неустойчив: до расхождения обе пары рельсов близки к лидару.
- **Стрелки как принципиальная неоднозначность.** Куда поедет поезд, из облака
  точек до перевода стрелки не определить. Корректное поведение — вести габарит
  по всем возможным веткам, а не угадывать одну.
- **Накопление ошибки одометрии.** Позы интегрируются, поэтому ошибка растёт
  с длиной проезда. Для карты это мешает слабо (важна форма на 100–200 м,
  а не абсолютная позиция через 700 м), но для длинных бэгов это предел.
- **Карта — не детектор.** Зелёная линия на 150 м строится из наблюдений,
  сделанных когда поезд туда доехал. Как разметка (в т.ч. для обучения) это
  корректно; в реальном времени на новом бэге такой информации нет.

### Почему `rail_mapper.py` не работал

Прежняя версия переводила точки в глобальную систему **только сдвигом по Y**,
а X записывала в локальных координатах кадра (`rail_mapper.py:130`). На повороте
кадры повёрнуты друг относительно друга, поэтому в один массив попадали X из
систем с разной ориентацией, и медиана по ним систематически **спрямляла
повороты**. Это и была причина «рельсы плохо определяются на поворотах» —
не ошибки детекции.

Дополнительно: `cumulative_dy` — длина дуги, а глобальный Y карты — декартова
координата; на прямой они совпадают, на повороте расходятся, так что и ось
параметризации карты была неверной.

## Фильтрация стен тоннеля (`tunnel_filter.py`)

Убирает точки стен и потолка тоннеля, оставляя зону путей. Три режима:

| Режим | Описание |
|---|---|
| `off` | Без фильтрации (по умолчанию) |
| `fixed` | Фиксированная полоса ±half_width от центра колеи |
| `adaptive` | Полоса сужается на дальности: вблизи шире (стрелки, 2 пути), вдали уже (один путь) |

### Что остаётся после фильтрации

- Рельсы, шпалы, балласт
- Кабели и конструкции вблизи путей
- Стрелки и ответвления (в пределах half_width)
- Контактный рельс/провод (до ceiling_height)

### Что убирается

- Стены тоннеля (далеко по X от центра колеи)
- Потолок (выше ceiling_height над землёй)

### Параметры (CLI)

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--tunnel-filter` | off | Режим: `off`, `fixed`, `adaptive` |
| `--tunnel-half-width` | 4.0 | Полуширина зоны путей, м (для fixed — постоянная, для adaptive — вблизи) |
| `--tunnel-ceiling` | 5.0 | Макс. высота над землёй, м |
| `--tunnel-far-width` | 2.5 | Полуширина на дальней дистанции (только adaptive), м |

### Использование как библиотеки

```python
from tunnel_filter import filter_tunnel

# Автоопределение центра колеи + адаптивная фильтрация
mask, track_center_x = filter_tunnel(
    points, ground_plane,
    mode='adaptive',
    near_half_width=4.0,   # вблизи — 2 пути + обочины
    far_half_width=2.5,    # вдали — один путь
    ceiling_height=5.0,
)
filtered_points = points[mask]

# Или отдельные функции:
from tunnel_filter import estimate_track_center, filter_adaptive_width
center_x = estimate_track_center(points, ground_plane)
mask = filter_adaptive_width(points, ground_plane, track_center_x=center_x)
```

## Оценка скорости (`speed_estimator.py`)

```bash
# Тест на конкретном bag
```

## Аккумуляция кадров по скорости

Обогащение облака точек на дальних дистанциях: N кадров сдвигаются по Y с компенсацией скорости и объединяются.

**Адаптивная фильтрация по дальности**: из старых кадров берутся только дальние точки. Чем старше кадр, тем выше порог дальности (`min_y = |сдвиг| × 2`). Это позволяет безопасно использовать 15-20 кадров даже на поворотах — ближние точки, которые "уплывают" по X при повороте, автоматически отсекаются.

```bash
# 15 кадров — максимум точек вдали, безопасно на поворотах
python visualize_bag.py for_hackathon/doubleT_platform --accumulate-speed 15 --max-y-distance 150

# 20 кадров — для прямых участков
python visualize_bag.py for_hackathon/doubleT_platform --accumulate-speed 20 --max-y-distance 200
```

| Кадров | 0-25 м | 50-100 м | 100-200 м |
|--------|--------|----------|-----------|
| 1 | 174,031 | 1,805 | 216 |
| 5 | 342,396 | 8,238 | 1,087 |
| 10 | 359,402 | 15,166 | 1,993 |
| 15 | 359,402 | 20,764 | 2,726 |
| 20 | 359,402 | 25,120 | 3,310 |

Ближние точки (0-25 м) стабилизируются после ~10 кадров (старые ближние отсекаются). Дальние растут линейно.

```python
from visualize_bag import BagFrames, find_db3, accumulate_with_speed
```
