# `guard/` — габарит и детектор препятствий

Тракт, который строит ось пути, ведёт вдоль неё габаритный коридор и
объясняет всё, что в этот коридор попало. Цель — **не видеть препятствий
там, где их нет**, и работать до 110 м.

Пишется по блокам: каждый следующий опирается на предыдущий и ничего в нём
не меняет. Порядок блоков и есть суть решения — сначала объяснить сцену
штатным (стена, конструкция тоннеля), и только остаток считать препятствием.

Полное описание замеров, порогов и результатов по бэгам — в корневом
[README.md](../README.md), раздел «Детектор препятствий: блоки (`guard/`)».

## Быстрый запуск

```bash
python -m guard.run for_hackathon/doubleT_platform --frame 100
python -m guard.run for_hackathon/doubleT_platform --sweep 10 --accum
python -m guard.run for_hackathon/doubleT_platform --sweep 10 --accum-pts
python -m guard.run for_hackathon/doubleT_platform --bar --sweep 40
python -m guard.run for_hackathon/doubleT_platform --frame 100 --plot
python -m guard.run for_hackathon/doubleT_platform --frame 20 --accum 5 --plot
python -m guard.run for_hackathon/squareT_platform_squareT_switch --frame 820 --branches
python -m guard.obstacles for_hackathon/doubleT_obstacle --sweep 10
python -m guard.multitrack for_hackathon/squareT_platform_squareT_switch --frame 820
python guard/eval_axis_far.py --step 5        # замер оси вдаль против карты
```

Пакет запускается как модуль (`python -m guard.run`), потому что импортирует
`visualize_bag` из корня проекта. Скрипты-замеры (`eval_axis_far.py`,
`plot_axis.py`) запускаются и напрямую.

### `geom.py` — общая геометрия кадра

Один раз переводит облако из осей лидара (`x` вправо, `y` **назад**, `z`
вверх) в рабочую тройку `fwd = -y`, `lat = x`, `up = z`, чтобы не тащить
минус через весь пакет. Дальше везде используются только `fwd/lat/up`.

Оценивает уровень пола под самим поездом — там он гарантированно есть и не
заслонён. Берётся 2-й перцентиль `Z`, а не минимум, чтобы один выброс не увёл
уровень вниз.

- `to_frame(pts)` → `(fwd, lat, up)`
- `floor_level(fwd, lat, up)` → уровень пола, м

Запасное значение при нехватке точек — `FLOOR_FALLBACK = -2.0`: это уровень
ПОЛА, а не головок (лидар на 1.65-1.73 м над головками, пол ещё на
0.30-0.45 м ниже). Стоявшее раньше −1.65 было высотой головок и смещало
полосу поиска рельсов выше них — ось терялась.

### `track.py` — блок 1: ось прямого пути

Даёт линию, от которой отсчитывается габарит. На прямом участке это прямая,
и сознательно не делается ничего сложнее.

Ось ищется по головкам рельсов в ближней зоне. Головка — не 0.25 м над
«полом»: пол это низ балласта и лотка, поэтому полоса поиска взята вокруг
0.35 м. Пара рельсов отбирается **не** по близости к номиналу колеи (таких
пар в срезе до 36 — соседний путь и кромка платформы дают такие же), а по
непрерывности: своя пара повторяется во всех срезах подряд. Ближний срез
(до 7 м) исключён — туда лезут шпальная решётка и крепёж.

Как собирается ветка. Связывание пар внутри среза жадное по паре (свежесть
ветки, расстояние), а не в порядке перебора: иначе дальняя пара, идущая
первой в списке, перехватывала живую ветку раньше ближней (f30
doubleT_platform). Длина ветки — самый длинный НЕПРЕРЫВНЫЙ прогон внутри
неё, и прогон короче `MIN_BRANCH` срезов ветку отбраковывает: чужая рваная
ветка, оставаясь единственной, угоняла ось (f170 roundT_pressureGate: +0.77
м от истины), а своя ветка с дырой от колец лидара (f30/f40) должна при
этом выживать. Плато-дубли пиков (равные счётчики соседних бинов) сливаются
в один. Отбраковка по `OWN_LAT` отдаёт нулевую ось и `gauge=None`: чужая
ветка не даёт ни оси, ни колеи.

- `straight_axis(fwd, lat, up, floor)` → ось кадра
- `axis_at(axis, d)` → поперечное смещение оси на дальности `d`

### `axis_wall.py` — блок 1б: ось вдаль ведёт стена

Рельсов дальше 50-75 м физически нет, поэтому блок 1 продолжает ось прямой,
и на кривой она промахивается втрое больше полугабарита. Стена тоннеля
параллельна пути и на дальности плотнее рельсов — значит, она может
**передать** ось вдаль: где стена, там путь со сдвигом.

Ось не заменяется стеной: в ближней зоне её по-прежнему ведут рельсы, стена
подхватывает её там, где прямая перестала объяснять сцену. Включение — по
измерению, а не по дальности (порог по дальности был бы подгонкой), и
побинно, а не на весь кадр. Первичный триггер — значимость СТРЕЛКИ кромки
(z-тест: |sag| > 2·sigma_sag, где sigma_sag выводится из rms линии стены
через псевдообратную дизайн-матрицу параболы; подогнанный порог SAG_TOL
удалён). Невязка отступа — второй триггер: она ловит переходы, где стена
сходится почти прямой (стрелка ~0), а путь уходит. Отступ «стена → путь»
**измеряется в каждом кадре**: у разных тоннелей он разный (−1.44…−1.72 м),
константа сломала бы часть бэгов.

- `pick_layer(fwd, lat, up, floor, axis)` → слой высоты, который ведёт ось
- `measure_offset(fwd, lat, up, floor, axis, layer=None)` → отступ по сторонам
- `_side_reach(...)` → докуда каждая сторона даёт кромку (выбор наружной)
- `trace_axis(...)` → ведение оси вдаль (в `analyze` попадает в `axis['far']`)
- `lat_at(tr, d)` → смещение ведомой оси на дальности `d`; за концом
  ведения продолжает последний наклон (регрессия по плечу `FIT_WIN` с
  пределом кривизны), а не защёлкивает константу

Мёртвый код удалён: `scan_edges`, `fit_line` и константы `LINE_TOL` /
`LINE_MIN` (урок «4 точки — не линия» живёт теперь в `MIN_BINS = 5`
`check_wall.py`).

Три механизма этой сессии поверх ведения:

- **`frame_edges` отдаёт ВСЕ линии стороны, а не одну**, и только
  ИЗМЕРЕННЫЕ бины: на pressure gate видны две стены с одной стороны
  (затравочная и стена следующего пролёта), а бин, куда линию дотягивает
  полином, но точек не было, в `reach` не засчитывается.
- **Переопора отступа при смене стены**: если ведущая сторона не прослежена
  в затравке, отступ переизмеряется из непрерывности оси (off = кромка −
  продолжение оси; прирост наклона ограничен `CURV_LIM`).
- **Ось в дыре — парабола линии стены минус отступ** (`_hole_pred`), с
  предохранителями: кривизна линии должна быть значима (тот же z-тест), а
  оценки двух стен — сойтись в пределах `GATE`, иначе откат на линейное
  продолжение. На f123 roundT_pressureGate ошибка в дыре 42-58 м падает с
  0.7-1.4 м (линейно) до 0.3-0.5 м.

#### Четыре замера, изменившие ведение

**Слой высоты для оси выбирается по гладкости, а не берётся худший.** Для
габарита худший (ближайший к оси) слой верен — поезд упрётся в самое узкое.
Для ведения оси он неверен: тоннель круглый, и внизу он ещё не раскрылся,
поэтому кромка садится внутрь и цепляется за лоток, балласт и кабели. Замер
профиля по высоте (f108, R ≈ 2.7 м):

| высота, м | 0.0-0.5 | 0.5-1.0 | 1.5-2.0 | 2.5-3.0 | 3.5-4.0 | 4.5-5.0 |
|---|---|---|---|---|---|---|
| кромка, м | 1.48 | 2.33 | **2.67** | 2.65 | 2.18 | 0.59 |

Зашить высоту нельзя — лучший слой зависит от бэга: на круглом тоннеле это
2.5-3.0 м (std 0.24 против 0.37 внизу), на платформенном 0.5-1.0 м (std 0.37
против 1.52 наверху, там платформа и навес). Поэтому слой выбирается по
кадру, по гладкости кромки вдоль дальности. Попадание против лучшего слоя
по карте — 67% / 69% / 95% на трёх бэгах.

**Наклон оси — регрессией по 4 бинам, а не разностью соседей.** Бин 5 м
квантует кромку: истинная дуга идёт ровно (−0.45 / −0.45 / −0.50 / −0.51 м
на бин), а поштучная оценка скачет (−0.15 / −0.65 / −0.40 / −0.74). По двум
точкам эта рябь становится ошибкой наклона 0.05 м/м, которую дыра растягивает
на 20 м. Плюс предел `CURV_LIM` на **кривизну**, а не на наклон: путь имеет
право уходить вбок круто (до 1.83 м/бин), но не разгоняться быстрее, чем
гнётся рельс. Предел выведен из нормы: СП 32-105-2004 — главные пути
R ≥ 600/300 м, соединительные R ≥ 150 м, откуда `CURV_LIM = BIN²/150 =
0.167` м/бин² (запас от измеренного по картам максимума 0.132 м/бин²
20-метровой стрелкой; старый побиновый замер давал p95 0.098, max 0.430).
Без предела ось уезжала в дыре на 13.7 м.

**Ось ведёт наружная стена — та, что обрывается РАНЬШЕ.** Против интуиции:
вдаль видна как раз внутренняя стена дуги. Луч упирается в наружную поперёк,
а вдоль внутренней скользит:

| поворот | кромка слева | кромка справа |
|---|---|---|
| влево | 97.5 м | **37.5 м** |
| вправо | **32.5 м** | 92.5 м |
| прямая | 97.5 м | 97.5 м |

Зеркалится со знаком поворота — значит геометрия, а не особенность бэга.
Разрыв на повороте 55-60 м, на прямой 0, поэтому `OUTER_MARGIN = 15` м лежит
в разрыве: на прямой ведут обе стены, сверяя друг друга.

**Отступ убывал с дальностью — и это была не физика, а смещение оценки.**
Замер (кромка против истинного пути, медиана по бэгу):

| дальность | 27 м | 47 м | 67 м | 87 м |
|---|---|---|---|---|
| roundT_pressureGate (кривой) | 2.21 | 2.19 | 1.98 | **1.68** |
| doubleT_platform (прямой) | 1.73 | 1.60 | 1.68 | 1.60 |

Снос реален: без поправки ошибка копилась монотонно, на f108 от −0.44 м на
52 м до −2.44 м на 97 м. Объяснялся он скользящим углом луча, и лечился
поправкой `OFF_FADE`. Объяснение оказалось неверным — см. ниже про край
стены: уезжала не стена, а 10-й перцентиль по горстке точек. Причина снята в
источнике, `OFF_FADE = 0`.

**Ведение цепляется за ВНЕШНИЙ край стены, габарит — за внутренний.** Это
разные задачи, и край для них нужен разный. Габариту нужен ближний к пути
край: поезд упрётся в самое узкое. Ведению нужна стена как линия, а её
внутренний край размывают кабели, кронштейны и ниши, висящие перед стеной, —
внешний же задан самой стеной, дальше неё луч не проходит.

Замер f108, слой 2.1 м, справа — где стоит кромка относительно слоя:

| дальность | 27.5 м | 52.5 м | 87.5 м |
|---|---|---|---|
| точек в слое | 180 | 29 | 12 |
| p10 (внутренний) | 2.12 | 2.23 | 1.91 |
| медиана | 2.22 | 2.40 | 2.30 |
| p90 (внешний) | 2.34 | 2.55 | 2.89 |

Медиана вдоль дальности стоит — стена никуда не уходит. Уезжала внутрь
только оценка по внутреннему краю, и тем сильнее, чем меньше точек. Отсюда же
снята причина `OFF_FADE`: снос был реальным, но объяснялся не физикой луча, а
смещением оценки, поэтому поправка **обнулена**, чтобы не компенсировать
снос дважды.

Внешний край надёжен, пока за стеной ничего нет. Где за ней открытый объём —
платформа, зал, второй путь — дальний конец разброса принадлежит уже не
стене: на `doubleT_platform` f215 слой даёт p10 1.87 / p50 3.26 / p90 5.33 м,
и 5.33 — это навес платформы. Поэтому внешний край не уходит от внутреннего
дальше `OUTER_SPAN = 0.60` м: на круглом тоннеле весь разброс слоя 0.73 м,
так что порог отделяет толщину своей стены от чужого объёма.

**Оценка края не должна гулять с числом точек** (`Q_RANK = 20`). Перцентиль с
фиксированной долей — не одна и та же оценка при разном `n`: p10 по 200
точкам это 20-я точка, уверенно тело стены, а по 12 точкам — вторая, то есть
пара крайних отражений. Перцентиль считается как `Q_RANK/n`, зажатый в
`[WALL_Q, Q_MAX]`: при 200 точках это прежний p10, при 20 — глубже.

**`reach` считается от первого наблюдаемого бина**, а не от нулевого. Бин
0-5 м лежит под самим поездом, и в верхних слоях он пуст: на высоте 3.1 м
вплотную к лидару точек нет вовсе (`roundT_doubleT` f14 — 0 точек с обеих
сторон на 2.5 м при 690/724 уже на 7.5 м). Пустой бин под поездом — слепое
пятно сенсора, а не разрыв знания о пути впереди; раньше он обнулял всю
подтверждённую дальность на 9 кадрах из 36.

**Слой выбирается по ряби, а не по гладкости.** Гладкость плохо отличает
стену от свода: свод сползает монотонно и по второй разности выглядит
идеально ровным. Та же f108, кромка справа на 72.5-97.5 м — слой 3.1 идёт
1.91 → 1.60 (сползание при нулевой ряби), слои 0.6-1.6 идут 3.08 → 3.69. По
одной гладкости выигрывал слой 3.1, то есть загиб потолка. Поэтому рябь
мерится остатком после вычитания линейного тренда, а сам снос входит в оценку
штрафом `DRIFT_W`: своя стена параллельна пути и её кромка не обязана ехать.
На f108 выбор сместился с 3.1 на 2.1 м.

**Ось сглаживается как функция дальности** (`SMOOTH_WIN`, скользящая
регрессия по ±2 бина). Та же рябь бина 5 м, но уже на выходе. Замер
сглаживания как постобработки:

| способ | скачок p95 | ошибка 70 м |
|---|---|---|
| сырая ось | 1.08 | 0.22 |
| ±2 бина | **0.90** | **0.15** |
| ±3 бина | 0.86 | 0.16 |
| парабола на всё окно | 0.94 | 0.25 |

Парабола — проверенный тупик: она подгоняет одну дугу под участок, где
радиус меняется, и на `roundT_doubleT` портит 70 м с 0.12 до 0.54 м. Окно
не переходит границу доверия к кромке: за ней стена другая (второй путь,
зал), и смешивать два участка в одну прямую — размазать разрыв, а не убрать
рябь. `SMOOTH_WIN = 0` выключает сглаживание — это и показывает `--raw`.

### `check_wall.py` — стены кадра как линии

Стены ищутся в АБСОЛЮТНЫХ координатах кадра, без знания об оси: бин отдаёт
ВСЕ свои поверхности (`layer_clusters`), из них по непрерывности собираются
цепочки (`chains`), цепочка режется на куски (`cut`), каждый кусок фитится
параболой с отбраковкой (`fit_seg`), линии соседних слоёв сливаются в одну
стену (`MIN_LAYERS = 3`), а половинки стены, разрезанной пересечением нуля
лидара, сшиваются обратно (`_stitch`).

#### Бин отдаёт ВСЕ поверхности, а не одну кромку

Прежний `layer_edges` сводил бин к одному числу — ближайшей к лидару кромке.
Пока в бине одна стена, это верно. Но если перед стеной встаёт вторая
поверхность, оценка перескакивает на неё, и стена пропадает из профиля
вовсе. Замер `roundT_pressureGate_roundT` f111 слева (кластеры по выносу,
разрыв > 0.5 м, n >= 4):

| бин | стена | вторая поверхность |
|---|---|---|
| 45-50 | −4.19…−4.54 (5 слоёв) | −0.50 только h=0.1-0.6 |
| 50-55 | −4.58…−4.80 (4 слоя) | −0.48 при h=3.1-3.6 (n=30) |
| 55-60 | −4.67…−5.16 (4 слоя) | −0.43…−0.58 во ВСЕХ слоях |
| 60-65 | −4.54…−5.26 (3 слоя) | −0.80…−2.02 во всех слоях |

Стена непрерывна: −4.5 → −4.8 → −5.1 → −5.2. Но с 55 м рядом с осью встаёт
конструкция от пола до свода (створка pressure gate, за ней начинается
стена следующего пролёта), кромка перескакивает −4.80 → −0.48, `cut` видит
скачок 4 м и режет НЕПРЕРЫВНУЮ стену надвое. Ведение упиралось в конец
ближнего куска на 52 м, а дальний кусок (57-112 м, 43 бина измеренной
кромки) не использовался вовсе.

**Больше точек не помогает.** Замер по накопленному облаку (полный SE(2) по
6 кадрам, 184 тыс. → 1.3 млн точек) даёт ровно тот же разрез в том же
месте: оба объекта просто становятся плотнее. Нехватки данных здесь нет.

Поэтому `layer_clusters` отдаёт все поверхности бина (разрыв по выносу
> `CLUST_GAP = 0.50` м — между двумя поверхностями есть пустота, внутри
одной её нет), а `chains` решает по НЕПРЕРЫВНОСТИ вдоль дальности, какая из
них продолжает стену: цепочка ведётся предсказанием по наклону
(`CHAIN_TOL = 1.00`, `CHAIN_SLOPE = 0.35`), жадно по цепочкам, а не по
кластерам — иначе объект, вставший рядом, перехватывает чужую цепочку
вместо того, чтобы завести свою. Это то же требование непрерывности,
которым блок 1 отбирает свою пару рельсов среди 36 кандидатов.

Результат — стены перестали рваться об объекты:

| кадр | было | стало |
|---|---|---|
| roundT_pressureGate f111 слева | 2-52 м | **2-102 м** (6 слоёв) |
| roundT_pressureGate f108 слева | 2-58 м | 2-78 м |
| roundT_doubleT f200 справа | — | **8-112 м**, rms 0.11 |

`doubleT_platform` f90 теперь разделяет зал за стеной (−5.33 м, 92 м) и
свою стену (−1.67 м, 78 м) как разные стены — раньше они конкурировали за
одну кромку.

Остальные решения:

- **`MAX_RANGE = 130`** (было 110). Замер по шести бэгам, шаг 30 кадров:
  при пределе 110 дальний конец стены упирался в него на ВСЕХ кадрах
  (med 108, max 108) — предел резал стену, а не данные. При 130 дальний
  конец med 108, p90 128; при 150 — те же med 108 и max 148, то есть
  дальше 130 прибавка редкая. Число стен на кадр не меняется вовсе (med 2,
  p90 3 при 110/130/150): запас по дальности ложных линий не плодит.
- **`MIN_LAYERS = 3`** (было 2). Ложные линии живут ровно в двух слоях и
  почти всегда в нижних (0.6/1.1 м) — это шпальная решётка, балласт, лоток,
  край платформы. Замер (шесть бэгов, шаг 30, `max_range` 130): стен на
  кадр p90 4 → 3, max 5 → 3, а лучшая стена кадра остаётся med 100 м /
  p10 62 м — бит в бит. Сквозной замер тоже не изменился.
- **`cut()` режет по ИЗМЕНЕНИЮ шага кромки** (вторая разность > `JUMP`), а
  не по самому шагу: на завороте первая разность законно велика, и линия
  рассыпалась на куски ровно там, где стена поворачивает (f123
  roundT_pressureGate: линия 42-108 м вместо обрыва на 78 м).
- **`MIN_BINS = 5`** — урок удалённого `LINE_MIN` блока 1б: при 4 точках
  парабола проходит почти точно, и резать нечего — любой рваный кусок
  становился «линией».
- **`MIN_OFF = W.MIN_OFF / 2`**: у walls это «ближе к ОСИ стены не бывает»,
  а здесь отсчёт от НУЛЯ ЛИДАРА — на кривой своя внутренняя стена подходит
  ближе 1.2 м. До нуля опускать нельзя: появляется псевдостена из точек
  пути впереди на дуге.
- **`NEAR_FWD = 15`: запрет `MIN_OFF` действует только в ближней зоне.**
  Псевдостена, ради которой запрет введён, — это СВОЙ ПУТЬ под лидаром
  (головки, балласт, шпальная решётка). Он виден вблизи и только вблизи;
  дальше у нуля лидара своего пути нет, а стена там быть может. На дуге
  путь уходит вбок, стена идёт вдоль пути и ПЕРЕСЕКАЕТ ноль лидара —
  запрет на всей дальности резал её ровно в точке пересечения.

#### Стена, пересекающая ноль лидара (`_stitch`)

`layer_clusters` собирает поверхности ДВУМЯ независимыми проходами —
отдельно левая полуплоскость, отдельно правая. Знак нужен технически:
`lat * side` делает «наружу» направлением бóльших чисел, и тогда сортировка,
кластеризация разрывом и `MIN_OFF` работают одинаково для обеих сторон.

На прямой это безразлично — своя стена остаётся в своей полуплоскости. На
дуге она пересекает ноль, и её половинки попадают в РАЗНЫЕ проходы, которые
не встречаются нигде. `_merge` их тоже не сводит: он требует одинакового
`side` и общего участка дальности, а половинки стыкуются концами.

Замер `doubleT_platform` f313 — кромка непрерывна, ни одного пустого бина:

| бин | 65-70 | 70-75 | 75-80 | 80-85 | 85-90 |
|---|---|---|---|---|---|
| кромка, м | −0.98 | −0.77 | **−0.28…+4.94** | +0.27 | +0.88 |

а `detect` отдавал 2-72 м (L) и 82-128 м (R) двумя стенами с дырой 72-82 м
посередине. Ось, ведомая левой половиной, уходила в эту дыру и к 92 м
промахивалась на +3.4 м при ПРЯМОМ пути.

`_stitch` идёт после отбора по `MIN_LAYERS` (половинки подтверждены каждая
своими слоями, а короткий мусор до сшивки не доживает и приклеиться не
может) и склеивает линии, продолжающие друг друга. Критерий — тот же, каким
`chains` ведёт цепочку внутри полуплоскости: продолжение одной попадает в
начало другой. Новых признаков не вводится, снимается только ограничение
«в пределах своей стороны».

- **Стыкуются и ВСТЫК, и С ПЕРЕКРЫТИЕМ.** Разрез идёт по точке пересечения
  нуля, и обе линии тянутся до неё с запасом: f239 даёт левую 2-42 м
  (кончается на +0.05) и правую 38-108 м (начинается с −0.25) — перекрытие
  4 м. Проверка «только встык» такую пару не рассматривала вовсе, и кадр
  рвался, пока соседний f241 сшивался.
- **Наклон НЕ сверяется.** На дуге он обязан меняться — стена там и гнётся.
  Требование совпадения наклонов отбрасывало настоящие стыки ровно там, где
  дуга разгоняется (тот же f239). Стену от чужой линии отделяет положение
  стыка, а не угол.
- Допуск положения — сумма rms самих линий (чем шумнее кромка, тем больше
  вправе разойтись продолжения), плюс на разрыве ход экстраполяции через
  дыру по `CHAIN_SLOPE`. Плюс требование ОБЩЕГО слоя высоты: сшивается одна
  стена, а не стена с навесом над ней.

| кадр | было | стало |
|---|---|---|
| `doubleT_platform` f313 | 2-72 + 82-128, дыра 72-82 | **2-122 м**, 6 слоёв, rms 0.18 |
| `roundT_pressureGate` f239 | 3 куска (2-38, 38-112, 2-48) | **2-108 м**, 6 слоёв, rms 0.25 |
| `roundT_pressureGate` f241 | 2 куска | **2-108 м**, 6 слоёв, rms 0.19 |

f239 и f241 теперь дают идентичный результат — дефект «на одном кадре
рвётся, на соседнем нет» снят в источнике.

**Сшивка — не финал.** Правильнее не резать вовсе: разделение на стороны
внутри сбора чисто техническое, и ОДИН проход со знаковым `lat` убрал бы
`_stitch` целиком (кластеризация разрывом симметрична, знак ей не нужен).
Не сделано потому, что один проход меняет поведение на ВСЕХ кадрах, включая
прямые: левые и правые поверхности попадают в общую сортировку и общую
жадную раздачу цепочкам. Проверять это надо по всем шести бэгам, а не по
трём кадрам. Открытые риски текущего решения: `_stitch` может склеить две
РАЗНЫЕ стены, случайно сошедшиеся в точке стыка (защита — общий слой и
допуск по rms, гарантии нет), и проверено оно на трёх кадрах двух бэгов.
- **`outer(walls, axis, off)`** (до 2026-09-27 называлась `leading`) отвечает,
  какая сторона НАРУЖНАЯ в повороте — та, что обрывается РАНЬШЕ, в неё луч
  бьёт поперёк: если даны ось и отступ, кандидаты фильтруются по отступу,
  иначе на двухпутке выбирается стена второго пути — она тянется дальше всех.
  Имя `leading` врало: вести по этой стене нельзя, она обрывается раньше всех,
  и ось эта функция не строит. Ведущую стену — ту, по которой ось реально
  построена, — отдаёт `wall_rules.leading`. Пороги `SEED_HI`/`GATE`/
  `OUTER_MARGIN` теперь локальны здесь: импорт `axis_wall` ради трёх констант
  делал детекцию зависимой от блока, который её же и потребляет.

### `wall_rules.py` — блок 1в: правила ведения

**Статус: прогнано против карты на трёх бэгах (шаг 25 кадров).** Не глазами по
кино — это ещё предстоит.

| бэг | режимы | 30 м | 50 м | 70 м | 90 м | 110 м |
|---|---|---|---|---|---|---|
| `doubleT_platform` | center 28% lead 45% | 0.03 | 0.06 | 0.07 | 0.60 | 1.55 |
| `roundT_pressureGate_roundT` | center 50% lead 22% | 0.09 | 0.09 | 0.13 | 0.29 | 0.22 |
| `roundT_squareT_pressureGate_squareT` | center 55% lead 20% | 0.11 | 0.15 | 0.18 | 0.16 | 0.51 |

Медиана ошибки против карты, м. До 70 м — 0.03-0.18 м при полугабарите 1.70
(замер сделан при том габарите; сейчас полугабарит 1.50 — ведение оси от
него не зависит, `axis_wall` работает от `OFF_MIN`/`OFF_MAX`, не от габарита).
Дальше 90 м расходится (p90 до 3.4 м), и это та же граница применимости, что у
`axis_wall`: в слое остаётся 20-40 точек.

**Три дефекта, найденных этим прогоном** (все — в правилах, детекция стен
работала верно):

1. **Сторона стены бралась из `w.side`** — а это сторона относительно НУЛЯ
   ЛИДАРА, не относительно пути. На дуге и на гейте ноль лидара уходит из
   коридора: `roundT_pressureGate_roundT` f115, путь уходит влево до -12.3 м на
   120 м, правая стена пути (отступ +2.4…+2.7 по карте) помечена `L`, потому
   что `_stitch` сшил её половинки через ноль и взял сторону дальней. Обе стены
   оказывались слева, пара для `CENTER` не складывалась НИКОГДА, в `LEAD`
   отступ применялся с обратным знаком — ось уезжала на +3.76 м вправо там, где
   путь шёл влево. Теперь сторона считается от оси, рекуррентно от предыдущего
   бина (тот же приём, что в замере 2 `axis_wall`: окно едет ЗА осью).
2. **Два порога были выведены из габарита вместо отступа.** Удалённый
   `LEAD_OFF_MIN = GAUGE_HALF + GAUGE_CLEAR = 1.95` м отбраковывал КАЖДОЕ
   измерение отступа (реальный диапазон 1.44…1.72 м весь ниже него), а
   `WIDTH_MIN = 2*GAUGE_HALF + 0.6 = 4.0` м отбраковывал КАЖДУЮ прямую
   (реальный коридор 2.88…3.44 м). Теперь оба выведены из отступа: `OFF_MIN =
   1.20`, `OFF_MAX = 8.0`, `OFF_FALLBACK = 1.60`, `WIDTH_MIN = 2*OFF_MIN`.
   Габарит и отступ — разные величины: в тоннеле стена штатно стоит внутри
   полугабарита, и это норма.
3. **Упор считался по абсолютному порогу**, а он — АСИММЕТРИЯ. На
   `doubleT_platform` f19 обе стены найдены верно, середина ровно в 1.98 м от
   каждой, но слева измерено 2.56 м, и «стена ближе своего отступа» объявляло
   упор на 32-77 м: ось уходила в `LEAD` по неизмеренной правой стороне
   (fallback 1.60 вместо реальных 2.13) и вставала на +0.35 вместо -0.31.
   Теперь упор — перекос зазоров, и на симметричной середине его нет по
   определению, как бы узок ни был тоннель.

**Открытый вопрос:** `roundT_doubleT` f185 ведёт по стене с отступом 6.62 м —
это дальний борт двухпутки, а не своя стена (med 1.49 max 2.44 против карты).
Но одометрия этого бэга слабая, и как эталон он непригоден, так что цифру
читать нельзя — смотреть глазами.

**Правила, добавленные последними сессиями.**

4. **CENTER требует согласия с рельсами** (`center_agrees`,
   `CENTER_VS_RAILS = 0.50`). Ось сначала идёт от рельсов, и передача её
   стенам не вправе эту ось сдвинуть: пара, которая не объясняет ось там, где
   ось известна точно, не объясняет её и дальше. Замер |середина − рельсы| в
   зоне рельсов: настоящий тоннель даёт med 0.07-0.10 м (середина И ЕСТЬ
   ось), зал 9 м — 2.33 м на каждом кадре, и именно он давал скачок оси
   +2.0 м в бине сразу за рельсами (`doubleT_obstacle`, 11 кадров из 11:
   −0.57 → +1.42). Сверяется ХОД, а не положение: постоянный сдвиг прямой оси
   законен (она стоит на своём `lat0`) и честную пару отменять не должен —
   на `roundT_pressureGate_roundT` f232 середина совпадает с картой до 5-9 см,
   а прямая ось врёт на 0.85-1.47 м, и проверка по положению запрещала там
   CENTER, загоняя кадр в LEAD по стене, пересекающей путь.
5. **Пара, сходящаяся почти в точку, — не два борта тоннеля**
   (`PAIR_CROSS = 0.25` в `cross_limits`). Признак «виновата та, чья кривизна
   меньше» выведен из кадров НА ЗАВОРОТЕ и на прямой даёт обратный ответ:
   своя стена идёт прямо именно потому, что своя. `doubleT_platform` f10 —
   честная стена 2.5-102.5 м (6 слоёв, rms 0.13, отступ от карты
   +2.48…+2.09) имеет кривизну +0.00058, а ложная линия 7.5-62.5 м (отступ
   +6.64 → +1.66) −0.00492; правило резало ЧЕСТНУЮ на 47.5 м, и ось падала
   с −0.17 до −7.96 м за два бина. Ниже `PAIR_CROSS` виноватая выбирается по
   сдвигу собственной кромки за общее плечо (4.87 м против 1.30 м).
6. **Перекошенная пара не даёт CENTER** (`PAIR_FAR_MAX = 3.0` в `_center`).
   Выезд на двухпутку и край платформы ломают середину, ни во что не
   упираясь: одна кромка стоит на штатном отступе, вторая — стена ЧУЖОГО
   пути. **По ширине этого не взять, и это замерено:** честный тоннель
   `roundT_pressureGate` даёт ширину med 4.96 м, целевой `roundT_doubleT` —
   5.03 м, то есть порог по ширине резал бы честный бэг. Разрез 1096 бинов
   CENTER по ширине против карты это подтверждает: 4-5 м дают ошибку 0.16 м,
   не хуже, чем 0-4 м (0.20 м). Признак — АСИММЕТРИЯ: ближняя кромка стоит
   там же, где всегда (1.76…2.52 м на всех бэгах), а уезжает ДАЛЬНЯЯ:

   | дальняя кромка | бинов | err med | доля > 1 м |
   |---|---|---|---|
   | < 2.5 м | 944 | 0.18 | 18% |
   | 2.5-3.0 м | 81 | 0.90 | 31% |
   | 3.0-3.5 м | 11 | 1.61 | **100%** |
   | 3.5-4.0 м | 6 | 1.72 | **100%** |
   | 4.0-4.5 м | 31 | 2.14 | **100%** |
   | 4.5-5.0 м | 23 | 1.93 | **100%** |

   За 3.0 м ошибка больше метра в 71 бине из 71 на четырёх независимых бэгах.
   Порог на границе: 2.5-3.0 — честный переходный слой (гейт, портал), он
   остаётся в CENTER. Проверяется ПОБИННО, а не раз на кадр: на f118
   `center_agrees` = True (в зоне рельсов пара честная), а ломается она на
   57.5 м, где сверять уже не с чем. `cross_limits` эту пару тоже не ловит —
   общего плеча у линий нет вовсе (2-48 м и 62-112 м, короче `PAIR_SPAN`).
7. **Ведущая из двух выбирается ближней К ОСИ, а не к нулю лидара**
   (`_pick`, тот же довод, что в `_usable`). На дуге путь уходит вбок, ноль
   лидара оказывается вне коридора, и «ближняя к нулю» — уже не «ближняя к
   пути». `roundT_doubleT` f118, 52.5 м (путь по карте на −4.66): своя стена
   2-48 м стоит на −7.0, чужая 62-112 м на +2.5; по модулю от нуля ближе
   ЧУЖАЯ, ведение уходило на неё и держало ошибку +4.7 м полсотни метров.
   Правило работает в паре с предыдущим: порог отказывает ложной середине, а
   этот выбор отправляет откат на верную стену. По отдельности ни то, ни
   другое кадр не чинит (замер на `roundT_doubleT`: только порог — p90 4.96,
   вместе — 1.78).

**Зачем.** `check_wall.detect` отвечает «где стены» и делает это хорошо
(линия 2-128 м, 6 слоёв, rms 0.21). Между «стены найдены» и «ось построена»
стоит слой РЕШЕНИЙ, и он был размазан по трём файлам: `check_wall.leading`
отвечала на другой вопрос (какая стена наружная) и ось не строила вовсе,
`axis_wall.trace_axis` решала ветками внутри рекурренции, `walls.trace`
держала свои отступы и лазила обратно в `axis_wall` за `RESID_TOL`. Поведение
нельзя было ни прочитать в одном месте, ни поменять, не влезая в алгоритм.

**Постановка (словами заказчика, они же и есть правила).** «Первая линия идёт
от габарита рельс, посередине — максимально возможно, насколько рельсы
показываются. Дальше коррекция по стенам: если путь чуть уходит и 2 стены
рядом и стены стабильны — мы середину возьмём и посередине продолжим. Если
габарит упирается в стену и она проходит дальше — мы считаем стену ведущей и
делаем от неё отступ и линию выстраиваем.»

**Режимы.** Ось строится бин за бином (5 м) до 130 м, и каждый бин объясняет
себя сам — режим целиком отвечает, откуда взялась ось:

| режим | когда | ось | цвет на картинке |
|---|---|---|---|
| `RAILS` | рельсы НАБЛЮДАЛИСЬ на этой дальности | середина колеи (блок 1), истина | зелёный |
| `CENTER` | рельсов нет, две стабильные стены, коридор симметричен и НЕ ПЕРЕКОШЕН (обе кромки ближе `PAIR_FAR_MAX` к оси) | середина между кромками (ведущей нет, отступ не нужен) | голубой |
| `LEAD` | коридор перекосило (заворот), и стена идёт дальше; ИЛИ стабильна одна стена | кромка + отступ, ведущая ВСЕГДА одна | оранжевый |
| `HOLD` | ни рельсов, ни стен | продолжение формы, «не знаем» | серый |

Приоритет ровно тот же, сверху вниз. Понижение с дальностью нормально
(рельсы кончились → `CENTER`, вторая стена кончилась → `LEAD`, обе → `HOLD`);
повышение требует `UP_RUN = 2` бинов подряд — один выброс на стене иначе
дёргает ось. Число взято из замера 4 в `axis_wall`: платформа даёт РАЗОВЫЙ
выброс (med +0.21 при p95 +3.54), а поворот — монотонный рост; один бин их не
различает, два уже различают.

**`RAILS` живёт только там, где рельсы наблюдались** — не там, куда прямую ось
можно продолжить. Продолженная прямая на кривой промахивается втрое больше
габарита (замер в `axis_wall`: 4.75 м на 70 м при полугабарите 1.70 м, том,
который стоял на момент замера),
поэтому граница режима стоит по `axis['obs_fwd']`, а не по `SEED_HI`.

**Сторона стены — от ОСИ, а не от нуля лидара.** `w.side` в этом блоке не
используется вовсе (см. дефект 1 выше): отсчёт идёт от оси предыдущего бина,
рекуррентно. Это же снимает вопрос «слева или справа» на дуге, где ноль лидара
оказывается вне коридора.

**Переход `CENTER` → `LEAD` — по ПЕРЕКОСУ коридора** (`_bump`), а не по кривизне
стены и не по скачку ширины. На дуге обе стены видны и ширина не скачет, так что
середина держалась бы до конца заворота, уводя ось. Признак такой: зазоры до
левой и правой кромки разошлись больше `2*GAUGE_CLEAR`, И та стена, к которой
ось прижата, продолжается дальше не меньше `LEAD_AHEAD = 10 м` (иначе упор — это
торец или ниша, вести по ней некуда). На симметричной середине упора нет по
определению, как бы узок ни был тоннель — это и есть урок дефекта 3. Скачок
ширины оставлен ВТОРЫМ триггером: гейт, платформа и выход на двухпутку ломают
середину, ничего не перекашивая.

**Отступ — не константа**, это уже замерено (замер 1 в `axis_wall`):
-1.69..-1.72 м на `roundT_pressureGate_roundT` против -1.44..-1.57 м на
`doubleT_platform`, тоннели разной ширины. Мерится в ближней зоне КАЖДОГО
кадра, где режим `RAILS` (`axis_wall.measure_offset`), запоминается на сторону,
применяется в `LEAD`. Где мерить было негде — берётся `OFF_FALLBACK = 1.60 м`
(медиана замеренного диапазона), и бин помечается `off_measured=False` (на
картинке пустой квадрат). Отбраковывается только то, что вне физического
диапазона `OFF_MIN = 1.20 … OFF_MAX = 8.0` м: такой «отступ» значит, что
кромка зацепилась не за свою стену.

**База отступа — кромка стены, а не «габарит не касается».** На завороте
стена и путь концентричны, отступ постоянен, и поехать он может только там,
где геометрия реально меняется (гейт, платформа, двухпутка).

**`tight` — не признак заворота, а настоящая аномалия.** Заворот разобран в
`_bump` и переводит в `LEAD`; пометка остаётся там, где ось подошла к стене
ближе `OFF_MIN`, то есть ближе, чем отступ физически бывает — кромка не та или
ось уехала. Порог тут именно `OFF_MIN`, а не полугабарит: сравнение с габаритом
помечало бы каждый бин нормальной прямой (см. дефект 2 выше). Ось при этом НЕ
правится — молчаливая правка даёт ось, которая на картинке «не ебашится в
стены», но врёт по сути.

**Почему порогам против карты верить осторожно.** Эталон (`track_map`) сам не
идеален: на `roundT_doubleT` одометрия слабая и как эталон непригодна. Карта
годится, чтобы НАЙТИ подозрительные кадры (три дефекта выше найдены именно
так), но решает глаз. Поэтому режим
каждого бина ВИДЕН на картинке, и пороги правятся по кадрам, где глаз видит не
тот режим. Карта — грубая проверка, не критерий.

дальность 130 вместо `axis_wall.MAX_RANGE = 100` сквозь весь конвейер
(`check_wall` уже тянет стену до 128); затем новые правила — съезд на
платформу, второй путь — как строки в ту же таблицу, а не как `if` в алгоритм.
Стрелка не нужна: едем прямо.

### `walls.py` — блок 2: стены и коридор

Когда впереди начинает появляться «что-то», это сначала надо попытаться
объяснить стеной. Что объяснилось стеной — препятствием не является, и по
этой же стене коридор продолжается дальше.

Граница берётся как внутренняя кромка (`edge_val`, ~10-й перцентиль), а не медиана: за
стеной открывается соседний путь, и медиана заявила бы «свободно до 5 м»
там, где на 1.8 м уже конструкция. Стена ведётся слоями высоты по 0.5 м —
тоннель круглый, вынос кромки зависит от высоты; границей габарита
становится худший слой в пределах высоты поезда. В каждом бине стена ищется
в окне вокруг предсказания по последним принятым бинам, а не по самому
сильному пику профиля.

Пустой бин — «не наблюдается», а не «свободно»: коридор в дыре ведётся
предсказанием, но подтверждённая дальность на ней не растёт.

**Габарит поезда и база его отсчёта.** Три константы в `walls.py`:

| Константа | Значение | Что это |
|---|---|---|
| `GAUGE_HALF` | 1.50 | полуширина, м (полная ширина 3.00) |
| `GAUGE_H_LO` | 0.10 | низ над уровнем ПОЛА, м |
| `GAUGE_H_HI` | 2.50 | верх над уровнем ПОЛА, м |

Габарит задан как **2.10 м от головки рельса**, а `GAUGE_H_*` отсчитываются
от ПОЛА (балласта). Это разные базы, и переводить между ними надо всегда:
головки лежат на 0.30-0.45 м выше пола (замер в `geom.FLOOR_FALLBACK`; то же
число независимо подтверждает полоса поиска головок 3-40 см над землёй в
корневом README). Отсюда `GAUGE_H_HI = 2.10 + 0.40 = 2.50` — берётся верх
диапазона, потому что запас вверх безопаснее срезанного габарита. Считать
высоту от лидара не нужно: связь «лидар → головки → пол» уже измерена
(лидар на 1.65-1.73 м над головками).

`GAUGE_H_LO = 0.10` остаётся ниже головок намеренно: опустить нижнюю границу
безопасно (лишние точки идут в поиск), а поднять до головок значило бы
перестать видеть препятствия на уровне шпал.

Полуширина влияет на то, клампится ли коридор стеной. Замеренный отступ от
оси до внутренней кромки стены — 1.44-1.72 м, то есть при 1.50 стена местами
оказывается ВНУТРИ полугабарита и коридор ею ограничивается (на бэгах
`roundT_*` и `doubleT_platform` — `min` коридора 1.22-1.32 при `med` 1.50).
Это норма, а не ошибка: в тоннеле стена штатно стоит внутри полугабарита
(см. ниже, «Два порога были выведены из габарита вместо отступа»). При
полуширине 1.05 габарит не достигал стен ни в одном бине — коридор выходил
ровно 1.05 всюду, и кламп по стене исчезал совсем.

- `trace(fwd, lat, up, floor, axis, max_range=..., bins=None, extra=None)` → бины коридора,
  подтверждённая дальность. `bins` — ось БЛОКА 1в (`wall_rules.build`, список
  `Bin`): окна поиска стен и отсчёт отступов идут от неё, и коридор
  повторяет изгиб пути. Все решения «откуда взялась ось» приняты там
  (RAILS/CENTER/LEAD/HOLD) и здесь не повторяются, поэтому правка правил
  ведения попадает в габарит сразу. За концом оси (`wall_rules.lat_at` → nan
  по `HOLD_MAX`) отсчёт возвращается к прямой: оставить nan нельзя — вынос
  стал бы nan и бины умирали бы молча. Режим каждого бина отдаётся наружу
  в `axis_mode`.

  Раньше сюда подавалась далёкая ось блока 1б (`far=axis['far']`), и правки
  блока 1в в габарит не попадали вовсе — коридор шёл по другой оси, чем та,
  которую показывает `plot_axis`.

  Если цепочка ловит ведомую ось внутри стены (предсказание ближе `MIN_OFF`
  в нескольких слоях — физически невозможно) или прямая ось объясняет бин,
  который ведомая потеряла (отступ сошёлся с ближней зоной в `RESID_TOL`),
  ведение признаётся ложным, и кадр доводится прямой осью (`far_dropped_at`
  в выдаче). Три ограничения на этот откат, все из замеров:
  * к бинам **RAILS/CENTER он не применяется** — они стоят на измерении
    (ошибка против карты med 0.07 и 0.16 м против 1.15 у LEAD и 2.47 у HOLD);
  * нарушение `MIN_OFF` в триггере A считается только по ИЗМЕРЕННОЙ кромке,
    а не по экстраполяции кончившейся стены («стена кончилась» — штатное
    событие, а не признак ложной оси);
  * кромка-доказательство в триггере B обязана лежать с той же стороны и от
    ВЕДОМОЙ оси, а не совпадать с затравкой одним модулем: стена, идущая
    вдоль пути, сторону относительно пути не меняет, а относительно прямой
    оси меняет, если та уехала (см. замер f222 в корневом README).

За сессию блок вырос вширь:

- **Одностороннее ведение.** Измеренная одна сторона подтверждает бин
  (статус `gauge`), вторая ведётся клампом габарита; поле `lead` помечает
  ведущую сторону (`left`/`right`/`both`/`gauge`). На двухпутке, где правая
  стена честно уходит, ведущей становится правая (замерено) — раньше такой
  бин ронялся в дыру целиком.
- **Оценка кромки — гибрид Harrell-Davis / percentile** (`HD_MIN_N = 8`,
  зажим к соседним порядковым статистикам): HD снижает шум кромки на
  10-17% и дрейф оценки от n в 2.5 раза, но при n=4 один выброс сдвигает
  его на −0.57 м — поэтому на крошечном n остаётся percentile.
- **Кольцевая модель Pandar128** (`_ring_floor_ranges`): по гистограмме
  вертикальных углов кадра восстанавливаются кольца, и бин-дыра, куда
  принципиально не попадает кольцо пола, помечается `uncovered` — «не
  покрыт сенсором» отличается от «покрыт, но пуст». Статус бина не
  меняется (дыра ведётся предсказанием), добавляется только маска.
- **`reach_bridged`** рядом с консервативным `reach`: мост через ≤
  `BRIDGE_MAX` (2) дыры подряд, если после дыры стена СОГЛАСОВАННО
  вернулась — кромка в пределах `GATE` от предсказания цепочки. Это
  предохранитель от моста через настоящий конец тоннеля: замер роя даёт
  40% коротких разрывов, отклонённых этой проверкой.
- **Окно поиска зажато в `MIN_OFF`**: иначе оно строилось от 0.7 м от оси —
  внутри габарита — и кабель/кронштейн на 0.7-1.2 м мог стать «стеной».
- **Поздняя затравка слоя**: слой, не давший кромки в ближней зоне,
  затравляется из точек полного окна `[MIN_OFF, MAX_OFF]` на первом бине,
  где они есть (`late_seed` в выдаче).
- **`extra=`** — точки прошлых кадров, перенесённые полным SE(2) из
  `trajectory.npz` (CLI-флаг `--accum-pts` в run.py): агрегат идёт только
  в оценку кромок стен (стены неподвижны, точки ложатся друг на друга;
  замер роя: 8-21 точка дальнего бина → 70-190, шум перцентиля втрое
  ниже). В structures и препятствия агрегат НЕ подаётся: движущийся объект
  размазывается одометрией в полосу и должен оставаться покадровым.

### `structures.py` — блок 2б: конструкции внутри коридора

Блок 2 возвращает одно число на бин, и всё внутри коридора для него не
существует. А там стоят штатные конструкции: ниша, кронштейн, откос, портал.
Отдать их дальше как есть — значит объявить препятствием нишу.

Разделяющий признак замерен, а не подобран: конструкция тоннеля идёт
**вдоль** пути (тоннель сам протяжённый), препятствие локально. Второй тип,
найденный по остатку, — вертикальная колонна до свода в одном бине; человек
обрывается на 1-1.8 м.

- `explain(fwd, lat, up, floor, axis, max_range=...)` → объяснённые ячейки и
  остаток по бинам

### `obstacles.py` — блок 3: препятствия в габарите

Препятствие — это то, что НЕ удалось отнести ни к чему штатному. Метод —
проверенный `wall_corridor.obstacles_in_gauge` (корневой README, человек на
~55 м найден в 21 кадре из 21), перенесённый на остаток после блока 2б:
штатные ниши и порталы сюда не доходят вовсе, а не отсеиваются порогами.
Три ключа метода прежние (избыток над фоном 40-го перцентиля занятых ячеек,
перекрывающиеся окна, высота колонки без свода); поверх — пять
правил-объяснений кластеров остатка, все про геометрию, а не про конкретный
объект (за «ширина ≤ 2 м, высота ≤ 2.4 м» прежний блок 3 и был откачен;
замеры у констант модуля):

| правило | смысл |
|---|---|
| `column` | колонна достала до свода (≥ 2.6 м) — пилон, портал, створка. **Сейчас не срабатывает никогда:** порог `COL_TOP_H = 2.60` выше верха габарита (2.50), а кандидаты берутся внутри габарита (`obstacles.py`, `h < GAUGE_H_HI`), поэтому верх кандидата не может превысить 2.50 < 2.60 — см. ниже |
| `wall` | кластер целиком в полосе `WALL_RIPPLE` (0.3 м) внутрь от измеренной кромки стены или за ней — это сама стена |
| `dust` | точки размазаны по дальности > `DEPTH_MAX` (1 м) — пыль рассеяния, твёрдый объект компактен вдоль луча |
| `base` | низ колонны выше 0.5 м над полом — не стоит на полотне (контактный рельс, подвесы); отключается в бинах `uncovered`, где пол принципиально не виден |
| `fragment` | над верхом колонны продолжается уже объяснённая конструкция — её нижний фрагмент |

**Признак `column` выключен понижением габарита.** `COL_TOP_H = 2.60` был
выведен из габарита 3.50: колонна отличалась от человека тем, что дотягивается
до свода. При габарите 2.50 порог недостижим, и на `doubleT_obstacle` счётчик
`колонна` упал с 76 (габарит 1.70/3.50) до 0.

Ложных препятствий это НЕ даёт — проверено покадрово: на всех кадрах
`doubleT_obstacle` находки имеют высоту 1.07-1.24 м (человек), находок с
высотой колонны нет. Объяснение просто переехало в другие признаки: `полотно`
вырос с 46 до 70. То есть это мёртвый порог, а не источник ложных
срабатываний.

Просто понизить `COL_TOP_H` нельзя: человек ростом 1.8 м занимает ячейки до
2.1 м, а `COL_MIN_CELLS` его не отсекает (замеры у констант `structures.py`) —
`COL_TOP_H` тут единственный различающий признак, и щель между 2.1 и 2.5 слишком
узка, чтобы ставить в неё порог. По существу признак сломался потому, что свод
теперь ВЫШЕ габарита: чинить надо проверкой колонны по точкам выше габарита
(свод там же, где был) при подсчёте находок внутри габарита. Это правка
блока 2б, пока не сделана.

**Порог `unanchored` привязан к габариту, а должен — к отступу.**
`gauge_centers` считает бин неподкреплённым по условию `|left| > GAUGE_HALF &
right > GAUGE_HALF` и подменяет там ведомую ось прямой осью рельсов. Но
«стена слишком далеко, чтобы держать ось» — свойство тоннеля (отступ
1.44-1.72 м), а не габарита поезда; это тот же класс ошибки, что описан ниже
в «Два порога были выведены из габарита вместо отступа». При 1.70 совпадение
с реальным отступом было случайным и проблему маскировало. Доля таких бинов
и расхождение подменённой оси с ведомой (каждые 10 кадров):

| полугабарит | `roundT_pressureGate_roundT` | `roundT_squareT_pressureGate_squareT` | \|сдвиг\| p95 |
|---|---|---|---|
| 1.70 | 20% | 22% | 1.33 / 0.09 |
| 1.50 (сейчас) | 27% | 37% | 1.77 / 0.28 |
| 1.05 | 62% | 68% | 3.83 / 12.78 |

Медиана сдвига всюду 0.00: расхождение сидит только на кривых, где прямая ось
уезжает. При 1.50 обострения почти нет, при 1.05 поиск препятствий в двух
третях бинов шёл вокруг прямой, ушедшей от пути на метры. Правка — вывести
порог из отступа (`OFF_MIN`), а не из `GAUGE_HALF`; пока не сделана.

Ось отсчёта габарита — ведомая ось коридора (`gauge_centers`); исключение —
зал: обе стены дальше габарита, и ось там берётся от рельсов блока 1
(замер: ведомая ось на 55 м гуляла −0.4..−1.7 м между кадрами при стоящем
поезде, и человек в центре пути «выпадал» из габарита).

Бины-'hole' в поиске НЕ пропускаются (человек на doubleT_obstacle стоит
ровно в таком), но находка помечается `confirmed=False`. Итог: человек
найден в 21 кадре из 21, ложных находок на чистых бэгах ~0. CLI:

```bash
python -m guard.obstacles for_hackathon/doubleT_obstacle --frame 40
python -m guard.obstacles for_hackathon/doubleT_obstacle --sweep 10
```

### `multitrack.py` — многопутность и стрелки

`track.straight_axis` сознательно выбирает ОДНУ ветку — ближнюю к лидару.
На стрелке и двухпутке в кадре ДВА пути, и до перевода стрелки из облака
не определить, куда поедет поезд. Этот блок находит ВСЕ ветки и отдаёт
наружу; выбором «нашей» не занимается. Четыре замера задали конструкцию
(подробно — в докстринге модуля):

1. Окно поиска шире, чем у блока 1 (±6 м: межосевое двухпутки ~4 м), и пик
   проверяется на «рельсовость»: доля точек его столбца в полосе высот
   головки у рельса ≥ 0.66, у стены/бордюра ≤ 0.16 (`RAIL_FRAC = 0.30`
   посередине). Без этого широкое окно даёт сотни ложных веток от стен.
1б. Связывание звеньев ветки — с предсказанием по направлению: при двух
   звеньях следующее ищется вокруг линейной экстраполяции с допуском
   `LINK_TOL + |slope|·df` (уходящая ветка законно уходит быстро: шаг веера
   на squareT_switch до 1.7 м/срез при LINK_TOL 0.35), первое звено — по
   LINK_TOL. Арбитраж между претендентами — в долях допуска (d/tol), иначе
   сеятель с фиксированным окном перехватывал пару у дуги с широким.
2. Дубли одного пути сливаются по центру: оси двух разных путей ближе
   полколеи быть не могут — иначе внутренние рельсы наложились бы.
3. Перекрёстная пара двух реальных путей (центр ровно посередине, колея =
   межосевое минус колея) — фантом, отбрасывается аналитически.
4. Путь за стеной — не маршрут: ветка помечается `blocked`, если стена
   кадра (`check_wall.detect`) проходит между своей осью и осью ветки у её
   дальнего конца — соседний путь сквозь проём обрывается ровно там, где
   проём закрывается, а уходящая ветка стрелки проходит МИМО торца
   платформы.

Находит перевод на squareT_platform_squareT_switch (f812-824) и двухпутку
roundT_doubleT (f150+). Коридор ветки — штатный `walls.trace` с осью ветки
(`branch_corridor`). CLI: `python -m guard.multitrack <bag> [--frame N |
--sweep N] [--corridors]`; в `run.py` — флаг `--branches` (одиночный кадр).

### `accum.py` — межкадровое накопление

Каждый кадр `walls.trace` считает коридор с нуля, и подтверждённая дальность
скачет между соседними кадрами. Причина не в тоннеле, а в дырах между
кольцами лидара: бин, пустой сейчас, был измерен кадр назад.

Накапливаются **не точки, а результаты**. Копить точки для габарита неверно —
движущийся объект размазывается в полосу вдоль пути, а он-то и нужен. Бин
несёт вывод «стена здесь», и у неподвижной стены выводы разных кадров
совпадают. Голосование медианой, бин подтверждён от двух голосов.

Позы берутся из `trajectory.npz` (`odometry.py` в корне проекта).

Уточнения этой сессии (все — замерами):

- **Отбраковка голосов по сносу и повороту** (`MAX_TURN = arctan(BIN/2 /
  MAX_RANGE)` ≈ 1.2°, выведен из геометрии бина, не подогнан): на кривых
  кадр, съехавший вбок больше чем на полбина или повёрнутый сильнее,
  голосует мимо своего бина и отбрасывается. Замер по кривым: 0.3-0.5° за
  6 кадров — под порогом, режутся только реально съехавшие.
- **Ближняя зона считается от БЛИЖАЙШЕГО голосующего кадра**, а не от
  старейшего: при `--sweep 10` сдвиг старейшего это 50 м, и бины до 50 м
  проходили с одним голосом, а при `--sweep 60` накопитель вырождался в
  одиночный кадр.
- Голос раскладывается в ближайший центр бина (round, не floor) — при
  дробном сдвиге он не дребезжит между соседними бинами; требуемое число
  голосов применяется к РЕАЛЬНО голосующим кадрам (кадры без позы голосов
  не дают).

- `CorridorAccumulator(poses, history=...)` — накопитель, `update` на кадр;
  возвращает копию коридора с полями `votes`, `reach_frame` (для сравнения с
  одиночным кадром) и `n_frames`
- `load_poses(bag_dir)` → позы из кэша одометрии

### `run.py` — сборка и CLI

`analyze(pts, wall_axis=True, with_structures=True, with_obstacles=True,
extra=None)` → `(axis, wall)`: один вызов на кадр, последовательно блоки
1 → 1б → 1в → 2 → 2б → 3. Ось блока 1в отдаётся в `axis['bins']` и подаётся
в блок 2 (`walls.trace(bins=...)`): коридор повторяет изгиб пути. Далёкая
ось блока 1б остаётся в `axis['far']` — она даёт измеренный в ближней зоне
отступ и диагностику, но коридор по ней больше не ведётся. Результаты
блоков 2б/3 лежат в коридоре ключами `wall['structures']` и
`wall['obstacles']` (блок 3 дёшев — 8-28 мс на кадр, включён по умолчанию).

Флаги CLI: `--frame N`, `--sweep N` (каждый N-й кадр), `--bar` (строка в
консоли), `--plot [PNG]` (вид сверху), `--accum [N]` (накопление, `N` —
глубина истории), `--accum-pts [N]` (агрегация ТОЧЕК прошлых кадров в
оценку кромок стен, полный SE(2) из trajectory.npz), `--branches` (после
основного тракта найти ВСЕ ветки пути — multitrack, только для одиночного
кадра).

`--accum` вместе с `--plot` даёт **сравнение двух версий одного кадра**: две
панели на общих пределах — сверху кадр сам по себе, снизу он же с
накоплением. Под нижней панелью подписано число голосов на бин: видно, чем
накопление отличается от одиночного кадра, а не только что «стало лучше».

История перед целевым кадром при этом **прокручивается**: накопитель копит
последовательным проходом, и без прогрева нижняя панель просто повторила бы
верхнюю. Пример на `doubleT_platform` f20: без накопления 14 бинов со
стенами и 60 м, с накоплением 16 бинов и 70 м — жёлтая зона «не
наблюдается» закрывается измерением.

### `draw.py` — визуализация

Три способа, от лёгкого к подробному:

- `corridor_lineset(...)` — Open3D-оверлей для `visualize_bag.py --guard`;
- `walls_lineset(...)` — Open3D-оверлей для `visualize_bag.py --walls`:
  найденные стены блока `check_wall` в 3D, то же, что `plot_axis.py --walls`
  на виде сверху. Каждая стена — своя цветная вертикальная лента ТОЛЬКО на
  своём отрезке `[d_lo, d_hi]` (экстраполяция не рисуется), высотой в полосу
  поиска `H_LO..H_HI`, с короткими штрихами на измеренных кромках. Цвета те
  же и в том же порядке, что `plot_axis.WALL_COLORS`, чтобы стена №N была
  одного цвета на 2D-виде и в просмотрщике. `--walls-lead` подсвечивает
  ведущую стену (считает ось блока 1 дополнительно);
- `corridor_bar(...)` / `corridor_line(...)` — строка на кадр, работает по SSH;
- `plot_top(...)` — вид сверху, показывает форму коридора целиком; с
  `wall_accum` рисует две панели, без накопления и с ним;
- `_panel(...)` — одна панель вида сверху на готовой оси matplotlib.

Цвет несёт статус бина, потому что именно он решает, можно ли верить
картинке: **зелёный** — габарит подтверждён измерением стен, **жёлтый** —
бин ведётся предсказанием («не наблюдается», не «свободно»), **серый** —
найденные стены, **синий** — ось пути.

Заливка вида сверху идёт посегментно, а не маской по `np.nan`: маска рвёт
полосу на острова и врёт, будто между бинами коридора нет.

### `eval_axis_far.py` — замер оси вдаль

Сравнивает ось блока 1б с картой пути (`track_map.npz`) и мерит две вещи
сразу: ошибку оси на 30/50/70 м и скачок между соседними бинами. Ось может
быть верной в среднем и при этом ломаной — излом даёт дёргающийся габарит.

Дальность входит в замер, только если она **внутри** покрытия карты этого
кадра. Покрытие сильно разное: медиана 149 м, но p10 = 43 м — на части
кадров карта коротка, и за её концом `np.interp` экстраполирует последним
значением, так что разница с ним ничего не значит.

Замер идёт **по одиночному кадру**: накопление (`guard.accum`) копит коридор,
а не ось, поэтому на эти числа не влияет.

```bash
python eval_axis_far.py
python eval_axis_far.py --bags roundT_pressureGate_roundT --step 5
```

### `plot_axis.py` — картинка оси вдаль

Показывает на виде сверху то, чего не видно в цифрах: где ось легла на
эталон, где отстала, а где улетела в сторону. Улёт важен особенно — на
кадрах с короткой картой он в метрику ошибки не попадает, но на картинке
виден сразу.

Считает кадр с нуля (`run.analyze`), накопление не использует: накопитель
работает с коридором, а не с осью. Сравнение стен с накоплением и без —
это `run.py --accum N --plot`.

```bash
python plot_axis.py roundT_pressureGate_roundT 108,123,240
python plot_axis.py roundT_pressureGate_roundT 108,123,240 -o axis.png
python plot_axis.py roundT_doubleT --worst 6     # найти худшие кадры самому
python plot_axis.py roundT_pressureGate_roundT 123 --raw   # + ось без сглаживания
python plot_axis.py roundT_pressureGate_roundT 108 --profile 47   # разрез
python plot_axis.py roundT_pressureGate_roundT 111 --walls --accum 5 --range 130
python plot_axis.py roundT_pressureGate_roundT 111 --corridor   # + коридор блока 2
python plot_axis.py doubleT_obstacle 40 --corridor --obstacles   # + находки блока 3
```

| Что на картинке | Цвет |
|---|---|
| путь по карте — эталон | зелёная толстая |
| прямая ось блока 1 (как было бы без стены) | оранжевый пунктир |
| ось блока 1б | красная линия, точки по статусу |
| от рельсов / прямая согласна / **ведёт стена** / дыра | фиолетовый / синий / красный / серый |
| кромка стены, за которую зацепилось ведение | чёрные точки |
| `reach` — дальше ось не подтверждена измерением | серая штриховая |
| стены `check_wall` (`--walls`) | цвет на стену, толщина по числу слоёв |
| **ось блока 1в по режимам** (`--walls`) | рельсы зелёный / середина двух стен голубой / ведёт стена оранжевый / продолжение формы серый |
| ось ближе к стене, чем бывает отступ — аномалия (`tight`) | красный крестик |
| отступ взят по умолчанию, не измерен | пустой оранжевый квадрат |
| габаритный коридор (`--corridor`) | зелёная полоса / жёлтая полоса |
| находки блока 3 (`--obstacles`) | красная рамка+точки в габарите / серая вне; пунктир — бин не измерен |

`--walls` рисует не только стены, но и **ось блока 1в цветом режима**: смена
цвета стоит ровно на том бине, где режим сменился. Это главный инструмент
отладки ведения — «ось уехала» само по себе ничего не говорит, нужно видеть,
ПОЧЕМУ: вела по рельсам, по середине двух стен, по одной стене с отступом или
просто продолжала форму в дыре. Заголовок несёт раскладку по режимам, ведущую
стену с применённым отступом и число `tight`-бинов.

`--corridor` рисует результат блока 2 (`walls.trace`): полоса по бинам,
**зелёная** там, где край упёрся в измеренную стену, **жёлтая** там, где бин
ведётся предсказанием («не наблюдается», а НЕ «свободно»), плюс серым
пунктиром кромка, в которую коридор упирается. По одной линии оси этого не
видно: ось может идти верно, а коридор в дыре выпрямиться и разойтись с
путём на метры. Заголовок несёт число измеренных бинов и `reach`.

`--obstacles` кладёт поверх находки блока 3 (`obstacles.detect`, тот же
`wall['obstacles']`, что считает `run.analyze`). Каждая находка рисуется тремя
вещами, потому что каждая отвечает на своё: **точки находки** подсвечены —
видно, из чего она собрана и не пыль ли это; **рамка** по её габаритам (по
дальности — окно поиска `OBST_WIN`, поперёк — измеренная ширина) — именно так
меряются ширина и высота в таблице `--sweep`; **подпись** с дальностью и
высотой — её и называют в тревоге. Красное — находка В ГАБАРИТЕ, серое —
объект мимо коридора (есть, но поезд проходит рядом); пунктирная рамка —
`confirmed=False`, бин не измерен ('hole'), находка настоящая, но за
неизвестным участком. Считаются и рисуются только находки в пределах
`--range`. Имеет смысл вместе с `--corridor`: коридор показывает, ДОКУДА
видно, а находки — ЧТО внутри.

Точки берутся из ТОГО ЖЕ кадра, по которому считался блок 3: `point_idx`
находки индексирует облако кадра, а не накопленное (`--accum` подкладывает
точки только под стены — движущийся объект перенос размазывает).

`--range 130` имеет смысл на поворотах: стены детектируются до 128 м, и
предел 100 м обрезал бы их на картинке (`MAX_RANGE` блока — 130).

Заголовок панели несёт отступ по сторонам, число бинов под стеной, выбранный
слой высоты и дальность перехода на ведение.

`--profile D` добавляет вторую панель: разрез поперёк на дальности `D` с
кромкой каждого слоя. Ей видно, **за что именно** цепляется ведение — на
круглом тоннеле красные точки выстраиваются столбиком по бокам, и сразу
понятно, сел ли выбранный слой на стену или на лоток.

### `metrics/obstacle_count.py` — сколько препятствий в бэге

Отвечает на вопрос, которого нет у картинки. Заголовок `plot_axis.py` говорит
«сколько находок в ЭТОМ кадре». Сколько препятствий в бэге — другое число:
настоящий объект живёт десятки кадров подряд (человек в `doubleT_obstacle` —
201 кадр из 201), и сумма покадровых находок посчитала бы его двести раз.
Поэтому модуль печатает два числа рядом — покадровые находки (нагрузка на
детектор) и **объекты**, то есть треки блока 3.5 (`tracker.ObstacleTracker`),
тот самый, что уже отсекает однокадровые транзиенты. Своей логики связывания
у модуля нет и быть не должно: замер обязан видеть ровно то, что видит
детектор.

```bash
python -m pavel.guard.metrics.obstacle_count for_hackathon/doubleT_platform
python -m pavel.guard.metrics.obstacle_count for_hackathon/doubleT_platform \
    --range 130 --accum-pts 5 --step 10 --episodes
```

Тот же замер печатается **рядом с картинкой** — флагом `--metrics` у
`plot_axis.py`, с тем же `--range` и `--accum`, что у самой картинки, чтобы
числа отвечали именно ей. Необязательный аргумент флага — шаг по кадрам
(по умолчанию 1, весь бэг). Печать идёт ДО окна: `plt.show()` блокирует
поток, и числа после него были бы видны только после закрытия окна.

```bash
python -m pavel.guard.plot_axis for_hackathon/doubleT_platform 120 \
    --range 130 --accum 5 --walls --corridor --obstacles --metrics --episodes
```

| флаг | что делает |
|---|---|
| `--range D` | предел ПО ВЫДАЧЕ находки, м (обработка всегда до `walls.MAX_RANGE` = 130). Тот же отсев, что у картинки: находку за её правым краем в счётчике видеть незачем |
| `--step N` | обрабатывать каждый N-й кадр. Для замера надёжнее 1: трекер считает пропуски в ОБРАБОТАННЫХ кадрах, и чем крупнее шаг, тем охотнее склеятся два разных объекта |
| `--accum-pts N` | агрегация ТОЧЕК N прошлых кадров полным SE(2) — то же, что `--accum` у `plot_axis` и `--accum-pts` у `run.py`. Имя от `run.py`: там `--accum` — это `CorridorAccumulator`, он копит бины коридора и препятствий не несёт вовсе. На находки влияет лишь косвенно: агрегат идёт в кромки стен, те задают границы коридора, те решают `in_gauge` |
| `--range-frames A:B` | ограничить прогон кадрами A..B |
| `--any-gauge` | трекать и находки МИМО габарита (по умолчанию только в габарите — как в `run.py --sweep`) |
| `--episodes` | таблица: строка на объект (кадры от/до, дальность от/до, поперёк, ШxВ, точек, подтверждён) |
| `--plot [PNG]` | НАРИСОВАТЬ найденные объекты: панель на объект, кадр наибольшего приближения, тем же `plot_axis.draw` с `--obstacles`. Без значения — окно, со значением — файл |
| `--only-confirmed` | с `--plot`: только подтверждённые (однокадровые транзиенты не рисуются) |
| `--top N` | с `--plot`: не больше N объектов, самые близкие |
| `--walls` | с `--plot`: добавить найденные стены (блок 1в) |

Число объектов само по себе не говорит, ЧТО это за объекты, поэтому рядом
с таблицей стоит `--plot`: он рисует по панели на объект — тот кадр, где
объект ближе всего (на нём он крупнее и виден лучше). Рисует тот же
`plot_axis.draw`, что и обычная картинка, чтобы рядом не стояли две разные
картинки одного и того же.

```bash
python -m pavel.guard.metrics.obstacle_count for_hackathon/doubleT_platform \
    --range 130 --accum-pts 5 --plot --only-confirmed --top 5
```

Замер на `doubleT_platform` показывает, зачем нужны фильтры: из 24 треков 15
однокадровых, а `--only-confirmed` оставляет 9, и на картинке видно, что
объекты 17, 18, 19, 21 — ОДИН человек справа (поперёк +1.2..+1.4 м),
подъезжающий с 15 м до 2.5 м, разорванный на куски на пропусках. То есть
«24 объекта» — это про находки детектора, а не про число людей в тоннеле.

Дальность в таблице — **от/до**, а не средняя: у едущего поезда объект
приближается, и «дальность эпизода» одним числом была бы ложью. Сортировка
по `d_near` — именно она определяет, насколько эпизод опасен.

«Кадров под тревогой» БОЛЬШЕ, чем «кадров с находкой», и это не описка:
подтверждённый трек живёт сквозь пропуски (`tracker.MAX_MISS`) — объект выпал
на дыру между кольцами лидара, но тревога по нему не снимается.

Замер на `doubleT_platform` (345 кадров, шаг 1, до 130 м): находок покадрово
157, в габарите 47, кадров с находкой 45 из 345, **объектов 24, из них
подтверждённых 9**. У этого бэга нет `trajectory.npz`, поэтому связывание
идёт в системе датчика, а не в мире (модуль печатает про это пометку), и
`--accum-pts` тоже недоступен — посчитать позы: `python odometry.py <бэг> --save`.

### Кромка берётся из линии кадра, а не окном по бинам (`line_edges`)

Ведение обрывалось задолго до конца облака. Замер причины — бины со статусом
`hole`/`stop` дальше `SEED_HI`, три бэга, шаг 10 кадров:

| причина отказа | roundT_pG | roundT_dT | dT_platform |
|---|---|---|---|
| пусто во всех слоях (нет покрытия) | 9% | 12% | 18% |
| в выбранном слое пусто, в соседних есть | 41% | 20% | 49% |
| точки есть и в выбранном слое (отсев) | 50% | 69% | 33% |

То есть **82-91% отказов — не нехватка точек**, и обе причины системные, а не
пороговые. Отсев даёт рекуррентность: окно `GATE` вокруг предыдущей кромки
плюс `JUMP_LIM` рубят то, что на дуге законно (стена уходит до 0.6 м на бин),
а потеряв кромку раз, окно ищет вокруг старого места и ведение встаёт при
полном облаке. Вторую причину даёт фиксация одного слоя на кадр.

Поэтому `trace_axis` берёт кромку не окном, а из **линии стены, найденной по
всему кадру** (`frame_edges` → `check_wall.detect`): бины там независимы,
слои сливаются в одну стену, а чужое снимается отбраковкой по совокупности.
Порогов не добавилось — `GATE` и `JUMP_LIM` в этой ветке не участвуют вовсе.
Старый тракт остаётся под `line_edges=False` для сравнения.

Два замера по ходу изменили отбор стены:

**Своя стена — ближняя к пути из протяжённых, а не самая протяжённая.** Чужой
объём тоже тянется вдоль пути: на `doubleT_platform` f90 длиннейшая линия
слева идёт по −5.88 м на 80 м (зал за стеной), а настоящая стена рядом —
−1.78 м на 76 м. Отбор по длине давал ошибку 3.51 м на 70 м. Отбор идёт по
**измеренному в кадре отступу**, а не по константе.

**Линия обрезается там, где перестала быть параллельной пути.** Своя стена
идёт вдоль пути, её отступ не растёт. На двухпутке одна парабола склеивает
стену и раскрывшийся второй путь в одну кривую: `roundT_doubleT` f115 даёт
−2.8 → −6.2 м к 50 м. Отбор по отступу этого не ловит — он смотрит на ближний
конец, где линия ещё верна. Порог тот же `OFF_MAX_RATIO`, что и у доверия к
кромке в цикле: это одно физическое утверждение, а не новое число.

## Ограничения

- **Граница применимости — 70 м.** На 90 м покрытие стен рассыпается, и в
  слое остаётся 20-40 точек: 10-й перцентиль по четырём точкам перцентилем
  не является.
- **Стрелку решает не стена, а `multitrack.py`.** Путей два, стена не
  параллельна одному, и куда поедет поезд — из облака не определить до
  перевода стрелки. Блок многопутности находит все ветки (перевод
  squareT_switch f812-824), но выбор маршрута за пределами тракта.
- **Коридор следует за осью блока 1в, пока она самосогласована.** Блок 2
  ведёт стены от `axis['bins']`; ложное ведение (ось пересекла стену — замер
  `doubleT_platform` f10/f20) отсекается инвариантом `MIN_OFF` и проверкой
  отступа от прямой оси, кадр тогда доводится прямой. Бины RAILS/CENTER под
  откат не попадают: ошибка оси против карты там med 0.07/0.16 м против
  1.15 у LEAD и 2.47 у HOLD.
- **Сторону стены нельзя считать от нуля лидара.** Стена, идущая вдоль пути,
  сторону относительно ПУТИ не меняет, но относительно нуля лидара и прямой
  оси — меняет, когда путь уходит вбок; `check_wall` сшивает такую стену в
  одну линию. Замер `roundT_pressureGate_roundT` f222: линия 2.5-112.5 м
  пересекает ноль на 52.8 м, от карты держит −2.43…−2.47 м (честная левая),
  а от прямой оси после 62.5 м выглядит правой с модулем ~1.75 и совпадает
  с правой затравкой ближней зоны. Сравнение по одному модулю сводило разные
  стены, и коридор скатывался на прямую ось на 55 метров.
- **Двухпутка ломает допущение об отступе.** На `roundT_doubleT` ширина
  коридора прыгает 3.88 → 7.37 м на 22 м (видно без карты), дальняя «стена»
  там — второй путь. Ведение это переживает, но ведёт его одна сторона.

### Что доработать дальше

Два открытых дефекта, оба замерены и оба НЕ в самой детекции, а в том, как
её результат используется. Порядок — по отношению эффекта к цене.

1. **Ведущая стена перескакивает между кадрами: 21% кадров** (27 из 131,
   `roundT_doubleT` — 6 смен на 21 кадр). `leading` выбирает сторону
   покадрово, без памяти: когда обе стены видны примерно одинаково далеко,
   выбор дребезжит, и картинка «пролистывается». Лечится гистерезисом — не
   менять сторону, пока новая не лучше текущей с запасом (`OUTER_MARGIN`),
   а не просто лучше. Одна функция.

2. **Линии заходят на путь: 14%** (55 из 392, вплоть до 0.04 м от оси).
   Дальняя стена заворота в проекции пересекает путь: внутрь габарита
   заходят 2-3 бина в самом НАЧАЛЕ линии, дальше отступ растёт нормально
   (замер f110 roundT_pressureGate: 62м 0.43 | 68м 1.02 | 72м 1.65 | … |
   128м 10.45). По качеству такие линии от настоящих неотличимы — span,
   слои, rms, число бинов совпадают в пределах разброса, порога по качеству
   здесь быть не может.

   Попытка обрезать ближний хвост по инварианту «стена не проходит через
   НОЛЬ ЛИДАРА» откачена: порог от нуля лидара — не тот инвариант. При 0.6 м
   он почти не срабатывает (47 заходов из 399), при 1.2 м чистит (10
   заходов), но роняет лучшую стену кадра p10 65 → 45 м, потому что на дуге
   своя стена законно подходит к нулю лидара близко. Резать надо по отступу
   ОТ ОСИ и не в `detect` (он не должен знать про ось — это его проверяемое
   свойство), а в потребителе, куда ось уже передаётся.

3. **Дубли параллельных линий.** `_merge` сливает линии соседних по ВЫСОТЕ
   слоёв; две цепочки одного диапазона высот, идущие в 0.3-0.5 м друг от
   друга, остаются двумя стенами. Слияние по общему участку дальности в
   пределах `MERGE_LAT` — косметика, но картинку чистит.

Чего делать НЕ стоит, и это проверено замерами:

- **Азимутальная развёртка вместо бинов дальности.** Идея верная (стена
  однозначна в полярных координатах, «докуда прошёл луч» не зависит от
  стороны отсчёта), контур на f111 прослеживается 10 → 107 м непрерывно. Но
  равный шаг по азимуту даёт крайне неравный шаг по дальности — угловой
  размер падает как 1/d: из 98 точек контура 68 легли в первые 10 м, а на
  60-110 м пришлось по 1-2 точки на десять метров, дальние участки
  перестали набирать `MIN_BINS`. Сквозной замер: ось med 85 → 60 на ВСЕХ
  шести бэгах. Работоспособная версия требует адаптивного шага
  (`RAY_STEP ≈ L/d`) и перекалибровки `MIN_BINS`, `MIN_SPAN`, `FIT_TOL`,
  `MERGE_*` — все они завязаны на сетку 5 м.
- **Нейросеть для дальних стен.** Замер: на накопленном облаке 1.3 млн
  точек, и разрез стены остаётся ровно тем же. Информации в данных хватает,
  не хватало параметризации; разметки на стены нет.
